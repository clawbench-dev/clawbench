# AI 群聊

群聊让用户把**多个已配置的智能体**（可跨后端，如 CodeBuddy + Claude Code + Codex）拉进同一个会话，就同一话题进行多智能体协作或辩论。单聊一次只能问一个智能体，用户得自己当"传话筒"在多个会话间复制粘贴；群聊把"谁接着谁说、每个人看到什么"交给系统编排，用户只需发一条消息然后旁观（或随时插话）。

群聊有两种形态，**建群时是否指定主持人决定模式，且不可中途切换**：

- **主持人模式（host）**：一个被指定为"主持人"的成员控场——它决定下一个该谁发言、给出什么指令，成员发言后主持人再决策，循环直到主持人发出结束信号或智能体讨论次数达到上限。像真实团队开会：有议程、有分工、有结论。
- **自由聊天模式（free）**：没有主持人，成员通过 **@ 提及**接力——谁被 @ 谁接着发言，被 @ 的人再把话头传给下一个人，形成一条可以延续的讨论链。像微信群里一群人自由接话。

两种模式都**默认串行**发言（后发言者能看到前者本轮内容）。若本轮的路由标签带 `mode="parallel"`（成员可自行使用，自由模式还可由用户侧的**「并发执行」开关**触发），被点名的成员则**并发发言、互不参考**——它们从同一份"群回合起始高水位"快照出发，谁都看不到同轮其他成员的输出。

**自动巡航（Auto-Cruise）** 是叠加在两种模式之上的**正交开关**（不是第三种模式）：打开后循环不再「把话权交回用户」，而是持续讨论到成员确认任务已满足用户要求（见下文流程图）。

### 自动巡航：确认回合的裁决

```mermaid
flowchart TB
    A[主持人干净收工的一轮] --> B{cruise 开?}
    B -->|关| H[照旧交回用户<br/>写「轮到用户发言」]
    B -->|开| P{有可派发的成员?<br/>非主持人 / 非用户 / 未离场}
    P -->|有| R[照常派活<br/>提问卡仅展示，不接管话权]
    P -->|无| C[触发确认回合<br/>写系统行 + 隐藏注入]
    C --> D{模式}
    D -->|host| E[只问主持人<br/>一人拍板]
    D -->|free| F[群发全体<br/>≥ ⌈n/2⌉ 确认]
    E --> G{确认完成?}
    F --> G
    G -->|是| I[写「已确认完成，共 N 轮」<br/>host 结论在同一回复内]
    G -->|否| J[继续正常讨论一轮<br/>接力再枯竭时再确认]
    J --> C
```

巡航只在「何时结束」这一条上与普通循环分叉，路由方式完全不变。裁决按模式不同（host 一人拍板 / free 至少半数确认），且**每回合重置**——只统计本次确认回合内的声明，主持人在普通轮里的主动声明只显示徽章、不计票。

**派活优先于提问**：主持人在同一轮里既点名成员、又向用户提问（AskUserQuestion 卡片或大白话）是常见形态。此时**路由必须赢**——有可派发成员就照常派活，提问卡照常渲染但只作展示，不把整轮改写为确认回合。否则被点名的成员一句话都不会说（`resolveSpeakerGroups` 根本不会被调用），用户看到的是「@ 了两拨人，一个都没动，反过来问我问题」。只有**没有**任何可派发成员时，提问/@User/大白话提问/无标签收尾才触发确认回合。

## 功能与设计要点

### 功能清单

- **建群**：会话列表头的 `+`（新建会话）打开**共用的选人抽屉**，抽屉头部的「单聊 / 群聊」分段开关切进建群模式（多选 + 可选指定主持人），一次请求原子创建群与全部成员（失败整批回滚，不留"只有主持人的半成品群"）。**开关的门槛是「至少一个可选智能体」而不是「至少两个不同的智能体」**——重复实例本就是独立成员，所以只装一个智能体也能建群（选中它、用行内 `− 2 +` 步进到 2）；只有可用列表为空（全被禁用）时才隐藏开关并显示空态。**同一智能体可被加进同一群多次**：选中行的步进器 `− N +` 可把同一智能体加多份，每个实例是一个独立成员。**建群时不输入群名**——后端用主持人名占位（`GroupHostTitle`："XX 的群聊"），自由模式用 `GroupFreeTitle`（"群聊"），**按请求 locale 本地化**（标题会落库并显示在会话列表，故不能硬编码中文），首条消息后由 auto-title 接管
- **空状态按模式区分**：空群的首屏卡片按 `groupMode` 渲染不同文案——头部行（头像堆叠 + 模式 chip：皇冠 / @）+ 一行模式说明 + 3 条 bullet 提示。两种模式的路由方式完全不同（主持人决定 vs 成员互相 @ 接力），一句固定提示只能在一种模式下正确、在另一种下产生误导
- **成员多实例与临时昵称**：同一智能体的多个实例自动获得唯一显示名——**首个实例保留智能体本名**（`Claude`，即入群时带的显示名/智能体名）；**重复实例（第 2 个及以后）从代码内置英文名池 `groupNamePool` 取第一个未占用的名字**（`Alice`/`Bob`/…）；**池耗尽时回退 `本名 序号`**（`Claude 2`、`Claude 3`……，**永不生成 `Claude 1`**）；取名避开群内其它成员名与用户昵称；池名**永不取**与本批次任一实例本名、或群内已有智能体本名相同的名字（**真名预留**——真实智能体名恒被保留、与 order 无关）。这样 AI 之间按名字路由时不会歧义。**已存在的实例不被改名**（历史快照），故跨批次再加实例时，先前那个保持原名、只有新实例取名池名。**主持人**仍按智能体指定，取该智能体的**首个实例**。名池刻意不可配置、无设置 UI
- **成员头像**：`chat_sessions.agent_avatar` 存成员**自身**的头像 SVG 快照（前端 DiceBear 按成员名生成、随机风格、经 `POST /api/group/member-avatars` 落库，以对齐分享/导出——公开分享页无 DiceBear 运行时）。**只有同一智能体在群内被添加多次时才生成**：第 **2 个及以后**的实例各生成一个（按唯一昵称做种子，故彼此可区分）；**第 1 个实例与群内唯一的实例都不生成**——没有需要区分的副本，保留智能体自身头像即可（`speakerFromMember` 在 `agent_avatar` 为空时回退智能体头像）。存量群不回填，只在建群/加成员时生成
- **真实智能体名披露**：`SpeakerIdentity.agentName` 携带底层真实智能体名（成员显示名 ≠ 实时智能体名时非空），前端在消息的「头像 + 昵称」之后以弱化样式 `.msg-speaker-real` 显示，让读者知道发言的智能体是谁
- **点发言人头像直达智能体配置**：消息的发言人头像是一个按钮，点击打开该成员的**智能体配置页**（压入设置导航栈，返回回到会话）。**必须用真实 agent id**——消息自带的 `agentId` 是成员**行 id**，任何配置页都解析不到；故 `GroupSpeakerIdentity` 额外携带真实 `agentId`（`GroupMemberInfo.agentId`），由 `ChatMessageItem` 用它 emit `open-agent-config`，经列表/面板转发到 `App.vue` 记录会话跳转来源并深链到 `agents:<id>` 详情页。id 无法解析时、以及只读分享页上，头像不可交互
- **成员管理**：群会话顶部横向头像条（主持人排最前、最多 4 个，最左端一个模式徽标——主持人=皇冠、自由=@）展示成员，**点整条头像条**打开群聊设置面板（`GroupSettingsSheet.vue`）；输入框下方的会话信息栏（群聊时显示巡航 / 自动批准两个 chip）末尾另有一个「群聊设置」入口打开同一个面板（它驱动头像条暴露的 `open()`，而非另挂一个实例，避免重复拉取花名册与两个面板状态漂移）。面板表头右上角是「添加成员」（打开多选抽屉批量加人，同样支持多实例），面板内可移除成员（**主持人的删除按钮保留但灰显且不可点**——它是群的唯一调度者，移除会让群失去路由；保留按钮是为了让每行的用量 chip 与尾部操作列对齐，缺一个按钮会把该行整体左移）。**主持人/离场标签紧跟在名字与真实智能体名之后**，不靠右对齐——它们描述「这是谁」，不是行级操作。增删成员都会在时间线写一条**居中的系统细条**（"XX 加入了讨论"/"XX 已离场"），让全员知道人员变动。**历史发言保留并标记"已离场"**——删掉某人发言会让后续"B 回应 A"失去上下文。**移除后再加同一智能体 = 新建实例**（不复用旧行、无连接恢复），序号继续递增。**系统细条在「写入时」按 `model.Language` 本地化**（`GroupMemberJoined`/`GroupMemberLeft`/`GroupUnknownMention`）：这些行既落库、又以 `[系统] <文案>` 注入每个成员的上下文，所以必须是可读句子而非键名；切换语言不追溯翻译历史（与决策 96b 一致）
- **成员上下文用量（花名册 + 详情面板）**：群聊设置面板的成员行右侧显示**该成员自己**的上下文占用（`Activity` 图标 + 28×6 进度条 + 百分比，与单聊会话信息栏同几何、同色阶），点整行打开**与单聊完全相同的设置抽屉** `SessionDrawer`（`target-session-id` = 成员行 id，默认落在 usage 页签），因此成员与单聊的设置界面是同一个组件、同一套语义（模型 / 思考深度 / 模式 / 传输 / 上下文用量 / 压缩）。**不再有 `MemberContextSheet`**：那会变成第二份面板，与单聊的设置界面漂移。**数据源是成员行自己的 `context_state.usage`**——成员回合的 `RunConfig.SessionID` 就是成员行 id，执行器的 `usage_update` 持久化写的是它，群行从不被写；活 ACP 连接有缓存时接口优先返回缓存（更实时），连接被空闲回收后回落 DB。**从未上报过用量的成员显示 `—` 而不是 0%**（CLI 传输的智能体不上报窗口，0% 会捏造一个不存在的测量）；**已离场成员不显示 chip 且整行不可点**（冻结的旧数字会误导，且它已不在讨论里）。面板里可**压缩该成员的上下文**（`POST /api/group/member-compact`，见下）；打开面板期间收到该群的 `usage_update` / `stream_finalize` 会**去抖 1.5s 重拉花名册**，否则数字一打开就冻住
- **智能体讨论次数上限**：全局设置（`chat.group_max_speeches`，默认 100，在 设置 → 聊天 → 群聊 里改），含义为「轮到用户发言前，智能体之间最多发言多少次」。**主持人模式与自由模式语义一致，只计成员发言**（主持人的路由 / 汇总回合不计）。达到上限即停止 AI 讨论（不管当前轮到谁发言）、写一条系统消息「成员间讨论次数达到上限」；主持人模式额外再产出一份汇总
- **@ 成员卡（输入侧）**：在群输入框用 `@` 唤起补全菜单（**可在输入框任意位置触发**——只有紧跟在 ASCII 字母/数字/下划线之后的 `@` 不触发，以免把 `a@b` 这类邮箱当引用；中文句子没有词间空格，`请@某人` 必须能唤起），**成员候选排在文件候选之前**（群里 `@` 通常是点名发言）。选中后不插入原始标签，而是在附件条生成一张**成员卡**——卡片显示成员真实头像 + 名字，**卡片本身即公开点名**，卡片上的批注则是**密送**（`private`）。**有密送时才显示锁图标**（无密送不占视觉噪音）。用户自己的公开问题由输入框正文承担（后端以「昵称: 正文」注入成员）
- **用户昵称**：人类用户在群聊里的保留显示名（`chat.user_nickname`，默认 `User`，在 设置 → 聊天 → 群聊 里改），成员用这个名字 `@` 你、注入前缀也用它。**与智能体名双向不可重名**——智能体建/改名/复制时拒绝等于昵称，设置昵称时拒绝与现有智能体同名；字符受限（禁引号/尖括号/逗号/控制字符，≤32 rune），因为它会被写进路由标签的 `targets` 属性。改名时同步迁移待投递的密送，避免孤儿
- **@ 接力（自由模式）**：用户和成员都能用 `@` 指定下一个发言人。成员输出里的 @ 把目标排到队尾，@用户昵称（保留名）则把话头交回人类、暂停接力
- **交回用户必写系统行**：AI 讨论**干净收尾且话权回到用户**时，统一由 `runLoop` 写一条居中系统行「轮到用户发言」（i18n `GroupYourTurn`）。覆盖全部收尾路径——自由模式接力自然耗尽、成员 `@` 用户、主持人结束信号、成员发言次数达上限、以及**成员/主持人发出 AskUserQuestion**。中间排队轮次不写（`GetQueuedCount>0` 时抑制），取消/报错收尾不写。`handUserBack` 只清用户密送账，不再写系统行
- **AskUserQuestion 交回**：成员或主持人的发言里带 AskUserQuestion（转换后的 tool_use，或未转换的 `<clawbench-ask-question>` 文本）即视为向用户提问——立刻停下接力、话权回到用户，即使同一输出还 `@` 了其他成员（提问优先于点名）
- **并发执行（自由模式）**：群级持久设置 `parallelDefault`（存 `context_state`），**只在自由模式显示**（主持人模式下用户不参与路由，与"讨论次数上限"行恰好互为镜像）。打开后，**用户 @ 的多个成员合并为一个 parallel 组并发发言**（不 @ 人时全体成员并发）；它只作用于"用户种子"，**不影响智能体之间 @ 出的组**（那些仍按各自标签的 `mode` 走）。**两个入口读同一个服务端值**：聊天区底部 session-info 栏的「并发执行」chip（仅自由模式渲染，点击直接 PATCH + 刷新花名册）与群设置面板里的同名开关
- **密送（BCC）**：一条只有指定目标看得到的消息（`private` 提及），在该目标**下一次发言时**注入一次。用于"暗中给某人递话"这类场景。**权限按模式不同**：**主持人模式**下主持人 ↔ 成员可双向密送、用户可密送给任何人，但**两个普通成员之间禁止**（主持人看不到的私下串联正是主持人模式要防的）；自由模式无主持人，任意组合均可。规则由 `noteAllowed` 在**写入时**判定（`storeRouteNotes`），被禁止的密送从不落库。投递时每条密送带**发送者署名**（`group_pending_bcc.sender_role`/`sender_name` → 「主持人密送给你」/「Alice 密送给你」/「User 密送给你」），不再一律记在主持人名下。每个目标的待投递队列上限 64 条，超限丢最旧（过期的私下交代价值低于刚写的）
- **成员间公开 @ 不触发调度（主持人模式）**：成员可以互相 `@`，注入时渲染成可读的 `@B 内容`（其他成员看得见这段交流），但**不会**把被 @ 的人排进发言队列——主持人独占调度权。自由模式下成员的 @ 就是接力信号，会把目标排到队尾
- **群内附件与引用**：群消息支持文件附件、`@` 文件补全、引用卡片——与单聊逐字一致（附件在注入成员时渲染，气泡仍靠 `files` 字段渲染）
- **人类插话**：群回合运行中发消息走**排队**（复用单聊队列）。排队条目的按钮文案为「插话」，语义是**中断本轮并发送**（= 停止当前回合、**保留队列**、该消息作为下一回合运行）——与单聊一致，**不是**「取消」（取消会清空队列）。群聊**不提供**「插入当前回复」：群回合是多轮循环，没有单一在跑回合可注入，且注入端点按会话 id 找 ACP 连接，而群成员各自用**成员行 id** 建连，群 id 下无连接、注入必然失败。实现上群回合按**群会话 id** 注册可中断回合（`RunGroupTurnDrain`），使 `POST /api/ai/queue/interrupt` 能命中；成员回合的 executor 再从**群槽位**读取中断原因，避免被打断的成员发言被盖上「已取消」徽标
- **自动巡航（Auto-Cruise）**：一个**正交开关**（不是第三种模式），叠加在主持人/自由模式之上，只改写「何时收敛」——把循环的终止从「交回用户」改为「成员确认任务已满足用户要求」。路由方式（谁点名谁）完全不变。打开后，**所有「本应交回用户」的动作全部拦截**，改为触发一次**确认回合**（隐藏注入「不要向用户提问，自主判定是否完成，完成则输出 `<clawbench-goal-satisfied/>`」+ 可见系统行「自动巡航：系统正在向成员确认任务完成情况」）。主持人侧共**六种**收工形态：结束标签、`@User`、AskUserQuestion 卡片、未被询问的完成声明（`<clawbench-goal-satisfied/>`）、**无标签的收尾散文**、**用大白话向用户提问**（如"要我继续吗？"）——但**这六种只在「没有可派发成员」时才触发确认**：主持人同一轮既点名成员又提问时，派活优先，提问卡仅展示（否则被点名者一句话都不会说）；成员侧另含 `@User`、提问与接力自然枯竭。**确认是唯一入口**：主持人若在未被询问的普通轮里直接声明完成，不算数，仍触发确认轮。**开关实时生效**：`cruiseOn()` 每次读（单条主键查询），回合跑到一半才打开巡航也立即接管，host 提示词随之每次 refill 重建——不再需要等下一条用户消息。裁决按模式不同——**host 一人拍板** / **free 群发全体活跃成员、≥ ⌈n/2⌉ 确认**；确认通过写「自动巡航：任务已确认完成，共 N 次发言」系统行，host 的最终结论在同一条确认回复里写出（不再单独跑汇总）。未通过则继续讨论一轮、接力再次枯竭时再确认（确认↔讨论交替）。每回合重置（只统计本次确认回合内的声明，按时间线高水位 `floor` 取 `memberOutputAfter`）。`group_max_speeches` 作为安全阀保留（撞上限仍按既有路径收尾、不写完成行）。**开启巡航强制打开自动批准（单向联动，单聊/群聊同一规则）**：巡航无人值守，若成员弹出权限确认无人应答会卡住整轮；由后端在 cruise PATCH 上强制 `applyAutoApprove(true)`（群聊 fan-out 到所有成员行 + 活连接），前端 ref 同步置真；关闭巡航不动自动批准。前端在群聊输入框下方的会话信息栏里显示「自动巡航」chip（开启时高亮并显示「巡航中」，点击即可开关；与群设置抽屉里的同名开关共用同一服务端值）、在确认完成的发言者旁显示青绿「已完成」永久小标签。巡航进行中用户发消息 → 排队
- **`/cb-*` 命令在群内生效**：命令模板注入本回合第一个发言者的 prompt（群里由主持人执行一次），结果进时间线供讨论；`/btw` 旁路问答不受影响
- **群聊可分叉（回溯仍不可）**：群会话的分叉按钮与单聊一样可用；回溯仍隐藏且服务端拒绝——截断群时间线会让每个成员的 `seen_cursor` 指向已删除的行，下一轮注入会漏掉一段上下文。分叉的目标可以是单聊，也可以是另一个群聊（弹窗里重新选成员/主持人，预填原班人马）。**历史处理**：涉及群聊的一端一律**不复制消息行**（群时间线的 `agent_id` 是成员行 id，复制到新会话里解析不到成员，会渲染成一整屏无归属的 AI 发言），改为把源历史渲染成背景文本写进目标会话的 `context_state.fork_context`，新会话保持空白并写一条系统行标明来源会话名。**只取聚合时间线**（用户消息 + 成员发言，跳过 `role='system'` 系统行与工具调用/思考——成员之间本就只交换发言文本，见决策 #9），因此预算（`chat.fork_context_budget`）能覆盖几乎整段讨论。**注入范围是每位成员各自**：`snapshotTurn` 在成员自己的 `seen_cursor == 0` 时把背景拼到 prompt 最前面，成功发言后游标推进、不再注入；失败/取消不推进游标，所以重试仍带背景。群行上的背景不清除，故分叉后新加入的成员首轮也会收到。**切点含被点击的消息自身、不向后扩展**——群聊对一条用户消息的"回答"是多人讨论，没有唯一的"那个回复"，按单聊规则取"紧随其后的第一条 assistant"会任意地只保留第一位发言者

### 设计要点

- **巡航是「正交开关」而非第三种模式**：它只接管「何时把话筒交回用户」这一个决策点，路由/并发/密送/成员管理全不受影响。因此实现上它不是一条新的循环，而是叠加在共享循环内核上的一层门控——`cruise` 关闭时各收尾动作照旧交回用户，打开时全部改判为「触发确认回合」。**确认回合是唯一收尾入口**（`confirmCruiseDone` 只有这一个调用点），主持人在普通轮里的主动声明只显示徽章、不计票——「主持人自己说了算」正是巡航要防的过早收工
- **「主持人想收工」的检测必须覆盖模型的实际写法，而非标签的规范写法**：主持人表达"做完/想停"有多种表现，早期只拦标签形态，漏掉最常见的一种——**不写任何路由标签、直接写一段收尾散文**（模型认为做完时的自然写法）会落进"零路由"分支、连错两次即 summarize 中止整轮，全程不经过确认轮（生产库有铁证：两段无标签散文后紧跟 abort 日志、时间线零系统行）。修法是把它并入 `hostRouteFailure`（巡航下第二次失败改走确认轮，有界）；并补「主持人用大白话向用户提问」（如"要我继续吗？"）——检测只看**最后一行非空文本是否以问号结尾**，这是唯一精确的规则：扫任意行会命中主持人**复述用户问题**（实测 3/112 vs 6/112）。误报代价低（多问一轮确认，主持人直接路由即拒），漏报才是被报的 bug，故规则偏保守
- **每回合重置靠时间线高水位而非内存**：确认回合开始前记下时间线最大 id（`floor`），结束后只解析该回合内（`memberOutputAfter(member, floor)`）的声明。这样「上一轮的完成声明不计入本轮投票」天然成立，且零 DB 迁移（设计初稿的内存统计被替换为按 `floor` 读时间线，结果等价）
- **成员就是一条隐藏的 `chat_sessions` 行**：成员行（`session_type='group_member'`）天然携带 `agent_id` / `transport` / `model` / `external_session_id` / `auto_approve` / `context_state`——正是"一条持久连接"所需的全部字段。于是 ACP 连接池按 session id 键控、空闲回收、resume/load 恢复、CLI `--resume` 全部**零改动**继承。唯一代价是会话列表要过滤掉成员行（用**白名单** `session_type IN ('chat','group')`，而非黑名单——新增查询漏加条件时白名单默认隐藏、黑名单默认泄漏）
- **成员的上下文是「成员行自己的」，群行没有上下文**：单聊的上下文面板读的是"当前会话"的 `context_state.usage`，而群时间线上有多路上下文、没有唯一所指，所以群聊信息栏一直刻意不显示它。每个成员回合的 `RunConfig.SessionID` 是**成员行 id**（`TimelineSessionID` 才是群），执行器 `flushPendingContextState` 因此把用量写进成员行——花名册直接读这份数据即可，**无需改采集链路**。反过来，`useChatStream` 的 `usage_update` 分支按**信封 session_id**（群 id）写前端缓存，那份值语义上是"最后一个发言成员"的，**新代码不得消费它**（要修需给信封加 speaker_id，属另一件事）
- **成员压缩不能走 `/api/ai/chat`**：群回合写的是群时间线，`/compact` 会被当成普通用户消息落库、再写一条助手回复，群里每个成员随后都会把这两行读成讨论内容。`POST /api/group/member-compact` 直接驱动该成员的 ACP 连接、把状态事件持久化到成员行、**不在群时间线产生任何输出**。守卫按序：群正在跑回合（成员连接忙）→ 409、成员不属于此群或已离场 → 404、成员非 ACP 传输（无命令通道）→ 400、同一成员已在压缩 → 409；服务端硬上限 3 分钟，期间用 `markGroupMembersActive` 挡住 ACP 空闲回收。**压缩期间发消息会排队而不是并发执行**：压缩直接驱动该成员的 ACP 连接，群回合若同时开跑就会在同一 ACP 会话上发第二个 prompt——agent 回 `Session is busy`（用户消息收到错误气泡），且 `RegisterSession`/`promptCancel` 是覆盖语义（压缩的事件流被静默丢弃、其中一个 prompt 变得不可取消）。因此 `AIChat` 在 claim 后额外检查 `GroupHasCompactingMember`，命中就交还 claim 走排队，压缩结束时 `wakeQueuedAfterCompaction` 唤醒消费者。**压缩必须在时间线上留痕**：压缩会静默改写该成员记住的内容，之后它答得比先前笼统、看起来像前后矛盾。因此开始/完成/失败各写一条居中系统行（与成员增删同一条通道，文案写入时按 `model.Language` 本地化）：开始写在 agent 往返之前（那几十秒的静默正是「它怎么突然不记得了」的来源），完成报出压缩前后占用（`32% → 3%`，未知窗口用 `—` 而非 0%），失败收尾这一对——只写「开始」会让时间线永久宣称一次没发生的压缩
- **消息只存一份，存于群会话**：成员之间只交换**发言文本**，工具调用与深度思考不进他人上下文。所有消息落进群时间线，成员行没有 `chat_history` 记录——从根上消除"两份副本不一致"的问题。**唯一例外是 AskUserQuestion**：成员向用户提出的提问卡会被渲染成可读文本注入给其他成员（见下条），因为"某人在问用户什么"是讨论上下文，而非私有工具细节
- **`run_turn` 的时间线解耦**：执行器里 `SessionID` 身兼两职——连接语义（用成员行 id，如写 `external_session_id`、查连接池）与时间线语义（用群会话 id，如落库、广播、摘要）。因此引入第二个字段 `TimelineSessionID`（缺省等于 `SessionID`，单聊路径行为不变），连接调用点用 `SessionID`、时间线调用点用 `effectiveTimelineSessionID()`。**`UpdateLastRead` 是例外**——它保持成员行 id，否则任一成员回合都会把**群**标记已读、群徽章永不亮
- **增量注入靠"发言游标"而非全量重放**：每个成员在 `context_state` 里存一个 `seen_cursor`（上次发言时群时间线的最大消息 id），下次发言只注入 `id > 游标 且作者≠自己` 的消息。这既保证成员看到讨论进展、又不重放自己说过的话。**游标只在回合成功时推进**——失败时推过去会让那段上下文永久丢失（成员后续答非所问且时间线看不出）
- **路由用结构化标签，解析失败回退轮转**：主持人输出 `<clawbench-mention targets="A,B">指令</clawbench-mention>`，后端解析出本轮发言者（有序）；标签可选带 `mode="parallel"` 表示这批目标并发发言（缺省串行，未知值回退串行）。**检测即解析、不可解析不剥离**（与 `askquestion` 的"绝不丢内容"契约一致），并回退到"下一个未发言成员"轮转；连续失败 2 次自动收尾。标签解析是独立叶子包 `internal/grouprouting`，与前端 `groupRouting.ts` 互为镜像、由 parity 语料双向固化
- **路由标识不对称是有意的：AI 用名字、用户用成员行 id**：`lookupMember` 先按成员行 id 精确匹配、再按显示名匹配。AI（主持人/成员）拿不到成员行 id，只能写**显示名**；用户 @ 提及由前端插入**成员行 id**（精确引用，改名/重名都不会误路由）。因此成员名**必须唯一**——这正是多实例需要唯一昵称（名池名 / `Claude 2`）的原因；用户侧本就按 id 路由，天然支持多实例
- **成员显示名以 `agent_name` 为权威，不回退智能体名**：`speakerFromAgent`（会话自身 agent）仍用实时 `agents.name`，但成员走 `speakerFromMember`，成员名取存储的 `agent_name` 快照。这样改智能体名不会追溯性改写群历史发言在分享/导出里的名字，多实例也各有其名。成员头像同理以 `agent_avatar` 快照为准，`speakerFromMember` 缺失时才回退智能体头像；真实智能体名经 `SpeakerIdentity.agentName` 单独披露（不覆盖昵称）
- **每个成员的 prompt 会声明其"自身显示名"**：成员/主持人/自由成员的 system prompt 都注入「你的群内显示名是「X」」，并附「其他成员」名单（排除自己）。**这是多实例身份不混淆的前提**——否则 AI 会退回 CLI 自身身份（agent 名），多个实例都自称 `Codebuddy`（甚至照名单瞎编数字），真实缺陷即四个同名实例全部报错自己的名字
- **主持人只控场、不代做具体工作**：主持人本身是完整成员（有全套工具，`/cb-*` 命令也由它执行），所以提示词必须显式划边界——它负责拆解任务、决定发言者、下指令、汇总结论，**写代码/改文件/跑命令/查资料等交给成员**，且明确禁止「先自己做完再通知成员」（真实失败形态是它干完活才派活，那时成员已无事可做）。例外只有两种：群内没有其他成员、用户本轮直接要求它本人执行。**巡航确认轮同样适用**：发现遗留工作时要求它**点名成员去完成**，而不是自己继续做——该处旧文案「请先继续完成它们」直接与角色边界冲突，是主持人抢活的来源之一（`TestBuildHostSystemPrompt_DelegatesWork` / `TestBuildCruiseConfirmPrompt` 钉住两侧）
- **两模式共用同一循环内核**：主持人模式与自由模式的回合脚手架、成员发言+游标推进+密送投递、@用户昵称交回、目标解析全部收敛到共享抽象（`prepareTurn` / `runSpeakerTurn` / `drainSpeakers` / `resolveSpeakerTargets`），差异只在"如何补充下一个发言者"（主持人用有界 `refill`，自由模式用自扩展 `onSpoke`）。避免两套循环逐字重复后各自漂移
- **用户昵称是"保留名"，不能与成员名撞车**：昵称会被写进路由标签的 `targets` 属性并作为注入前缀，若与某个成员同名，`@` 到底指人还是指成员就无法区分。因此昵称与智能体名**双向唯一**（建/改/复制智能体与设置昵称两处都要校验），且昵称受限字符集（禁引号/尖括号/逗号/控制字符）以免破坏标签语法。改名时把 `group_pending_bcc` 里按旧名键控的待投递密送一并迁移，否则已发出的密送会变成永远投不出的孤儿
- **串行发言可用"最新流式行"定位，并发发言必须按 id 定位**：`UpdateStreamingMessage` 按 `session_id=群 AND streaming=1 ORDER BY id DESC LIMIT 1` 命中行——这只在"一条时间线上只有一路在飞"时成立（单聊、或**串行**群回合）。并发发言时多个成员的流式行共存，落错行就会串台，因此执行器持有自己的占位符 id、改用 `UpdateStreamingMessageByID`（按 `id + session_id` 精确命中）。**并发组的快照必须整组一次性取自"回合起始高水位"**（`runParallelGroup` 在启动任何成员前先 snapshot 全部），否则后启动的成员会看到先启动者的输出，破坏"互不参考"。并发度另有启动上限（`maxParallelLaunches`），分批启动不影响快照不变性
- **单个成员失败不终止整个群**：成员发言失败复用单聊 `failTurn`（可见 warning block、带成员归属），循环继续、主持人可改选；失败残留保留在时间线供用户查看。主持人跑挂则回退轮转继续，再失败才终止群回合。**任何失败都不丢已有发言**（已落库）
- **成员能看到彼此的 AskUserQuestion**：某成员（或主持人）向用户发出的提问卡，会以**可读文本 + 方向标注**注入给其他成员——形如 `[A 向用户提问，等待用户回答] 用哪个方案？: A — 快, B — 稳`。两个理由：①"某人在问用户什么"是讨论上下文，成员需要据此判断自己该不该补充、还是等用户拍板；②不加方向标注时，成员会把问题误读成普通讨论内容而抢先回答。渲染复用 `askquestion.PlainText`（TTS 与推荐提示词用的同一个），故措辞不会与朗读版本漂移；**原始 `<clawbench-ask-question>` 标签绝不注入**（同 mention 标签的模仿事故，决策 #67），剥离后由方向标注行补回问题本身。覆盖两种持久化形态——转换后的 `tool_use`/`AskUserQuestion`（正常路径）与仍带原始标签的 text block（转换缺口/不可解析），后者按 askquestion 契约以可读 Markdown 降级。**纯提问消息（无散文）也注入**——此前 `ExtractPlainText` 对其返回空串，整条被跳过，其他成员根本不知道有人提了问
- **群成员的连接受 ACP 空闲回收保护**：成员行是隐藏会话，不会被"用户可见 running 会话"查询命中，因此 ACP 空闲 sweep 会误杀正在使用的成员连接。编排器维护"当前群回合正在使用的成员行集合"，sweep 判定回调同时查它——**不动 `GetRunningSessionIDs`**（那是喂会话列表与项目删除判定的，混入隐藏成员行会误触发"项目有会话在跑不能删"）
- **保密优先于保内容**：密送的注入侧是 **fail-closed**（剥离一切畸形/嵌套/未闭合的提及形态），显示侧是 **fail-open**（只认良构、畸形保留原文供用户查看）。摘除顺序是安全核心——`Parse` 必须在剥离一切标签后的文本上计算"标签前背景/指令"，否则密送会经公共指令段或共享背景泄漏给所有成员
- **密送权限只禁「成员 ↔ 成员」**：主持人模式下主持人独占调度权与共享记录，所以私密通道必须**绕过不了主持人**——主持人 → 成员（单独交代）、成员 → 主持人（向上汇报）、任何涉及用户的组合（用户地位高于主持人）都允许；唯一禁止的是两个普通成员私下串联。判定放在**写入侧**（`storeRouteNotes` + `noteAllowed`）而非投递侧：被禁的密送从不落库，任何新增投递路径都不会让它复活。自由模式无主持人，全放行——密送是那个模式仅有的侧信道
- **成员提示词必须写出真实主持人名**：`targets` 按**显示名**解析，所以 `BuildMemberSystemPrompt` 的密送示例必须带上主持人实际的群内名（由 `groupTurnSetup.hostMemberID` 解析），不能写「主持人名」占位符——模型会原样照抄，目标解析不到任何成员，密送被静默丢弃。自由模式无主持人，传空串即整段省略（那里由 `BuildFreeMemberSystemPrompt` 说明不设限）
- **密送署名必须真实**：`group_pending_bcc` 存 `sender_role`/`sender_name`，投递时逐条渲染「主持人密送给你」/「Alice 密送给你」/「User 密送给你」。此前一律写死「主持人密送给你」，把自由模式成员之间与用户发起的密送都误记在主持人名下；空 role（升级前的旧行）回退到历史文案，保证未投递的旧笔记读得通
- **群聊跳过逐成员摘要推荐**：成员回合的 Finalize 不跑摘要，**只在整轮群回合结束时跑一次**——否则 N 个成员 × 轮数会产生大量 LLM 推荐调用 + 全表摘要扫描

## 数据模型

| 表 / 列 | 用途 |
|---|---|
| `chat_sessions.session_type` | `group`（群会话，独占时间线）/ `group_member`（成员连接绑定行，用户不可见） |
| `chat_sessions.group_id` | 成员行指向所属群（群行自身为空）；索引 `idx_sessions_group` |
| `chat_sessions.agent_name` | **成员行的显示名（权威）**；由后端生成（首个实例用本名，重复实例取名池名，池尽回退 `本名 序号`）。非成员行留空。成员行的 `title` 留空（会话标题对成员无意义） |
| `chat_sessions.agent_avatar` | **成员行自身的头像 SVG 快照**（前端 DiceBear 按名生成、随机风格）。**仅同一智能体的第 2+ 个实例生成**（用于区分副本）；第 1 个/唯一实例留空，回退智能体头像。非成员行留空 |
| `chat_sessions.context_state` | 群行存 `group_mode`（`host`/`free`）、`host_member_id`、`parallelDefault`、`cruise`；成员行存 `seen_cursor` **与 `usage`**（该成员自己的上下文占用，花名册与详情面板的数据源） |
| `chat_history.role='system'` | 成员增删的系统事件（`agent_id=''`，居中细条渲染，计入注入游标但不计入未读） |
| `chat_sessions.awaiting_user_at` | **群的「在等我」标记**：最后一轮结束、发言权交回用户时置位，`UpdateLastRead` 清空。群未读因此是 **0/1**，不按成员发言条数累加 —— 讨论进行中不会每说一句就亮一次。通知同样只在整轮结束时推一次（不再逐条排队消息各推一次） |
| `chat_history.agent_id` | **发言人成员行 id**（非 agent id）；前端据此解析发言人头像/名字并判定主持人发言 |
| `group_pending_bcc` | 密送待投递队列，按目标名字键控，成功投递后删除。`sender_role`（`host`/`member`/`user`，空=升级前旧行）+ `sender_name` 供投递时署名。**每个目标上限 64 条**，超限按差额丢最旧（已超限的队列一次写入即收敛回上限） |

## API 端点

全部经 `middleware.Auth`，且为项目作用域：

- `POST /api/group/create` — 建群（`hostAgentId?` + `memberAgentIds[]`，同一事务创建群与全部成员；`hostAgentId` 缺省即自由模式，须过会话上限门）
- `GET /api/group/members?groupId=` — 列成员（含 `isHost`、`mode`、`parallelDefault`、`cruise`、`avatar`、`agentName`、`model`、`usage`）。`usage` 与该成员自己的上下文同形（同 `/api/ai/chat` 的 `usageState`），**`null` 表示从未上报**，不是 0%
- `GET/PATCH /api/ai/session/settings` — 按 session 读写设置（模型 / 思考深度 / 模式 / 传输 / 自动批准 / 巡航 + 上下文用量）。**成员行也能用**：成员行没有自己的 `chat_history`，历史端点描述不了它，而设置抽屉必须能在成员上打开。群回合进行中或该成员正在压缩时写入返回 409
- `POST /api/group/member-compact` — 压缩**一个成员**自己的上下文（`{groupId, memberId}`，`memberId` 是成员行 id）。不走 `/api/ai/chat`，不在群时间线产生输出；返回压缩后的 `usage`
- `POST /api/group/members` — 批量加成员（整批过成员数上限）
- `POST /api/group/member-avatars` — 批量写回成员头像（`{groupId, avatars:[{memberId, avatar}]}`；每个 SVG 过 `avatarSVGLooksSafe` 安全门）
- `DELETE /api/group/members` — 移除成员（拒绝移除主持人）
- `PATCH /api/group/settings` — 群设置（`parallelDefault`、`cruise`）
- 智能体讨论次数上限（`chat.group_max_speeches`）与用户昵称（`chat.user_nickname`）都是**全局配置**（`PATCH /api/config`），不是每群设置
- 群消息发送**复用 `/api/ai/chat`**——`AIChat` 检测到群会话即委派编排器 `RunGroupTurn`，前端不改，不新增 `/api/group/chat` 以避免双入口
