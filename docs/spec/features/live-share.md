# 会议与屏幕共享（实时）

Windows 桌面客户端、**Android App** 和**桌面浏览器**都可以把**屏幕画面 + 系统声音 + 麦克风**共享出去，生成一个链接；任何拿到链接的人在浏览器里打开就能看画面、听声音，**无需登录**。多个观众之间还能互相说话（经发布端混音）。

macOS / Linux 桌面客户端同样可以发布，只是**没有系统声音**（Electron 的 `audio: 'loopback'` 仅 Windows 可用），画面与麦克风不受影响。

这是「看着 AI 干活」的直播，不是投屏工具：链接的模型与文件/会话分享一致——**token 即凭证**。

## 流程图

### 建立连接

```mermaid
sequenceDiagram
    participant 发布端 as Windows 桌面
    participant 服务端
    participant 观众 as 观众浏览器

    发布端->>服务端: POST /api/live-share（鉴权，带项目 cookie）
    服务端-->>发布端: { token, path }
    发布端->>服务端: WS /api/live-share/publish/ws?token=...
    发布端->>服务端: {"type":"publish"}
    观众->>服务端: GET /api/share/{token}/meta → kind=live
    观众->>服务端: WS /api/share/{token}/signal（公开）
    服务端-->>观众: {"type":"joined","viewerId":"v1","iceServers":[]}
    服务端-->>发布端: {"type":"viewer-join","viewerId":"v1"}
    观众->>服务端: {"type":"offer","sdp":"..."}
    服务端-->>发布端: {"type":"offer","viewerId":"v1","sdp":"..."}
    发布端->>服务端: {"type":"answer","viewerId":"v1","sdp":"..."}
    服务端-->>观众: {"type":"answer","sdp":"..."}
    观众<<->>发布端: 媒体 P2P 直连（不经服务端）
```

**服务端只转发 SDP / ICE，从不解析、从不承载媒体。** 每个观众与发布端之间是独立的 `RTCPeerConnection`，观众发 offer、发布端答 answer。

`POST /api/live-share` 按项目**幂等**（双击、响应丢失后重试、另一台设备都走同一条路），但它携带的开关是**房间的初始状态**，不是命令：房间已有发布端（含已预留）或已有观众时，请求体里的 `title` / `video` / `camera` / `screen` / `allowTalk` / `allowMemberScreen` / `notes` 一律**忽略**——这些字段缺席即 `false`（`title` 缺席时是日期占位），照写就会在第二次 POST 时给正在进行的会议改名、收走所有观众的麦克风、掐断正在共享的屏幕，或者把正在录的听记标记成「已停止」（新进场的观众据此停止轮询，而转写还在增长）。会中要改这些开关走发布端信令帧（`set-talk-enabled` / `set-screen-enabled` / `set-picture` / `set-notes`）。发布端还没 attach 时（grace 窗口、重试）这些字段仍然生效，那是它们的唯一用途。

## 功能与设计要点

### 功能清单

- **纯 P2P WebRTC**（默认）：媒体点对点直传。观众上限 **8**，受发布端上行带宽约束（每个观众一条独立编码流）。人数更多时可在创建页勾选[中继服务](#中继模式大会)，把媒体交给独立部署的 LiveKit，房间不再设人数上限
- **分享链接**：复用现有 `/share/{token}` SPA，`kind: 'live'`。token 32 位 hex，与文件/会话分享同级。**链接按本机全部地址生成**（见下）。会中页、加入页与记录页与其他分享页共用顶栏的「自适应屏幕大小」开关（见[文件管理](file-management.md)）
- **会议结束后的可见性是一个开关，默认关**（`live_notes.share_enabled`，在会议记录的「资源」页签里切换）。token 是开会时**自动**分配的（观众靠它加入），这与「把纪要公开出去」是两件事，所以归档记录默认 404：会议一结束，链接就不再解析，直到主人在结果页打开开关。**开会期间不受开关影响**——房间地址用的是同一个 token，拒绝它就等于拒绝所有人参会。开关只管 `/api/share/{token}/meta`、`/notes`、`/notes/shot` 三条归档读取路径（发布端自己的管理接口不受影响）。切换走独立的 `PATCH /api/live-share/notes/sessions/share`，不与重命名共用接口：改名是纯标签操作，公开与否是另一件事，混在一起会让一次改名意外改变可见性
- **编码预算**：发布端为每个观众独立编码一路画面（WebRTC 不跨连接共享编码器），所以捕获上限压到 1920×1200 / 30fps——4K 屏按原生分辨率编 N 份，4 个观众就能把 CPU 打满。屏幕轨道标 `contentHint=text`、摄像头标 `motion`，让 Chromium 走屏幕内容路径；**只在平台报告有硬件编码器时**才优先 H.264/VP9（软件 H.264 编屏幕内容比 VP8 又慢又糊，猜错比不猜更糟）。`VideoLoadGovernor` 轮询 `qualityLimitationReason`：连续两次 CPU 受限降一档（2× / 4× 下采样），连续四次正常才回升；一个 governor 管所有 sender——CPU 是整机资源，每个 peer 各自判断会让观众端画质参差
- **系统声音**：Windows 上通过 `audio: 'loopback'` 采集。**macOS / Linux 不支持**——这是 Electron 的限制，非实现取舍；非 Windows 平台 UI 不提供该开关
- **画面是选择，不是开关**：创建页与会中「会议管理」用同一套画面格——把「不共享」和每个屏幕/窗口画成同一种格子（缩略图 + 屏幕/窗口标签），点谁共享谁；会中点击即生效（换源不重连，点「不共享」只停画面、不结束会议）。宿主还没给出列表时（macOS 未授权屏幕录制、Wayland portal 未询问）多一格「选择共享画面」，点了才去拉列表；纯浏览器没有列表，它的选择器就是源，所以那一格直接是「共享屏幕」，会中再点它即重新唤起选择器。摄像头 / 麦克风也是同一套卡片（第一张是关闭态）；房间级三个开关——AI 听记 / 允许成员发言 / 允许成员共享屏幕——合成同一组勾选行，别处不再单独出现；分组标题、提示行、勾选行由 `web/src/assets/meeting-form.css` 统一，两屏不得各写一份
- **麦克风**：与系统声音在 `AudioContext` 里混音后发送。麦克风被拒绝不影响共享（画面仍可发）。**输入设备是一份偏好清单**：机器上有多个输入时全部列出，点一个换一个——一场会议只发布**一个**麦克风，`deviceId` 以 `exact` 约束传给 `getUserMedia`（设备已拔掉时走既有的「无本地声道」降级，不中止会议）。设备**标签**在首次授权前是空的（浏览器指纹防护），此时按序号显示，不隐藏。**会中也能换**（`switchMicDevice`）：先开新设备再释放旧的，成功后同时改写三处持有麦克风的图——混音器（`LiveMixer.setMicStream`）、听记录音（`LiveNoteCapture.addChannel` 替换同名的 `mic` 声道）、以及电平表（分析节点跟着源节点重建），对端连接完全不动，所以观众听不到断点；麦克风关闭时清单隐藏，避免"静音状态下打开一个设备"
- **开麦失败要说清是哪一种**：成员按下麦克风按钮而浏览器打不开设备时，按钮不能只是弹回「关」——那看起来就像「没识别到麦克风」。按原因分别说明：权限被拒（引导去地址栏改允许）、设备未就绪或未启用（提示检查耳机麦克风与系统声音设置）、根本没有输入设备。用 HTTP 打开时「需要 HTTPS」直接显示成一行字，不做悬停提示（灰按钮在 Chrome 里不弹 tooltip）
- **耳机插拔后跟随当前默认设备**：刚插上耳机时设备常短暂报 `NotReadableError`，采集路径统一重试一次（400ms）再放弃；开过一次麦后插耳机，缓存轨道仍绑在旧设备上会一直用内置麦，故监听 `devicechange`——不在说话就立刻丢弃缓存，正在说话则等这句话说完再丢（不打断），下次开麦用当前默认设备；说话中拔耳机导致轨道 `ended` 时自动关麦并提示「麦克风已断开」，而不是留着死轨道继续发、按钮还显示「开」
- **多人语音**：观众打开自己的麦克风开关即可发言，**其他观众也能听到**（见下）
- **发言授权**：房间级开关（初始值来自设置 → 视频会议，出厂为开）；开启后观众自行开关麦克风；发布端可单人静音与「全部静音」
- **零新增依赖、零新增端口**：服务端只多一个内存房间表，端口仍然只有 TCP 20000

### 为什么多人语音不需要 SFU

发布端本来就和每个观众各有一条连接，也本来就收到所有人的音频。所以为每个观众建一个独立混音即可：

```
dest[A] = 系统声音 + 发布端麦克风 + 观众B的音轨 + 观众C的音轨 + …   ← 排除 A 自己
dest[B] = 系统声音 + 发布端麦克风 + 观众A的音轨 + 观众C的音轨 + …   ← 排除 B 自己
```

- **0 条额外连接、0 服务端媒体工作**
- 8 人只多约 256kbps 上行（视频本身就要 16Mbps，占 1.6%）
- 代价是多一跳：A 说话 → 发布端 → B，局域网下约多 100–200ms

视频 mesh 才需要 SFU（8 人 28 条额外连接、56Mbps 上行）；音频不需要。**中继模式（大会）不改变这个结论**：它解决的是「N 个人各拉一路画面」，音频仍然是发布端混音后一人一路。

**排除自己是一条代码级不变量**：把 `viewerTrack[X]` 连进 `dest[X]` 会让 X 听到自己，并经发布端外放再被麦克风拾取，产生无限回声。

### 观众上行不需要重新协商

观众加入时先占一条 `sendrecv` 音频 m-line（不挂 track），之后开麦/闭麦只用 `replaceTrack`：

```ts
const tx = pc.addTransceiver('audio', { direction: 'sendrecv' })
await tx.sender.replaceTrack(micTrack)   // 说
await tx.sender.replaceTrack(null)       // 停
```

实测（Electron 44 / Chromium）`signalingState` 全程保持 `stable`、SDP 不变。若改成"发言时重新 offer"，会引入 SDP 抖动与连接重建风险。

### 发言授权：一个房间开关 + 一个麦克风开关

文件分享的 token 是**只读**的，泄露顶多被看。**多人语音的 token 是写权限**——拿到链接的任何人都能往房间灌声音，且**所有观众都会听到**。所以授权模型只有两层：

| 层级 | 机制 |
|---|---|
| 房间级 | 发布端显式勾选「允许观众发言」，**初始值来自「设置 → 视频会议」的新会议默认值（出厂为开）**。关闭时服务端直接拒绝 `talk-start`（观众端回 `talk-disabled`） |
| 人级 | 房间开启后，观众自己点麦克风开关即可发言/静音；发布端可随时「静音」某个人（`talk-revoke`，对方可以再打开）或「全部静音」；也可以**硬静音**（`talk-mute`，之后该观众的 `talk-start` 一律被拒绝，直到发布端解除）或**移出会议**（`kick`，服务端先回 `kicked` 再断开 socket） |

**刻意没有「申请 → 批准」这一层。** 早期设计有逐人审批，后来移除了：房间开关本身就是安全边界（只有发布端能改，会中实时生效），在其之上再加一层逐人确认只是摩擦，没有对应的威胁模型。**开关的初始值可配**（设置 → 视频会议，出厂为开）——多数会议确实需要成员发言，而默认值不改变边界在哪，只改变第一下要不要点。

观众端只有一个麦克风开关（开 = 上行麦克风，关 = 静音），**不是**按住说话。开关式在这个场景更好：多人语音是「一起聊」而不是「轮流发言」，按住说话在长时间讨论里是纯粹的负担。

### 状态机

每个观众只有一个布尔：麦克风开/关。

```
none --talk-start--> talking        （要求房间开关已开）
talking --talk-end--> none
talking --talk-revoke--> none        （发布端静音这个人）
talking --mute-all--> none           （发布端全部静音）
talking --set-talk-enabled(false)--> none  （房间开关关闭，连带静音所有人）
talking --talk-mute(true)--> none    （发布端硬静音，此后 talk-start 被拒）
muted --talk-mute(false)--> 可发言    （解除硬静音，麦克风仍由观众自己开）
```

`talk-start` 在房间开关关闭时**拒绝并回 `talk-disabled`**，不静默忽略——静默会让「开关点了没反应」变成不可诊断的问题。`talk-end` 永远允许，这样发布端刚关掉开关时观众仍能正常上报自己已静音。

### 分享链接按「全部本机地址」生成

`window.location.origin` 只知道浏览器恰好用的**那一个**地址。一台机器同时有 Wi-Fi（`192.168.100.104`）、USB 网卡（`192.168.100.142`）和 Docker 网桥（`172.17.0.1`）时，同事可能不在同一网段，拿到的链接打不开。

所以三个分享入口（屏幕共享 / 文件分享 / 会话分享）都改为请求 `GET /api/server/addresses`，由服务端枚举地址：

- **默认只显示一条主链接**，其余折叠在「查看全部 N 个地址」后面——常见场景下满屏 IP 只是噪音
- **主链接优先选浏览器当前用的那个地址**：用户此刻能用它访问，说明它在这个网络里是通的，这是最好的证据。当前地址不在列表里时（localhost / 域名 / 反向代理），仍以浏览器 origin 为主
- **虚拟网卡不隐藏，只标注**：`172.17.0.1` 这类地址仍会列出，但标「虚拟网卡」。静默丢弃会让用户无法解释「为什么这个地址别人打不开」

**唯一被过滤的是 IPv6 隐私地址**。现代系统每个接口会额外分配若干 RFC 4941 临时地址，**每隔几小时轮换**。实测一台双栈笔记本 17 个地址里有 14 个是这种，发给同事时大概率已失效，还会把真正可用的 3 个埋掉。`net.IP` 拿不到 temporary 标志，所以按 **(接口, /64)** 折叠：稳定地址与它的临时兄弟共享 /64，折叠后每个前缀只剩一条。

### 发布端能听到观众

`LiveMixer` 把每个观众的远端音轨连到 `ctx.destination`（扬声器），所以发布端能听到观众说话。**只有远端音轨连扬声器**——发布端自己的系统声音和麦克风绝不监听，否则会听到自己的延迟回声。

### 观众端必须处理的三件事

1. **自动播放策略**：带音轨的 `<video>` 在无用户手势时会被拦截。处理是先 `muted` 播画面，顶部显示「点击开启声音」。**不要**直接报错。
2. **发布端断开**：收到 `publisher-gone`（`reason=ended`）时**切到该会议的记录视图**（纪要 / 转写 / 校对 / 聊天）。链接不会失效，只是不能再进会——token 指向的永久记录继续可读，直到记录被删除；只有「再加入一场新会议」才需要新链接。`reason=kicked` 不切记录，仍显示「已被移出」。
3. **ICE 失败要说清原因**：纯 P2P 下常见原因是双方不在同一网段、AP 禁了组播（mDNS 候选解析失败）、或开了客户端隔离。提示里要列出这三条，不能只说「连接失败」。

### 刷新发布端页面会结束会议

发布端 socket 就是会议的生命周期：页面卸载 → socket 关闭 → 服务端在宽限期（见下文「发布端断线」）内等它回来，没人回来才广播 `publisher-gone`、删房间、收尾会议记录（`internal/handler/live_share.go` 的 `endPublisherSocket`）。**刷新页面走的正是这条路，所以仍会被当成断线**——只不过现在有两道确认拦在前面，用户几乎不会真的撞上；真撞上时连带损失是：正在上传的录音段丢失、「停止后合并整场录音 / 生成纪要」不会发生。

因此会议进行中（`state === 'publishing'`）有两道守卫（都在 `web/src/composables/useLiveShare.ts`）：

- **F5 由应用自己拦**：冒泡阶段监听 keydown（终端转发 F5 给 TUI、文件管理器 F5 刷新都会先 `preventDefault`，`useF5Reload` 也读同一个标记，所以不能抢在捕获阶段）。命中时弹应用内确认框（`meeting.stage.leave*`），确认后**先正常结束会议再刷新**——`stop()` 会折好最后一段录音、启动纪要生成、给观众一个真正的「已结束」，而不是让 socket 半路断掉。确认框文案可自定义，故走 i18n。
- **其余路径走 `beforeunload`**：Ctrl+R、关闭标签页、关闭窗口、浏览器自带的刷新按钮。这条通道的文案由浏览器决定（不可自定义）。**桌面端必须自己接 `will-prevent-unload`**（`desktop/src/main/window.ts`，文案在 `labels.ts`）：Electron 的默认行为是**静默丢弃这次卸载、不弹任何框**，表现就是「F5 / 关闭按钮完全没反应」。Android WebView 没有 `onJsBeforeUnload` 实现，同样是静默拦截。

### 会议期间保持屏幕常亮

开会时系统锁屏会直接中断采集与共享（观众画面冻结、录音断档），而主持人常常正对着另一块屏幕讲。所以**会议中与观众页都会申请屏幕唤醒锁**，离开会议页、结束会议或页面被隐藏时释放；浏览器标签被切到后台时系统会自行释放，回到前台重新申请。

这条是纯客户端行为（`useWakeLock`），服务端不参与——「会议还在进行」这个事实在服务端有，但「这块屏幕该不该熄灭」只有客户端知道。

### 已知限制

| 限制 | 说明 |
|---|---|
| 仅同一局域网（P2P 模式） | **无 TURN 中继**。跨网段、公网、开客户端隔离的 AP 一律不可用。需要跨网段时改用[中继模式](#中继模式大会)，那是另一套传输 |
| mDNS 候选 | 观众端是浏览器、通常无媒体权限，Chromium 会把 host candidate 伪装成 `<uuid>.local`。AP 禁组播则解析失败 |
| 系统声音仅 Windows / Android 10+ / 部分浏览器 | Electron 的 `loopback` 只支持 Windows；安卓走 AudioPlaybackCapture，且只能录到允许被录制的声音；浏览器由选择器决定（Chrome 只在共享标签页或整个屏幕时给音频） |
| 8 人上限（P2P 模式） | 发布端上行 = N × 码率。中继模式没有这个上限，真实容量由中继节点的网卡与 CPU 决定 |
| 房间是内存态 | 进程重启即失效（语义正确：直播是瞬时的）。失效的只是「进会」通道，会议记录与 token 的读取不受影响 |

## 中继模式（大会）

小会用点对点，**默认就是点对点**。上百人的培训、跨研究所的全员会走中继：媒体交给一台独立部署的 LiveKit，主播只上传一份，每个观众从最近的中继节点拉流——发布端不再为每个人单独编码，房间也就没有人数上限。

```
主播 ──1 路──▶ LiveKit 中继 ──▶ 观众 1
                    ├─────────▶ 观众 2
                    └─────────▶ …（N 个观众，主播上行不变）
```

中继是**每场会议的开关**，不是全局切换：同一台服务器上，小会继续走点对点（少一跳、无外部依赖），大会才走中继。两条路径共用房间、信令、听记、分享页与记录，只有媒体的搬运方式不同。

### 功能清单

- **默认关闭，行为完全不变**：不开中继时，代码走的仍是「每个观众一条 PeerConnection」。开了才切到中继
- **配置属于这台服务器，不属于某场会**：一个地址 + API Key + API Secret，所有启用中继的会议共用。配置在**设置 → 视频会议**里编辑（`MeetingRelaySetting`），创建页只留「本次使用中继服务」一个开关——三个对每场会都一样的输入不该出现在「这一场会」的表单里；未配置时创建页的开关可以点，但开始按钮被挡住并指向设置
- **创建页有直达配置的入口**：中继服务那一行右侧的「配置」直接跳到设置里的中继卡片（`beginExternalJump('live')` + pending category），并把这半填的创建表单登记为返回目标——返回手势（Android 返回键 / 屏幕内滑）落回创建页而不是记录列表，表单里已填的名称不丢；回到表单时重新读一次中继状态，刚配好的端点立刻可选
- **先测通再保存**：「保存并测试连接」用草稿值真的连一次中继，通过才落库。反过来的顺序会存下一个用不了的端点，之后每场会都开不起来，而用户分不清是地址、Key 还是 Secret 错了
- **未配置时开始按钮被挡住**，并提示去「设置 → 视频会议」补齐，不静默退回一个 8 人的点对点房间。静默退回的后果是第 9 个人看到「房间已满」，而主播以为自己开的是大会
- **密钥默认打点、按需回显**：已存的 Key / Secret 显示成圆点，点眼睛才用 `?reveal=1` 取回明文（与模型服务商的密钥框同一套做法）；不点就不取，读设置页本身不会把明文凭据拉进页面。留空表示「不修改」，只改地址的保存不会把凭据抹掉；圆点本身永远不会被当成凭据提交
- **创建时快照配置**：改全局配置不影响进行中的会议——否则同一场会的人会连到两个不同的中继，互相看不见
- **人数不设上限**：房间不再有 `maxViewers`。真实容量是中继节点的网卡与 CPU（经验值：本节点人数 × 码率 < 网卡 × 0.6）
- **禁言同步到中继**：静音 / 解除 / 全体静音 / 移出会议都同时下发 LiveKit。只改本地状态的话，界面显示已禁言、实际还能说话
- **说话指示用中继的结果**：LiveKit 服务端本来就在算音频电平并广播 `ActiveSpeakersChanged`，中继模式下不再由主播轮询自己的电平表
- **`/livekit/*` 反向代理**：https 页面不能连 `ws://`（浏览器按混合内容拦掉），而中继按普通 `ws://` 部署即可、不需要证书。页面因此连同源的 `/livekit/rtc`，由服务端把信令转发到**配置里那台中继**（配置成回环名字时只拨 `127.0.0.1`），socket 就继承了页面的协议。代理只拨配置的那台，绝不按请求里的地址转发，避免变成「从服务器访问内网任意地址」的入口。跨过的只有握手和候选地址（每人几 KB），**画面和声音仍由浏览器直连 LiveKit**，中继该扛的流量一点没少

### 设计要点

- **媒体仍然不经过 ClawBench**：中继模式下服务端只签发 token、管房间、转控制帧，一个媒体包都不碰。这条边界让听记、权限、分享页、会议记录的业务代码在两种模式下几乎不用分叉
- **听记仍由主播采集**：只有主播握着全部音源。中继模式下主播必须订阅**所有**发布者，漏一个那段话就不进纪要，而且不会报错
- **主播也要把那几路音轨放出来才听得到**：LiveKit 只交付轨道，不会自己发声（点对点靠混音器每个观众一条 `ctx.destination` 监听边，中继模式没有这条路）。订阅到的远端音轨必须显式接进主播的 `AudioContext`，否则「成员能听到主播、主播听不到成员」——单向会议，且界面上一切正常
- **控制帧改走中继的 data channel**：聊天、标注、激光笔、举手、远程控制这些原来跑在 RTCDataChannel 上的帧，在中继模式下走 LiveKit 的同一条通道，前端只是换了个发送实现
- **多所级联是部署方案，不是本仓库的能力**：每所一台中继 + 一个桥接程序（把主节点的画面转发布到本所）写在[多所 300 人大会设计稿](../../plans/2026-11-03-multi-site-300-meeting-design.md)里，当前代码只实现单节点中继。单节点在千兆网卡、4 Mbps 下约可承载 150 人
- **不做「自动挑模式」**：人数无法预先知道，猜错比让用户选更糟（猜小了一开会就卡，猜大了白白多一跳）

## 控制通道（小会工具）

媒体之外还有一条 **RTCDataChannel**（发布端在每条连接上创建，观众 `ondatachannel` 接收）。它承载的不是画面，而是：

| 消息 | 用途 |
|---|---|
| `laser` | 激光笔位置（2.5s 无更新自动隐藏） |
| `ink` / `ink-undo` / `ink-clear` | 画面标注（自由笔迹） |
| `chat` | 文字聊天（两端各自保留本次会话的消息；后加入的观众看不到之前的聊天） |
| `presence` | 观众窗口是否可见（「离开」标记） |
| `talk` | 说话电平（发布端 → 观众，0..1，只在跨越阈值或明显变化时发） |
| `ctrl-req` / `ctrl-grant` / `ctrl-ev` | 远程控制的申请、授权与指针事件 |

信令通道（WebSocket）另有一条与能力相关的状态帧：发布端发 `set-control-enabled` 声明「我能不能被远程控制」（注入器 + 整屏），服务端转发给每个观众 `control-enabled`，并在 `joined` 里带上当前值。观众端据此灰显按钮，见下文「远程控制」。

**坐标系是 0–1 归一化到画面内容**，不是像素：观众 A 是 16:9 带黑边、观众 B 是全屏裁切，同一个像素坐标在两人屏幕上落在不同位置。换算只在 `liveControl.ts` 的 `contentRectOf` / `toNormalized` / `fromNormalized` 里做，绘制层与标注层都走它。

**线宽也必须是同一套比例**：笔画粗细按**画布宽度 / 800** 缩放，而不是「固定 CSS px × dpr」。桌面透明覆盖层曾经把线宽写死成 `width * dpr`（恒定 4 CSS px），而成员端与网页标注窗口按画布宽度缩放——1920 宽的屏上主持人看到 4px、成员看到 9.6px，同一条笔画两个粗细。现在三端共用同一个 `inkScale()`；高分屏仍由「画布宽度与线宽同为设备像素」自动抵消 dpr，不需要也不应该再看 dpr。

**发布端是这条通道的中转**：观众发来的帧被打上 `from` 后广播给其他观众，所以观众的激光笔别人也能看见，且不需要服务端参与。

**说话人高亮由发布端测量**：所有麦克风都在它这里汇合（观众只收到混音，自己量不出来）。`LiveMixer` 给每条远端音轨和发布端自己的麦克风各挂一个 `AnalyserNode`，每 200ms 算一次 RMS；只有**跨越「在说话」阈值**或数值变化超过 0.1 才发一帧 `talk`，安静的会场因此零流量。观众端收到后点亮 900ms 的「X 正在说话」，超时自动熄灭——发布端停止发送（静音、切后台）时不能留一个常亮的灯。**提示里的名字必须与成员列表一致**：`talk` 帧只带观众编号，而成员列表显示的是各自填的称谓，所以两处提示（浮动「正在说话」条与「正在共享屏幕」横幅）都按编号去名单里查名字，查不到（帧早于名单）才回退编号——同一个人在两处有两个叫法，用户只会以为是两个人。主持人说话同样显示称谓。

**远程控制**注入指针（移动/点击/滚轮）与键盘（命名键 + 任意文本）。

- **不需要安装任何东西**：注入由随应用分发的 `input-helper.exe` 完成（Go 写的，纯 `syscall` 调 `SendInput`，无 CGO、无原生 npm 模块）。Electron 在首次需要时 spawn 它，用 NDJSON 走 stdin/stdout，一次一个回执。
- **键盘分两种**：命名键（Enter/方向键/F1–F12/Delete…）按虚拟键码发；单个可打印字符走 `KEYEVENTF_UNICODE`，所以中文、emoji 都能输入，不依赖键盘布局。
- **只有 Windows 发布端能注入**：`internal/inputinject` 在其它平台是 stub（`Supported()` 恒 false），因为只有 Windows 会发起共享。发布端面板挂载时读一次 `remoteControlSupported()`，不支持时**不显示「允许」按钮**，改成一行说明——让人点了没反应比不给按钮更糟。
- **能力由发布端广播、观众端据此灰显**：观众能不能申请控制，取决于**发布端**（有没有注入器 + 当前画面是不是整屏），观众端自己算不出来。所以发布端用 `set-control-enabled` 把它告诉房间，服务端在 `joined` 里带给后加入的观众、变更时推 `control-enabled`；观众端只按这个标志决定「请求控制」是可用还是灰显（灰显时 title 说明原因）。观众自己的平台不参与判定：浏览器观众照样能驱动 Windows 发布端，浏览器**当发布端**时才因没有注入器而广播不可用。
- **`input-helper.exe` 是打包产物**，不在仓库里：`release.yml` 的每个桌面 job 会跑 `desktop/scripts/build-input-helper.mjs`，`build.sh` 也跑一次（否则本地 `npx electron-builder --dir` 出来的包里没有它，远程控制会静默失效）。
- **Escape 是本地逃生键**：按 Esc 只结束自己的控制，不会转发给对端。
- 限制：仅 Windows 可注入；对端窗口若以管理员权限运行（UIPI），`SendInput` 会被系统拒绝，界面会收到 `ok:false` 而不是假装成功。

## 成员端：浏览器 vs 客户端

同一个分享页在两种宿主里跑，能力不同：

| 能力 | 浏览器 | 桌面客户端 |
|---|---|---|
| 观看画面 / 聊天 / 标注 / 缩放 | ✓ | ✓ |
| 共享自己的屏幕 | 仅 HTTPS | ✓（原生选择器，HTTP 也行） |
| 使用麦克风 | 仅 HTTPS | ✓ |
| 被主持人远程控制 | ✗（浏览器没有输入注入 API） | ✓ |
| 系统声音 | ✗ | ✗（成员端没有第二条音频 m-line） |

客户端入口在共享弹窗里：「加入别人的共享」→ 粘贴链接 → 在独立窗口打开（复用同一 preload，所以分享页能识别出自己跑在客户端里）。

**为什么客户端能绕开 HTTPS**：桌面壳启动时把**已保存的全部服务器 origin**（`serverUrl` + 服务器列表）加进 Chromium 的 `unsafely-treat-insecure-origin-as-secure`（见 `desktop/src/main/secureContext.ts`），所以 `navigator.mediaDevices` 在这些 origin 上存在。Chromium 只在启动时读一次该开关，且不支持通配符，因此连接一个尚未保存的新服务器时桌面壳会**自动重启一次**（URL 先落盘，重启后即被覆盖）——不这样做的话，切完服务器会议就建不了，而界面上没有任何补救入口。

**客户端模式下共享屏幕要先选源**：Electron 的 `setDisplayMediaRequestHandler` 拒绝未声明的源，所以分享页会先调 `listCaptureSources()` 弹一个选择器，再 `setPendingCaptureSource()` + `getDisplayMedia()`。**只有用户点「选择共享画面」时才枚举**：Linux/Wayland 下"列一遍屏幕"这个请求本身就是桌面 portal 的「要共享什么」弹框，而会议面板与创建表单在挂载时就枚举的话，启动应用、甚至只是点开会议页签看记录，都会先弹一次系统框。因此在点之前只用空列表构建画面格，并在没问过系统之前**不断言**「没有可共享的屏幕或窗口」（`sourcesProbed`）。代价是创建会议不再默认选中第一个屏幕，要共享得先点那一格。**同一份清单要复用**：开始共享时若重新枚举，Wayland 下用户会被要求选两遍，且第二次的选择会覆盖第一次的——桌面壳把 picker 画过的那份清单留 5 分钟，开始共享时按声明的 id 直接取源，超时或找不到才回退到重新枚举。**应答必须只答一次**：`getDisplayMedia` 的一次性 callback 若在抛错后又被 promise 的 catch 答第二次，第二次必然抛「One-time callback was called more than once」，日志里只剩这句、**第一次的真错误被吞掉**，渲染端只拿到一个被拒绝的请求，界面上什么都不显示——所以要有 `answered` 守卫，并把第一次的错误原文记进日志。渲染端也要"失败要说话"（原先只写一行日志就返回 false）

浏览器端在主持人开启「允许成员共享屏幕」时会显示一条提示，说明共享屏幕/系统声音/被控制需要客户端——只在真的用得上时出现，不是每场都弹。

## 成员反向共享屏幕

发布端可以打开「允许成员共享屏幕」，成员（**电脑**浏览器）就能把自己的屏幕共享给**所有人**。

### 链路

```
成员浏览器                发布端（Electron）              其他观众
getDisplayMedia
  └ 屏幕轨 ──P2P──▶ 收到 ──replaceTrack──▶ 转发 ──P2P──▶ 看到
```

- **一次只允许一个人**：第二个人点会收到 `screen-denied / busy`。原因是转发成本：每个共享者都要在发布端复制成 N 路，N 个共享者就是 N×N。
- **共享者收不到自己的画面**（发布端转发时跳过它）——否则自己的屏幕会延迟一拍回放，变成回声。
- **四条 m-line 在加入时就协商好**，开始/停止只 `replaceTrack`，不重新协商：

  | m-line | 方向 | 内容 |
  |---|---|---|
  | 1 | sendrecv | 成员麦克风 ↑ / 混音 ↓ |
  | 2 | sendrecv | 发布端**主画面** ↓ / 成员共享画面 ↑ |
  | 3 | sendonly / recvonly | 发布端**转发**别人的共享画面 ↓ |
  | 4 | sendonly / recvonly | 发布端**摄像头** ↓（画中画小窗） |

  这个顺序是前后端的契约（`useLiveShare.ts` 与 `liveViewer.ts` 必须一致）。中途加 m-line 会强制重新协商，而连接上正跑着会议。

  **主画面 = 屏幕轨 ?? 摄像头轨**：只有摄像头时摄像头走第 2 条，第 4 条不挂轨（否则观众会把同一张脸渲染两遍）；屏幕 + 摄像头同时存在时第 2 条走屏幕、第 4 条走摄像头。摄像头必须用**独立的 `MediaStream`**（`setStreams`），和主画面共用一个流会让观众把摄像头挂到主 `<video>` 上、屏幕消失。

  发布端接受**三或四条** m-line：三条是旧缓存页面，只是没有小窗，主画面照常——拒绝会让整场共享对那个观众失效。

  摄像头开关只切 `track.enabled`（不重协商）；画面本身可以随时开关——开始/停止共享屏幕、开/关摄像头都只是对已协商的 m-line 做 `replaceTrack`，**从不重新协商**。三种状态（有没有画面 / 摄像头开着吗 / 画面是屏幕吗）打包成一帧 `set-picture` → `picture-state` 发给观众：分开发会让观众短暂渲染出一个从未存在过的组合。

### 权限

- 房间级开关「允许成员共享屏幕」，**初始值同样来自「设置 → 视频会议」的新会议默认值（出厂为开）**（和发言一致：token 本身已是写权限，拿到链接就能开麦；共享屏幕交出去的是整块桌面，比声音更多）。
- 发布端可随时关开关（连带停掉正在共享的人），也可只停某一个人。
- 被拒绝时服务端回 `screen-denied`，成员端**立即释放本地采集**——否则浏览器的「正在共享」指示会一直亮着，实际什么也没发出去。

### HTTPS 是硬门槛

`getDisplayMedia` 只在安全上下文存在：`http://192.168.x.x:20000` 这种页面里 `navigator.mediaDevices` 直接是 undefined。所以：

- 成员端**必须通过 HTTPS 打开分享页**。自签名证书有两条路：设置 → 安全 →「HTTPS 证书」里点「生成自签名证书」（覆盖本机所有 IPv4 + localhost，一键重启），或命令行 `./clawbench --gen-cert`。浏览器点一次「继续访问」之后即生效。
- 证书把**IP 写进 SAN**（浏览器不认 CN）；换网络后 IP 变了要重新生成一次。设置面板会显示当前覆盖的地址。
- 同一限制也作用于**观众麦克风**——HTTP 下「允许观众发言」同样用不了。
- 手机**浏览器**（Chrome Android / Safari iOS）不支持共享屏幕，只能看；安卓**App** 内可以发起共享（见下一节）。
- 开关打开但当前不是安全上下文时，按钮**仍然显示但置灰**并提示需要 HTTPS：直接隐藏会让人以为功能不存在。
- **建不了会时给一键修复**：浏览器在非安全上下文打开「创建会议」时，表单位置显示 HTTPS 提示（`components/live/HttpsNotice.vue` 的 `block` 形态），按钮直接生成自签名证书 → 重启服务 → 跳到 https；磁盘上已有 CA 签发的证书时要求二次确认，不静默覆盖。
- **桌面壳在 http 下打开会议列表**时，顶部挂同一条提示的 `banner` 形态：本机采集可用（壳把 origin 提升成安全上下文），但发给别人的链接在浏览器里要 HTTPS 才能开麦/共享屏幕。按钮同样一键生成证书并重启，随后由 `native:switch-server-url` 把外壳切到 https——**改写**保存的服务器条目而不是新增一条，显示名与凭据随条目一起迁移，否则服务器列表里会永久留一条连不上的 http 记录。两个形态是同一个组件，文案与按钮逻辑不重复实现。
  - **这个横幅不能靠 `isSecureContext` 判断**：桌面壳为了让采集 API 可用，启动时会给 http origin 加 `unsafely-treat-insecure-origin-as-secure`（`desktop/src/main/secureContext.ts`），而这个开关的**全部作用**就是让该 origin 的 `isSecureContext` 变成 true。于是「能采集」与「要提示」被同一个标志绑成互斥，横幅永不显示。判「页面本身是不是 http」只能读 `location.protocol`（`isHttpOrigin()`）。这是本仓一类反复出现的假绿：**单测在 jsdom 里手动把 `isSecureContext` 设成 false**，造出了宿主永远不会给的组合，所以一直绿。

## 浏览器发起共享

桌面浏览器（Chrome / Edge / Firefox / Safari 15+）也能当发布端：Dock 的「视频会议」页签在安全上下文里出现，采集走标准 `getDisplayMedia`。房间、信令、P2P、混音、听记、观众端与客户端完全一致，服务端一行没改。

### 与客户端的三点差异

| 能力 | 桌面客户端 | 浏览器 |
|---|---|---|
| 选择共享源 | 先列出屏幕/窗口（带缩略图），再 `setPendingCaptureSource` 声明 | 无列表：`getDisplayMedia` 自带系统选择器 |
| 中途切换共享源 | 源网格里选一个 | 再调一次 `getDisplayMedia`（等于再弹一次选择器） |
| 系统声音 | 采集屏幕时一律请求 `audio: true` | 同左（Chrome 只在标签页/整个屏幕时提供；没有就是纯视频流）。**没有开关**：系统声音跟着画面走，用户不需要选 |
| 窗口最小化 | `setPublishingActive` 保活，编码不降频 | 无等价物，标签页被隐藏时可能掉帧 |
| 被观众远程控制 | Windows 可注入 | ✗（浏览器没有输入注入能力，按钮显示为不支持） |

### 两个实现分支

- **没有源列表就没有「选源」这一步**：`start()` 只在宿主提供 `setPendingCaptureSource` 时才声明源并先校验；否则直接 `getDisplayMedia`。浏览器每次调用都会弹自己的选择器，所以「切换源」在浏览器端就是再调一次，不渲染源网格（`openSwitch()` 按 `hasNativeCapture` 分叉）。
- **`captureKind` 由 `getSettings().displaySurface` 推导**：`monitor` = 整个屏幕，`window` / `browser` = 窗口或标签页。它只影响远程控制与标注覆盖层：窗口/标签页共享时指针映射到桌面会错位，所以按「非桌面」处理。
- **先采集、再建房间**：`getDisplayMedia` 要求瞬时用户激活，而建房间 + 查地址是两次网络往返，慢网下会把手势窗口耗掉，浏览器随后拒绝一个用户明明发起的请求（Firefox / Safari 最严格）。采集只依赖本地能力（原生声明是 IPC），所以放在最前不损失什么；代价是建房间失败时要显式 `stop()` 释放采集，否则浏览器的「正在共享」指示会一直亮着。

### 门槛

- **必须是安全上下文**：`http://192.168.x.x:20000` 下 `navigator.mediaDevices` 是 undefined，页签直接不出现（与之前一致）。要发起就开 HTTPS（见「HTTPS 是硬门槛」的证书说明）或用 localhost。
- **手机浏览器不支持**：Chrome for Android / Safari iOS 都没有 `getDisplayMedia`，手机端发起仍然只能靠安卓 App。
- **观众开麦同样要安全上下文**：HTTP 打开的分享页能看画面，但发言要 `getUserMedia`。麦克风开关与「共享屏幕」走同一套判定（`canTalk` / `canShareScreen`），不可用时置灰并提示需要 HTTPS——否则按钮点下去只会静默弹回。
- 能力判定集中在 `web/src/utils/screenCaptureSupport.ts`：`getDisplayMedia` 是否存在决定「能不能采」，`isSecureContext` 只用来选提示文案（「需要 HTTPS」而不是「请更新客户端」）；而**「这一页是不是 http」用 `isHttpOrigin()` 读 `location.protocol`**，理由见上文桌面横幅那条——桌面壳的 `isSecureContext` 恒为 true。

## 安卓端发起共享

Android App 也能当发布端：Dock 的「视频会议」页签在安卓上可用，分享出去的是**手机屏幕 + 系统声音 + 麦克风**。房间、信令、P2P、混音、听记、观众端全部复用桌面那套，服务端一行没改。

### 为什么不能直接用 getDisplayMedia

Android WebView 里**没有** `getDisplayMedia`（Chrome for Android 也一直没有）。所以采集必须是原生的 `MediaProjection`，再想办法把画面送回 WebView 变成一条 `MediaStreamTrack`：

```
MediaProjection ─▶ VirtualDisplay ─▶ ImageReader ─▶ 缩放 + JPEG
                                                        │
                                          （原生 tick 通知页面）
                                                        ▼
                            JS 桥取帧 ─▶ 解码 ─▶ VideoTrackGenerator / canvas
                                                        │
                                                        ▼
                                            现有的 RTCPeerConnection
```

- **帧走「原生推、页面拉」**：原生每产出一帧就 `evaluateJavascript` 触发一次 tick，页面在 tick 里调 `takeScreenFrame()` 取走。反过来让页面 `setInterval` 轮询是不行的——分享自己屏幕时 App 必然在后台，Chromium 会把隐藏页面的定时器压到约 1 Hz，轮询当场瘫掉；而脚本求值不受这个限制。
- **只有最新一帧有意义**：原生只保留一个帧槽，页面没取走就被下一帧覆盖。解码期间到来的 tick 直接丢弃，天然形成背压，不会越积越多。
- **优先 `VideoTrackGenerator`，回退 canvas**：canvas 的画面由合成器产出，而 App 在后台时合成器是暂停的；`VideoTrackGenerator` 的帧直接进 WebRTC 管线，不经过合成器，后台也能持续出帧。老 WebView 没有这个 API 时退回 `canvas.captureStream(0)` + `requestFrame()`，代价是后台可能卡顿。

### 系统声音

`AudioPlaybackCapture`（Android 10 / API 29 起）把设备播放的声音录成 PCM，按 100 ms 一块推给页面；页面用一个环形缓冲 + `ScriptProcessor` 把它转成音轨，之后就走桌面端完全相同的 `LiveMixer` 混音链路。

- **只能录到「允许被录制」的声音**：媒体、游戏可以；通话（`USAGE_VOICE_COMMUNICATION`）平台层面就抓不到，DRM 内容同理。UI 上明确写了这一点，避免用户以为录不上是 bug。
- **抖动缓冲**：先攒 0.2 s 再开始播，超过 0.6 s 就丢掉多余的（回到 0.2 s）。不这么做的话，桥接侧的抖动会一路累积成越来越长的延迟。
- 低于 Android 10 时 `getAudioCaptureSupport()` 返回 `systemAudio:false`，开关置灰并说明原因，而不是点了没反应。

### 前台服务与系统确认

- 采集跑在 `ScreenShareService`（`foregroundServiceType="mediaProjection"`）里。这不是选择而是要求：**必须先有该类型的前台服务，才能调 `getMediaProjection()`**，且投影回调要在 `createVirtualDisplay()` 之前注册。App 在共享期间始终处于后台（用户在看别的应用），Activity 级的采集会被直接回收。
- Android 14+ **每次开始共享都要用户点一次系统确认**，无法缓存或复用。确认框由系统绘制，应用无法跳过。
- 共享期间常驻一条通知（`正在共享屏幕`）——这既是平台的硬性要求，也是用户唯一能看到的「还在共享」提示。
- `MainActivity.pauseWebView()` 只调 `onPause()`、**刻意不调 `pauseTimers()`**，所以切到后台后 JS 仍在跑；再叠加「原生推 tick」，共享不会因为切应用而断流。
- 旋转屏幕会重建 VirtualDisplay：不重建的话虚拟显示还停在旧尺寸，画面会被拉伸。

### 安卓端的差异

| 能力 | 桌面端 | 安卓 App |
|---|---|---|
| 选择共享源 | 屏幕 / 窗口列表 | 无（系统确认框决定，恒为整屏） |
| 中途切换共享源 | ✓ | ✗（只有一个源，按钮不显示） |
| 系统声音 | Windows | Android 10+，且只限允许录制的声音 |
| 被观众远程控制 | Windows 可注入 | ✗（需要无障碍服务，不做） |
| AI 听记 | ✓ | ✓（与会议页签同一条链路） |
| 分辨率 / 帧率 | 原始分辨率 | 最长边 1280、10 fps（桥接 + 二次编码的成本上限） |

## 界面位置

桌面共享不再是顶栏的一个弹窗，而是**左栏 Dock 的一个页签「视频会议」**（面板内标题是「会议」，在「端口映射」前面）。一个页签，五个视图：

| 视图 | 内容 |
|---|---|
| 会议记录（默认） | 本项目的会议列表（数据库记录，永久）；footer 按「是否有进行中的会议」分三态（见下） |
| 创建会议 | 会议名称（选填）+ 称谓（必填）→ 画面（屏幕格 + 摄像头格）→ 麦克风格 → 其他（听记 / 关键画面 / 允许成员发言 / 允许成员共享屏幕）→ 中继服务（默认关；只有一个开关，地址与密钥在 设置 → 视频会议） |
| 加入会议 | 称谓（必填）+ 链接；桌面端在独立窗口打开 |
| 会议中 | 会议管理 / 参会者 / 转写 / 聊天四个页签；底部动作条：结束会议（左）+ 留存画面（关键画面开着且有画面时）/ 标注画面（右，仅屏幕画面） |
| 记录详情 | **资源** / 纪要 / 转写 / 校对 / 聊天 五个页签（**默认落在资源**）+ 打开文件 / 复制 / 删除 |

- **结束会议直接落到记录详情**，没有单独的「会后纪要」界面：生成中、生成失败、无产物都在详情里表达。
- **刚结束的记录要能自己收敛**：壳子在收到 `publishing → idle` 的那一刻就打开记录页，而这条状态变化发生在结束请求被应答**之前**，所以第一次读到的 `endedAt` 可能还是 0——那条记录和「真的还在开会」完全一样，而「进行中」的记录不轮询，页面就会一直显示进行中、重命名按钮永不出现（切走再回来才好）。因此记录详情对「打开后 60 秒内仍显示进行中」的记录也轮询一次，等服务器写入 `endedAt` 后自动收敛。窗口有界是刻意的：别人的长会（另一台设备主持）不该被这个页面一直轮询。
- **返回**：创建 / 加入 / 记录详情 / 会议中四个子页都支持屏幕左右边缘内划返回（Android 物理返回键同一条链路），一律回到会议记录列表。会议中的返回**不结束会议**，列表里那条「进行中」的记录点开会回到会议中。
  - 手势之外，**每个子页都有自己的返回控件**：记录详情在顶栏左侧，会议中同样在顶栏最左（`data-action="stage-back"`）。桌面端没有硬件返回，只有手势等于没有出口。
  - 会中回到列表后，**底部动作条只剩「返回会议」**（主按钮，`data-action="meeting-resume"`）：开会期间不提供创建 / 加入——那会把进行中的会议晾在一边；这一枚按钮同时充当「会议仍在进行」的提示。
  - **footer 与列表共用同一份「进行中」事实**（`isLiveRecord`，`useMeetingHistory.ts`），三态与行内的「进行中」徽标永远一致：本机在发布 → 只留「返回会议」；行显示「进行中」但本机不是发布端（另一台设备主持，同项目只有一间房）→ 主按钮「加入进行中的会议」（`data-action="meeting-join-live"`，直接以记录 token 打开成员端），**不提供创建**——创建会复用同一间在用房间、再撞发布端 409；无进行中会议 → 「加入会议 / 创建会议」两个入口。
  - 重新进入页签时**保留用户离开时的视图**：只有创建 / 加入这种一次性表单会退回（进行中则回会议中，否则回列表）。会中去看别的会议纪要、切走再切回，不该被拽回会议中。
- 会议进行中页签右上角挂**主题色圆点**（`.dock-badge--live`，无数字）。不再用红色区分「录音中」——红色只留给错误。
- **人数显示在两处、口径一致**：主持人「参会者」页签的标题与名单顶部、观众「成员」页签的标题与名单顶部都显示当前人数，口径是**主持人 + 全部观众**。人数不靠客户端自己数名单——同一场会在两个设备上看到的数字必须一样。
- **参会者页签**（会议管理之后）：主持人固定第一行，观众一行一人（头像由称谓生成，与转写/聊天同一套；重名加 `#2`；徽标显示说话中 / 已静音 / 共享屏幕 / 离开）。行内动作：静音（硬静音，服务端拒绝其再开麦）/ 解除、移出会议（先回 `kicked` 再断 socket）、停止共享屏幕、允许 / 拒绝 / 收回远程控制。**有远程控制申请待批时，页签上挂主题色数字角标**（`.live-count`），申请被处理或对方撤回即消失。
- 页签**恒显示**：记录永远可读；宿主不能采集屏幕时，创建页里说明缺什么。
- **观众端（分享页）先过称谓门**：填了称谓才建立信令连接（不占观众名额），称谓记在 `localStorage`，发布端观众列表与聊天署名都用它。
- **观众端侧边栏三个页签**：聊天 / 听记 / 成员。成员列表由服务端 `roster` **全量快照**驱动（`joined` 里也带一份，避免加入后先空一拍），主持人固定第一行、其余按加入顺序；显示头像（称谓生成，与转写/聊天同一套）、说话中 / 已静音 / 共享屏幕，并标出「你」。观众**没有任何管理动作**——静音、移出、停屏只有主持人有。
- **会议没有类型**。「语音会议 / 视频会议」这个概念不存在：一场会议从头到尾是同一种东西，画面只是它此刻的状态。
  - 创建页是**一组独立勾选**：共享屏幕（+ 源）、摄像头、麦克风、AI 听记。全都不勾也允许开始——那就是一场只有链接、观众和聊天的会议。
  - **会议中随时可切**：基础页有「共享屏幕」和「摄像头」两个开关，走 `startScreen` / `stopScreen` / `setCameraEnabled`，只对已协商的 m-line 做 `replaceTrack`，观众无需重连。
  - 观众端据 `picture-state` 的 `video` 渲染/移除「暂未共享画面」占位；`video`（有没有画面）、`camera`（摄像头开着吗）、`hostScreen`（画面是屏幕吗）是三个正交标志，一帧全带。
  - **关掉屏幕时摄像头自动转主画面**；两者都没有时回到占位。摄像头在会议开始时没采、中途打开也能用（那时才 `getUserMedia`）。
- **`hostScreen` 决定桌面类能力**：标注、切源、远程控制只在「画面是屏幕」时可用；摄像头画面没有桌面坐标可映射。这些入口跟着当前画面出现/消失，而不是跟着创建时的选择。
- **系统声音没有开关**：它只能随屏幕采集一起来（`getDisplayMedia({audio:true})`），所以一律请求；源不带音频就没有，用户不需要知道这件事。
- 顶栏没有听记入口：Dock 页签是唯一入口（`headerClusterSpacing.test.ts` 钉住顶栏只有「主题 → 服务器」）。
- **五个子页的底部动作条与定时任务一致**：药丸按钮 `.fbtn`（`--primary` / `--danger`），条本身 `padding: var(--space-3) var(--space-4)` + `background: var(--bg-primary)` + 顶部发丝线，不再各写一份 `.meeting-btn`；窄面板放不下时左右滚动（`flex-wrap: nowrap` + `overflow-x: auto`，`justify-content: safe flex-end`）。规范与理由见 `docs/spec/client/design-guide.md` §按钮，守卫 `components/live/__tests__/meetingFooterButtons.test.ts`。正文里的行内小动作（产物行的「复制路径」）仍用小号局部类。
- **会议中的页脚是常驻的**：结束会议与标注画面不再分居顶栏与「会议管理」表单——顶栏只留返回、状态（标题 + 共享中），标注画面跟着当前画面出现（摄像头画面没有桌面坐标可标注）。
- **标注画面按钮是画布的唯一把手，点它必须「看得见」**：画布活在面板之外（桌面透明覆盖层，或它自己的窗口），所以每次点击都要以「画布可见」收尾，不能因为「已经开着」就静默返回。
  - 桌面覆盖层的工具栏在**会进画面**的平台（Linux）上会淡出——它出现在观众看到的那块屏上；淡出后由「指针移到屏幕底部 120px」「窗口获得焦点」「再点一次标注画面（`annotate:wake` IPC）」唤回。**不会进画面**的平台（Windows/macOS 的 `setContentProtection`）根本不淡出（`?hideBar=0`）：观众看不到它，藏起来只会让主持人找不到工具。
  - 窗口模式（Document PiP / 桌面壳弹窗）里 `useScreenWindow` 在「已打开」早退之前要验活（`closed` + 目标 body 仍 `isConnected`）：窗口被用户关掉、或导航走导致目标文档作废时，早退会让按钮永久失效，所以这种情况必须重建窗口。
  - **成员画面与标注面画各用各的窗口名**（`SCREEN_WINDOW_NAME` / `ANNOTATE_WINDOW_NAME`）：`window.open` 对同名窗口返回的是同一个，共用名字会让两个表面叠进同一份文档、关掉任一个另一个也跟着消失。
  - **工具栏必须压在画布之上，且不能只靠调自己的 z-index**：窗口模式的画笔层自带 `z-index: 4`，而它的父级没有层级——这个 4 就直接与工具栏在同一个层叠上下文里比较，画布赢了。画面铺满窗口时（窗口共享常见的非 16:9 比例）工具栏整个落在画布范围内，**看得见却点不到**，每次点工具都变成画了一笔。修法是给画笔层的父级建立自己的层叠上下文（`z-index: 1`），把画布的层级关在里面，工具栏放在其上的 `z-index: 2`。整屏共享走桌面原生覆盖层，所以只有窗口共享暴露这个问题。

### 会议记录

- 一条记录 = `live_notes` 表的一行，**身份是 token**。发布端连上信令时创建、断开时收尾（**断开后有宽限期，见下**），与「有没有录到东西」无关。
- **永久保留**：转写分段、聊天、磁盘目录都不按天清理；删除记录（或删除项目）是唯一的删除路径。
- **崩溃遗留的会议在启动时收尾**：发布端 socket 的 `defer` 在进程崩溃时不会执行，`ended_at` 会永远停在 0，列表就一直显示「进行中」。房间只存在内存里，重启后必然没有活会议，所以服务启动时把所有仍 open 的行一次性关闭（结束时间取该行最后一次写入，并夹在 `[started_at, now]` 之间——服务器停一夜不会把 20 分钟的会算成 11 小时）；12 小时扫描只作为「进程还活着但写入方消失」的兜底
- 产物目录（`.clawbench/notes/<场次>/`）是**可选**的：第一次要写录音、聊天归档或纪要时才创建。项目改名不影响（记录里存的是目录**名**）。
- 记录可以拖进聊天作为引用（与 git 提交 / issue 一致）；详情顶部的引用按钮走**与 issue/PR 详情相同的引用条**（composer 模式：先预览会议 chip，用户填批注后提交才落卡片），正文支持选中文字引用。
- **会议中的转写与聊天也能引用到对话**：会中看到某段转写或某条聊天，直接引到聊天区交给 AI——引用带会议 token 与**产物目录**（`dir: .clawbench/notes/<场次>`，见[引用与附件体系](quotes-and-attachments.md)），AI 因此可以自己去读这场会的纪要、录音与关键画面，而不是只看到内联的那一段文字。
- **引用要带上产物目录**：只内联转写正文的话，AI 看不到这场会还留下了什么（纪要、录音、关键画面），也就没法自己去读。目录用**项目相对路径**——智能体的工作目录就是项目根，绝对路径对它没有意义。记录引用取宿主端相对化后的 `dirPath`，只有目录名时回落到固定的 notes 根；会中的引用取服务端已上报的 `artifacts.dir`，还没写文件时不带（给一个不存在的路径比不给更糟）。
- **资源页签排第一、并且是默认页签**：读者打开一条记录，第一件想要的东西是它留下了什么（目录、纪要文件、录音）以及**会议链接**。资源页签顶部固定展示链接（全部本机地址 + 复制），下面才是产物列表。
- **会议链接长期可读**：链接只在房间存活期间能用来「进会」，但**读取**在会议结束后仍然有效——token 从此指向永久记录，直到该记录被删除。资源页签里那一行提示就是这个承诺的界面表达。

### 成员端的会议记录

会议结束后，**成员（观众）界面也切换到会议详情**，而不是停在「共享已结束」的卡片上：

- 正在观看时发布端结束 → 信令收到 `publisher-gone`（`reason=ended`）→ 页面换成记录视图。
- 事后打开同一个链接 → `/api/share/{token}/meta` 返回 `kind=live` + `ended=true`（房间已销毁，但记录在库）→ **直接进记录视图，不再要求填称谓**（没有房间可加入，读记录也不需要身份）。
- 记录视图是 纪要 / 转写 / 校对 / 聊天 四个页签，数据来自公开的 `{token}/notes?full=1`（一次请求拿到转写分段、校对稿正文、纪要正文与归档聊天）。
- **被主持人移出**（`reason=kicked`）仍然走原来的提示，不切记录：被移出不是「会议结束」，把记录摊开回答不了「我为什么被移出」。
- 成员看不到主持人磁盘上的路径、不能删除记录、不能引用到聊天——记录视图只读。

## 会议通知

会议里的五件事会写进通知中心并推送：**远程控制请求**（`control_request`）、**成员加入**（`viewer_joined`）、**成员开始共享屏幕**（`screen_share`）、**纪要生成完成 / 失败**（`minutes_ready` / `minutes_failed`）。通知中心那一行的 `kind` 是 `meeting`，身份是会议 token（`notifications.meeting_token`），点击打开该会议记录。

**两半，两个受众**：`EmitMeetingEvent` 一次做两件事——写 `notifications` 行（无条件、不经过任何推送开关，与其它三类一致），以及广播 `live_event`（`ws.MeetingEventData`，`title`/`body` 由服务端按配置语言渲染好，与 `usage_meter_update` 同一套做法）。前者是「发生过什么」的持久副本，后者是「现在提醒你」的实时信号。

**为什么远程控制请求要发两次**：`ctrl-req` 走 WebRTC 控制通道（P2P），服务端**完全看不到**——那是发布端 UI 要立刻响应的路径，不能等一次往返。所以观众端在 `ctrl-req` 发出成功后，再向自己的信令 socket 补一帧 `control-request`（`ViewerControl`，服务端只转成通知，不改任何房间状态）。没有这一帧，主持人只有在会议页里才看得到角标。

**谁来弹**：服务端广播给项目的所有客户端（含观众），真正的门槛在客户端（`utils/meetingVisibility.ts`）——**只有主持人**（本机正在发布这个 token），且**会议页不在屏幕上**（页签未激活，或文档不可见）。两种情况各用一条通道：

- 应用在前台、只是不在会议页 → **应用内 toast**（带点击跳转）。这是唯一能覆盖「窗口有焦点但在别的页签」的通道。
- 应用在后台 / 窗口最小化 → **系统通知**。它原有的抑制规则（页面焦点、桌面窗口在屏幕上、安卓前台）在这里正好不重复：应用就在眼前时它本来就不弹。

安卓的原生策略把 `live_event` 记为**可通知但不推进游标**：它从不写 `pending_events`（会议事件只在房间活着时有意义，房间随发布端 socket 消失），而把游标推到服务端解析不了的 id 会让 `GetPendingEvents` 永远返回空列表。

## AI 听记

发布端可选开启「AI 听记」：共享过程中实时转写，停止后生成结构化会议纪要（概要 / 议题与讨论 / 结论与决定 / 待办事项），观众可以展开只读面板跟读。**默认收起**；观众端的「聊天 / 听记」是同一块**右侧全高侧边栏**的两个页签，展开时**挤压**画面而不是盖住它（窄屏改为上下堆叠），边界上的分割条可拖动调整宽度——直接复用 `components/common/SplitDivider.vue`（与 App 分栏、文件管理器预览同一套拖拽交互），面板宽度上限由 CSS 兜住，保证画面不被拖到消失。侧边栏只在 听记 页签激活时轮询转写。

**会中关闭听记只停止采集，不隐藏已经转写的内容**：页签的存在与否由「这场会议是否有听记」决定，而不是「此刻是否在录」。关闭后观众端的页签与内容原地保留（顶部加一行「主持人已关闭听记」说明为什么不再增长）；连在关闭之后才加入的观众，也会用一次 `notes?since=0` 探测决定是否给出页签——已经落库的转写不能因为加入得晚就消失。只有确实什么都没录到时才不给入口。

**重新出现时必须落到最新一行**：转写页签切走会重建组件，成员端的听记侧栏是 `v-show`（隐藏时高度为 0，量出来的「离底距离」也是 0，等于永远误判在底部）。两种形态都从会议开头显示，而跟随规则只滚动「本来就在底部」的列表——不修的话，中途切到页签或重新展开侧栏都会停在开头，之后再也不会跟随。因此抽出一个共享的「贴底」实现（`useStickToBottom`）：内容变长时跟随、**挂载与重新可见时贴底**、尺寸变化时重新贴底，同时记住读者是否主动翻上去回看——**主动往上翻的读者不受打扰**。转写列表与会议聊天共用同一实现，两侧行为不会漂移。

**开关本身走信令，不走 HTTP**：发布端的 `startNotes` / `stopNotes` 发 `set-notes`（`{type:'set-notes', enabled}`），服务端记进房间并以 `notes-enabled`（`{type:'notes-enabled', notesEnabled}`）广播给**全部**观众。`joined` 里的 `notesEnabled` 只是加入那一刻的快照，光有它的话，会中开启听记后已在场的观众永远看不到页签（它的 `joined` 早就过去了），会中关闭后也没人告诉观众停止轮询。该字段在 `notes-enabled` 帧里**总是存在**（关闭时是显式 `false`，不可省略）——省略与「关掉」在客户端无法区分。

### 发布端断线：宽限期 + 重连，而不是直接结束

发布端 socket 曾经是「房间的命」——它一断就广播 `publisher-gone`、删房间、收尾记录。但换 Wi-Fi、合盖休眠、代理回收空闲连接、安卓切后台产生的断线与「主持人按了结束会议」在服务端看来完全一样，为两秒抖动赔上整场会议（房间、录音、所有人的连接）不划算。

- **服务端保留 15 秒**（`publisherGrace`）：socket 断开只释放发布端槽位，到点前没人回来才真正收尾。重连成功（`AttachPublisher`）与取消收尾在同一把锁里完成，不会出现「刚接上就被拆」。
- **重连占位但握手未完成**时再给 5 秒（`publisherGraceHandoff`），避免升级失败的空占位把房间拖到空闲超时。
- **显式结束不受影响**：客户端发 `end` 后紧接着 `DELETE /api/live-share`，DELETE 立即收尾并取消待执行的宽限收尾。
- **房间最后才删**（先广播、再收尾记录、最后 `Delete`），所以「token 查不到」是「这场会议彻底结束」的可靠信号，测试与调用方不必猜收尾写没写完。
- **客户端**按 `0/1/2/4s` 重连（共约 7 秒，落在宽限期内），重连成功后重发 `publish`（标题 / 昵称）、`set-control-enabled`、`set-notes`——这些状态服务端只从这些帧得知，缺了就是「连上了但哑着」。期间写出的控制帧进 `publisherOutbox` 并在重连后补发（ICE 候选例外：过期的候选比没有更糟）。
- 每次尝试都失败才按老路径结束会议，并先把状态条切成「与服务器断开」。

### 转写状态：把「没在转」和「没人说话」分开

面板过去只有一张空状态卡：麦克风掉线二十分钟和刚开场还没人说话长得一模一样，而两者只有一个需要用户动手。现在转写页签顶部常驻一条状态行（`NotesStatusBar`），由 `useLiveNotes().health` 驱动，优先级即因果优先级：

| 状态 | 条件 | 是否可自愈 |
|---|---|---|
| `micDead` | 某信道源音轨 `ended` | 自动重取设备；失败才给「重新连接」 |
| `suspended` | `AudioContext` 被系统挂起 | 自动 `resume()`，失败才持续显示 |
| `offline` / `reconnecting` | 发布端 socket 断开 / 正在重连 | 见上一节 |
| `queued` | 待转写 ≥ 3 段 | 会自己追上 |
| `silent` | 距最后一次有声 ≥ 2 分钟 | 可能只是没人说话 |
| `ok` | 其余 | — |

**硬信号立刻报，软推测等一等**：音轨 `ended` 是事实，立即变红；「没声音」只是推测（人可能真的两分钟没说话），所以有 2 分钟阈值。页签上的红点同步变色（异常时变红且停止脉动），主持人待在「参会者」页签也能看见。

丢失段数与截断不参与这条优先级——它们是**永久的洞**，不是当前状态，所以单独挂在状态行右侧，正常态也一直显示。

### 麦克风与音频图的自愈

- **音轨 `ended`**（耳机断开、USB 声卡拔出、系统切换输入）→ 立刻按同一设备重取，失败两次后退回系统默认设备，仍失败才提示。自己主动停的轨道（换设备、结束会议）记在 `stoppedMicTracks` 里，不会被误判成掉线。
- **`AudioContext` 挂起**（切音频设备、休眠、安卓后台）→ 挂起时 `resume()`；`audioRunning` 保证「从没跑起来过」（无输出设备）不会被报成「被系统暂停」。

### 为什么必须在发布端采集

共享是纯 P2P，**服务端一个音频包都收不到**。而发布端本来就握着全部音源：系统声音、自己的麦克风、以及每个观众的麦克风（`pc.ontrack`）。所以转写只能在发布端做——它也是唯一还保留着**信道分离**的地方。

### 信道分离 + 按时间重排

每个音源单独录一条信道，互不混音：

```
mic         发布端的麦克风
viewer:<id> 每个观众的麦克风，一人一条
```

**只录麦克风，不录系统声音**。系统回环会把机器上正在播放的一切都录进来（音乐、通知音、另一个会议），而它唯一有价值的内容——远程参与者——在本产品里本来就通过 `viewer:<id>` 单独一路进来。早先两路都录时，同一句话会在 `system` 和 `mic` 各出现一次，靠 5 秒窗口去重才勉强合并；去掉之后这段重复从源头消失了。

于是**说话人标签是免费拿到的**，不需要说话人分离（diarization）模型。代价是各信道独立转写、完成顺序与说话顺序不同，所以读取时必须按 `startedAt` 重排——`startedAt` 由发布端**同一个时钟**打，跨信道可比。

- **在停顿处切段**，不是按固定时钟切：用 `AnalyserNode` 每 100ms 取一次 RMS，静音超过 450ms 且本段已满 4s 就收尾；连续说话则由 20s 硬上限兜底（仍在 Whisper 原生窗口内）。固定 10s 切会让每句话都有概率在词中间断开，Whisper 在切口处会吞词或猜词，一小时会议几百个切口，转写质量会明显变差。
- 每次收尾都得到**独立可解码**的完整 WebM/Opus 文件（`timeslice` 更省，但只有第一片带容器头，后续切片单独解不出来）。整段全是静音的会被丢弃——它不含内容，送上去只会换回一个空字符串；无法测电平的短尾段则保留（「不知道」不能当成「静音」）。
- 上传**每信道串行**，失败按 1s/3s/9s 退避重试。**积压不丢段**——字幕可以滞后，转写不能缺口；队列上限 180 段/信道（约 30 分钟音频）只是防内存泄漏的硬闸门，触顶会累加丢失计数，状态行右侧常驻显示「已丢失 N 段」。
- 停止时先停录音机、等最后一段真正产出（`onstop` 才生成 blob）再关 `AudioContext`，然后等队列排空（最长 3 分钟）才生成纪要；排不空就明确提示「纪要可能缺少结尾」。
- 回声去重：发布端用扬声器外放时，观众的声音会被自己的麦克风再次采到，同一句话可能出现在两条信道。合并时若两条信道在 **±5s** 内出现**归一化后完全相同**的文本，只保留较早的那条。真正的同时说话用词不同，不受影响。

### 产物：录音 + 三份 Markdown + 聊天（永久）

会议结束时，这场会落成一个目录（第一次真正要写东西时才创建）。**记录与目录都是永久的**，只有删除记录（或删除项目）才会消失：

```
<项目>/.clawbench/notes/2026-10-31-1430-周会-a1b2c3/
    minutes.md               纪要（末尾链接同目录的另外两份）
    transcript.vtt           原始转写（STT 原样输出，WebVTT 字幕；cue id = 信道，正文 <v 称谓>）
    transcript-revised.md    校对版转写（结合项目上下文修正听写错误与专有名词）
    chat.md                  聊天归档（会议结束时写入；详情读的是数据库）
    files.md                 会议期间打开的文件时间轴（归档结果与跳过原因）
    files/                   这些文件的归档副本（同一内容只留一份）
    audio/                   录音（会议结束后合并成整场 + 每信道各一份）
        meeting.webm         整场会议（混音轨）——听回放就听这一个
        mic.webm             发布端麦克风
        viewer-2.webm        某个观众的麦克风
```

- **整场会议是一个文件，不是一堆片段**：录制中每个信道被切成 10–20 秒的独立片段（每片都要能单独送去转写），会议结束后服务端把它们**重封装**成每信道一个文件，混音轨写成 `audio/meeting.webm`，然后删掉片段。用户打开详情看到的是「整场录音」一行，不是几十个文件。
- **重封装不是转码**：同一信道的片段来自同一套编码参数，把各段的 Cluster 复制进一个 Segment、把每个 Cluster 的时间码按该段距会议开始的偏移平移即可，音频数据一个字节都不改。平移同时保留了静音间隔——安静两分钟就是两分钟的时间码空档，不需要补静音音频。时间码平移后 `Info` 里的 `Duration` 按「最晚结束的那一段」重算，否则一小时会议在播放器里显示成几秒。
- **混音轨是录制端多录的一路**：发布端把每个被录音的信道同时接到一条共享的 Web Audio 总线上，再单独录这条总线（`channel=mix`，`archive=1` 上传——只存档、不转写，它没有单一说话人）。这样「整场会议」在任何播放器里都能直接听，而分信道文件仍然保留，供日后重新转写时保住说话人区分。
- **只有一个参与人时不再产出第二份**：单人会议的混音轨和那一路信道是同一段音频，两份都合出来等于把一个文件写两遍、占两倍磁盘。合并时若恰好是「mix + 一路信道」且 mix 存在，就只保留 `meeting.webm` 并把那一路的片段一并清掉；已经有 `mic.webm` 的旧会议不动（重试不删已完成的工作），mix 缺失（老录音）时也照旧合出信道文件。
- **合并只在上传队列排空之后**：发布端排空后调 `POST /api/live-share/notes/audio/merge`；纪要任务启动时也会再调一次（幂等）作为重试路径。已经有输出的信道直接跳过，所以重试不会产出一个只含残余片段的不完整文件。
- 合并**只对新会议生效**：老会议目录里的片段保持原样，详情页仍显示「录音（N 段）」。
- **转写用 WebVTT 而不是 SRT**：cue id 承载**信道**（`mic` / `viewer:<id>`）——显示名会被改名、复用、本地化，只有信道是稳定身份，文件里丢了它就再也对不上人；正文的 `<v 称谓>` 承载播放器要显示的名字。浏览器也只支持 VTT 的 `<track>`，SRT 得自己写解析器才能播。详情页读这个文件时会把头、cue id 和时间轴剥掉，只显示「说话人：内容」。
- **录音在转写之前落盘**：STT 挂了要重转、模型升级要复跑、某句听错要复核——都需要原始音频，而它是唯一无法再生的产物。写盘失败只记警告，不阻断转写。
- **文件名带 token 后缀**：同一分钟、同一标题的两场会不能共用目录，否则录音会交错、纪要会互相覆盖。
- **`audio/.gitignore` 内容为 `*`**：录音是二进制，一小时约 14MB/信道；同目录的 Markdown 仍然可以进 git。
- 录音**片段**（合并前）按 `<开始毫秒>-<信道>.webm` 命名，**按文件名排序就是按时间排序**，合并时也靠这个顺序与偏移把各段摆回时间轴，不需要索引文件。
- **转写是流式的，不再等会议结束**：发布端把某一路的 16 kHz PCM 边录边发（`WS /api/live-share/notes/stream`），服务端边识别边落库并推回客户端，省掉「等停顿 → 上传 → 整段识别」三段延迟。**引擎差异由服务端消化，客户端只有一条路**：流式引擎（豆包）收到音频就识别、边收边推 partial；只支持整段的引擎（OpenAI 兼容 / Whisper）由服务端攒成 WAV，安静 0.8 秒或攒满 10 秒转写一次。因此换引擎不用改前端，也不需要「这个引擎能不能流式」的能力位开关。
- **一句什么时候算说完，只能由服务端定**：流式引擎没有句末标记，只会一直重发当前这句的全文，故判据是「稳定 1.2 秒没有新修订」，一行最长 15 秒强制收口（否则连续朗读时整场会变成一行）。测试用逐帧到达的三段修订验证「三次修订只落一行」——把判据改成「每次都提交」会红。
- **转写页签显示「正在说」的灰色草稿**：还没定稿的那句以灰色草稿形式跟在已定稿行后面，用户能立刻看到识别在工作，而不是以为卡住。草稿不落库，定稿才成为一行。
- **片段边录边拼进整场录音**：不再等会议结束才开始合并——已在录的片段按时间码偏移直接拼进 `meeting.webm`，片段退化为纯存档。这样会议进行中就能听回放，且中途崩溃不丢已录部分。

### 校对版转写（转写与纪要之间的中间层）

原始转写是语音识别的结果，专有名词基本靠猜：`ClawBench`、`ACP`、人名、缩写，识别出来常常是同音词。所以在生成纪要**之前**多一道校对：

```
原始转写 ──(项目上下文)──▶ 校对版转写 ──▶ 纪要
```

- **上下文来自会议本身与项目文档**：会议标题、参会称谓、会中打开的文件名、项目文档里抽出的标识符，以及日期、时长、聊天记录、关键帧时间线——连同待校对片段一起给模型。不查 RAG、不读代码
- **只输出「原词 => 改词」替换对，由服务端确定性应用**：模型不再重写整篇，所以时间戳、说话人、行数在**结构上**不可能被改写（旧实现靠提示词求模型老实，文件事件合并依赖的 `[mm:ss]` 锚点一直是脆的）。替换对按「多数票 → 先出现者」跨块归一后一次性作用，同一错词只留一种写法；替换只作用于分隔符之后的内容，说话人标签永不改写。唯一的结构性例外是「换人」（见下）
- **说话人标签是信道，不是人**：一路声音是一个麦克风，麦克风前可能不止一个人（旁边的人被转述、两人共用一台电脑），所以「一行 = 一个人」不成立。校对因此有第二种输出 `[mm:ss] 原词 ==> 新说话人`：以该行的 `[mm:ss]` 为锚，在「原词」处插入一行，两行**共用同一个时间戳**——两个人是在同一个 cue 里说的，给后半句编一个新时间就是撒谎。三条同时成立才允许拆：有明显换人迹象（一问答、被点名应声、互相称呼）、新说话人在转写里**已经出现过**（不得新造名字）、换人后的第一句至少四个字且足以唯一定位；否则保持原样。`==>` 行永远按换人解析，解析不了就**丢弃**而不是判格式违规——格式违规会整场中止，而一句话说歪了并不说明其余修改不可用。前端 `parseRevisedTranscript` 本来就逐行渲染，多出来的一行自然成为独立的说话人行
- **答非替换对按格式违规失败**：例如又把整篇转写输出一遍，不能静默当成「无需修改」；没有修改必须回 `NO_CHANGES` 哨兵——这是区分「没错误」与「没照格式答」的唯一判据（换人行不参与这条判定）
- **人名与称呼各有专门规则**：转写自带的唯一人名词表就是**行首说话人标签**，而标签就是本人入会时填的**称谓**（发布端也一样，`notesLabel("mic")` 直接返回自己的称谓），所以正文里明显指同一个人的近音写法要改成标签里的名字，**标签本身不动**；称呼（「王总」「李工」）保留称谓，只校正其中的姓或名，不整体换成姓名。标签是代词或占位时（旧转写里的「我 / Me」、还没拿到称谓时的「观众 3」）不含姓名信息，提示词禁止据此推断，也禁止为任何说话人补上转写里没有的名字——**规则按说话人统一表述，不给任何角色开例外**。
- **发起人说明只服务旧转写**：新转写的标签已经是称谓，规则 3 直接覆盖，无需额外注入。但历史上（标签还是「我 / Me」时录的）会议仍会被重新生成纪要，那种转写里发起人的名字无处自证，所以 `LiveNotesSpeaker{Label, Name}` 仍写进**系统提示词**（不是某一段的正文，否则不含「我」的段落就看不到），说明「标注为『我』的那一路是发起人本人，称谓是 X」，并显式声明**优先于**上面那条代词禁令。`Label == Name` 时自动关闭（新转写就是这种），称谓为空或占位 `User` 时不注入；发起人全程没说话时没有标签可绑定，只注入称谓本身。校对与纪要两个阶段共用同一个 `LiveNotesSpeaker`。
- **长会分段**：校对按 6000 字切分、纪要按 2.4 万字切分，都按行切，不会把一句拆成两半。校对是 1:1 改写（输出≈输入），段小是为了让输出落在 `max_tokens` 内；纪要输出很短，段大是为了少丢跨段上下文。
- **输出被截断按失败处理**：校对必须与原文逐行对齐（换人只会增行，不会少行），模型撞上 `max_tokens` 时返回的是残稿（尾部整行消失）。所以 `finish_reason=length` / `stop_reason=max_tokens` 一律报错，整段校对降级为「纪要基于原始转写」，而不是把半截稿当成校对成功。
- **失败不阻断**：校对失败时纪要改用原始转写生成，`revise_status` 记为 `failed`，界面上写明「纪要基于原始转写」。有摘要胜过没摘要。
- 校对版本身也是文件，可以人工再改；改了不影响已生成的纪要（要重新生成一次纪要才会用上新版本）。
- **详情页有独立的「校对」页签**（紧挨着「转写」）：读 `transcript-revised.md`，但**按转写页签的画法渲染**——同一套说话人行（头像 / 说话人 / 内容），文件与屏幕事件仍是图标行，不是一块 Markdown 正文。文件本身是纯文本 `[mm:ss] 说话人：内容`，详情页用 `utils/revisedTranscript.ts` 解析（两种 UI 语言的冒号、`[--:--]`、事件行的中英文标签都要认），标题与说明行属于文件元信息、不进列表。校对在纪要之前完成，所以纪要还在生成时这一页通常已经有内容——有正文就不显示生成中。校对失败（纪要基于原始转写）或没开听记时显示空态说明，而不是一块空白面板。
- **转写与校对正文里的文件路径 / URL 可点**：两页共用 `TranscriptList`，正文走与 markdown 预览**同一套**标注与交互，不是第二套实现——`annotatePlainText`（先 HTML 转义 → `annotateBareUrlsIn` → `annotateFilePathsIn`，顺序不能反，否则 `github.com/foo/bar` 会被读成本地路径尾巴）产出与预览相同的 `.chat-file-path` / `.chat-file-open-btn` / `.md-external-link`，再挂 `useMarkdownDocumentInteractions`（`source: 'live'`，Back 回到会议）。所以桌面点路径 → 内联预览卡、触屏点 → 底部抽屉、旁边的打开按钮 → 文件查看器、目录 → 文件管理器、外链走全局确认层，行为与预览逐条一致。共享页不标注文件路径（文件查看器与 `batch-exists` 都要鉴权，画出来只能点空），只保留 URL。路径按项目根解析（转写不是文档，没有自己的相对基准目录）。
- **文件事件行与关键帧说明也走同一套标注**：`打开文件 docs/a.md`（open/close cue）与 `打开文件 main.ts`（帧说明）里的文件都是引用，两行的措辞、字号、颜色也统一（都是时间轴标记，不再一个「打开」一个「打开文件 ·」，也不再一个小一号灰字一个正文）。两处都有同一个坑：路径标注器**刻意不认单段文件名**（`AGENTS.md` 与 `build.sh` 这类标识符无法区分），而项目根目录下的文件记下来就是裸名（`打开文件 README.md`）。所以裸名先补 `./` 再标注、标完把 `./` 从显示里去掉；帧说明的标注源用完整 `ref`、标完把 chip 文本换回基名。两处的行读起来都和以前一样，点开的是真实文件。旧会议记录里服务端写死的是旧措辞（`打开 X` / `Opened X`），前端渲染时按当前文案重说一遍，所以老会议看起来和新会议一致。

### 会议期间打开的文件（转写里的第二时间轴）

一场会聊了什么，转写有；**看了什么**，转写没有。会议里打开过的文件是纪要最好的背景知识——"我们把 `README.md` 里那段接口说明过了一遍"比一句"讨论了一下文档"有用得多——所以会议期间在 ClawBench 里打开的每个文件都按**区间**记下来，并落进转写与会议目录。

- **只记 ClawBench 内部打开的文件**：文件管理器、聊天里的路径链接、会议资源、编辑器。浏览器/WebView 拿不到"用户在别的软件里打开了什么"，那需要 Windows/macOS/Linux 各写一套系统级前台窗口钩子，是另一件事。
- **两个采集点**：`useFileNavStack.openFile()` 是全部文件打开的唯一入口（它已经承担了「最近文件」的记录），打开 / 前进后退 / 换文件 / 关闭浮层都在这里进出 `utils/meetingFileTracker.ts`；另一个是**文件查看页签的可见性**（`useMeetingFileVisibility`）。只有前者时，**开会前就已打开的文件永远不会产生打开事件**——会中切到文件页签看十分钟，记录里也一条都没有；可见性把这件事补上：文件真正在屏幕上（页签激活、浮层打开、宽屏左栏未折叠）才算开始看，离开就收尾。追踪器是**叶子模块**，两个调用方都只单向调用它，避免 `fileNav → liveShare → chat` 的环。
- **区间是推断的**：没有"文件被关闭"的系统事件，只有四个信号——打开另一个文件、关掉预览浮层、文件查看页签离开屏幕（切页签 / 折叠左栏）、会议结束。会议结束时服务端把仍开着的按 `ended_at` 收尾（`CloseOpenLiveNoteFiles`），所以客户端崩溃不会留下一条永远开着的记录。同一文件 30 秒内重开合并成一段（切走再切回不会刷出碎片，但离开超过 30 秒就算两次访问），避免前进/后退刷出一堆碎片；不足 1 秒的停留直接丢弃。
- **落库 `live_notes_files`**：`(token, owner, path, opened_at)` 唯一，重复上报幂等；`closed_at` 只向后推进（重试时带着 `0` 不会把服务端已收尾的区间重新打开）。`owner` 一期恒为 `host`，为将来参会人上报留位。
- **转写里体现**：`transcript.vtt` 里插入 `cue id = file`、`<v 文件>` 的 open/close 两条短 cue（不是一条长 cue——那会在播放器里挂满整场）。前端 `parseVttCues` 据此标 `kind: 'file'`，`TranscriptList` 画成文件行而不是"文"字头像。文件行**不参与同说话人合并**，否则「打开 a.md」和「关闭 a.md」会粘成一行。
- **校对阶段不碰它**：`[文件]` 行不能交给校对模型（它会把非语音行改写成语音）。校对只吃语音，文件事件按 `[mm:ss]` 前缀**确定性地**插回 `transcript-revised.md`；模型把时间戳改烂时退化成末尾一节，不丢事件。
- **纪要单独给一节**：`## 会议期间打开的文件` 按墙钟时间列出区间，并附前 5 个文件的内容摘录（每个 1500 字、总预算 8000 字）。措辞明确"这些是看过的东西，**不是发言内容**"——否则模型会从"打开了 a.go"编出"团队决定重构 a.go"。这一节加在 map-reduce **之后**，否则长会里它会被并进最后一段的要点里消失。
- **归档**：会议结束时把文件复制进 `files/`（单文件 ≤ 5 MB、单场 ≤ 40 个、sha256 去重，同名加序号），`files.md` 记录时间轴、归档位置与跳过原因（过大 / 已不存在 / 无权限 / 内容重复）。资源页签会自动列出 `files.md` 与 `files/`，不需要额外接线。
- **观众只看文件名**：公开端点 `GET /api/share/{token}/notes` 返回同样的行但把 `path` 清空，只留 `name`——观众本来就在看共享画面，知道"打开了哪个文件"是连贯的，但主持人的目录结构不是他们的。

### 屏幕共享人变化（第三条时间轴）

会议里「现在这块屏幕是谁的」会变：主持人自己共享、成员申请共享、主持人收回、共享的人掉线。这件事不进转写就丢了——「这个报错在日志里」只有知道当时是谁的屏幕才有意义。

- **记录的是区间链，不是状态**：客户端上报**变化**（`sharer` 为空 = 没人共享），服务端在同一个事务里关掉上一段、开启下一段，所以时间线上永远不会同时出现两个共享人。重复上报同一个人只刷新称谓，不会把区间拆成两段。
- **谁在共享**：`viewer:<id>` 优先于 `host`——成员接管屏幕后，主持人的画面就不再是大家看到的东西。主持人的画面来自本地的 `captureKind`（共享屏幕/窗口），成员来自服务端的 `screenSharer`。
- **落库 `live_notes_screen`**（token / sharer / sharer_name / started_at / ended_at）。会议结束时服务端把仍开着的一段按 `ended_at` 收尾。
- **转写里同样体现**：`cue id = screen`、`<v 屏幕>`，例如「张三 开始共享屏幕」「张三 停止共享屏幕（8 分 25 秒）」。转写页签用显示器图标区分，和文件行一样不参与同说话人合并。
- **纪要**：`## 屏幕共享` 一节按墙钟列出谁在什么时候共享，紧跟在文件时间轴后面（两者回答的是同一个问题：当时在看什么）。
- **观众可见**：称谓本来就在参会名单里，公开端点不做脱敏。

### 关键画面（第四条时间轴）

会议记录原本有文字（纪要 / 转写）、有声音（录音）、有聊天，**唯独没有画面**。而屏幕会议里大量信息只存在于画面上：打开的那张架构图、切过去的那个页面、讲到一半停住的那一屏。所以会议过程中自动留存关键画面，作为时间线里的一行。

- **在发布端抓，不是服务端**：纯点对点下服务端一个媒体包都收不到；抓的也必须是**正在发送的那一路轨**，另开一次 `getDisplayMedia` 会再弹一次系统授权，共享单个窗口时还会把整块屏幕拍进去
- **抓哪一路跟共享者走**：成员共享时抓成员的画面，不是主持人自己的屏（与「谁在共享」同一判据）
- **触发带语义，不定时全量截图**：打开文件、切源 / 成员开始共享、语音关键句、画面显著变化、手动。前两条是主力——「主持人打开了什么、切到了哪」本身就是这场会的信息结构，而且这两条链路已经在记时间线了，截图只是给它们补上画面
- **去重与配额在编码之前**：先缩到 9×8 算 dHash，与上一张保留的画面汉明距离 ≤8 视为同屏直接丢弃；非手动触发之间至少间隔 8 秒；每小时 40 张、每场 80 张（服务端另有 100 张硬上限）。一小时的幻灯片会议因此只留几十张，不是几百张近似帧
- **语音触发天然滞后几秒**：转写要等 STT 往返，命中关键词时那句话往往已经说完。它抓的是「说完之后仍在看的那一屏」，不要宣传成「说到哪拍到哪」
- **存 `<会议目录>/shots/*.webp` + `live_notes_shots` 表**：与录音、纪要同目录，随记录一起删除
- **展示在转写时间线里**：缩略图内联在「打开 architecture.md」「张三开始共享屏幕」这类行下面，点开放大（复用图片查看器），**删除放在放大视图里**——缩略图上挂小叉在触屏上点不准，而误删不可逆。资源页另把 `shots/` 作为一个分组列出，可拖进聊天引用
- **开关独立、默认开、只归主持人**：与听记解耦（可以只要文字不要图，也可以只要图不要文字）。关掉即不抓不上传；中途打开从那一刻开始抓，**不补拍**之前的内容。成员端没有这个开关，成员共享的画面同样受它约束
- **不写进纪要**：`minutes.md` 只描述说过的话，把图塞进正文会让纪要变成相册
- **观众不可见**：观众看的是直播，不需要回看；公开分享端点也不暴露发布端的持久化产物

### 数据流

```
发布端  ── POST /api/live-share/notes/segment（multipart 音频 + channel + startedAt）
        ←─ { id, text }                     服务端用 STT provider 同步转写后落库
观众    ── GET /api/share/{token}/notes?since=<maxId>   （公开，token 即凭证，听记页签显示时才轮询）
发布端  ── POST /api/live-share/notes/minutes           （异步生成，轮询 GET 取状态）
发布端  ── POST /api/live-share/notes/chat              （每条聊天即时落库，按消息 id 幂等）
发布端  ── POST /api/live-share/notes/files             （打开/关闭区间批量上报，按区间幂等）
发布端  ── POST /api/live-share/notes/screen            （共享人变化，按变化上报而非状态）
发布端  ── POST /api/live-share/notes/shot              （关键画面：webp + 触发原因 + 时间）
发布端  ── GET  /api/live-share/notes/shots             （关键画面清单；单张删除走 DELETE）
发布端  ── POST /api/live-share/notes/regenerate/plan   （先要计划：要跑哪几步、会不会覆盖）
发布端  ── POST /api/live-share/notes/regenerate        （按计划执行：转写 asr/render、校对稿、纪要）
发布端  ── POST /api/live-share/notes/regenerate/cancel （取消当前任务）
发布端  ── GET  /api/live-share/notes/sessions          （会议记录列表；?token= 取单条）
发布端  ── GET  /api/live-share/notes/sessions/artifact （按 token 读产物）
发布端  ── GET  /api/live-share/notes/sessions/chat     （按 token 读聊天）
发布端  ── DELETE /api/live-share/notes/sessions?token= （删除记录 + 目录）
```

- **鉴权**：发布端端点需登录 + 项目 cookie，token 必须属于本项目。归属依据是**会议记录行**（发布端连上信令时就已创建），所以「结束共享」瞬间的最后一段上传与聊天仍能落地。
- **公开读**：`{token}/notes` 在会议结束后仍然可读——记录是永久的，房间只是实时通道。共享结束后**不能再进会**（信令 WS 已无发布端，返回 404），但同一 token 继续提供纪要、转写、校对稿与聊天，直到记录被删除。
- **保留期**：**没有**。记录、转写分段、聊天、磁盘目录都永久保留；删除记录（或删除项目）是唯一的删除路径。
- **纪要生成**：校对版转写超过 2.4 万字时先分段提取要点，再合并成纪要（map-reduce），避免整段塞进模型窗口被截断。
- **纪要的上下文不止转写**：会议日期与时长、参会人与发起人标记、会议聊天、关键帧时间线、上一场会议的待办事项都会一并给模型，因此纪要能多出一节「遗留事项」追踪上次没做完的事。长会议的分段提取必须保留 `[mm:ss] 说话人：` 前缀，否则最终合并时拿不到待办的负责人和时间。
- **没有 MediaRecorder 就降级，不拖垮整场会**：部分浏览器（如 WebKit）没有 `MediaRecorder`，早先 `new MediaRecorder()` 直接抛错会让会议启动整条链失败、用户只看到原始 JS 错误。现在先做能力探测：缺能力时不建采集、会议照常进入「进行中」（画面 / 麦克风 / 共享 / 聊天都在），会中打开听记开关会弹回并说明原因，创建页的听记开关直接禁用并写明为什么
- **纪要里用称谓指代本人**：新转写里发布端那一行本来就写着称谓，模型不需要任何说明。旧转写（标签是「我 / Me」）则相反：模型无从知道那是谁，而纪要要给没参会的人看，所以生成时把 `user.nickname` 与该信道的实际标注一起写进提示词（分段提取与最终合并两处都注入），纪要里指代本人时写称谓。`Label == Name`、称谓为空（占位 `User`）或本人全程没说话时不注入（校对阶段是另一条更宽松的规则：没说话也注入称谓，见上）。
- **落盘**：见上面的「产物」一节。纪要生成后写 `minutes.md`，同时把两份转写和录音留在同一目录；同一场共享重新生成会覆盖同名文件而不是堆副本。

### 会议记录列表与详情

列表读的是**数据库**（`live_notes`，一条 = 一场会），不是磁盘：记录在发布端连上信令时就存在，与「有没有录到东西」无关；没开听记、全程静音的会议同样列出，标「无产物」。

- `GET /api/live-share/notes/sessions` 按 `started_at` 倒序取 200 条；带 `?token=` 时返回单条 `{session}`。
- `GET /api/live-share/notes/sessions/artifact?token=&kind=` 读 `minutes.md` / `transcript.vtt` / `transcript-revised.md` / `chat.md`。目录由服务端从记录行解析，**客户端不传任何路径**。记录没有任何产物时 404。
- `GET /api/live-share/notes/sessions/chat?token=` 读落库的聊天（按服务端行 id 升序）。
- `DELETE /api/live-share/notes/sessions?token=` 删除记录：**先删目录、再删行**；房间仍在发布、或纪要/校对任务正在运行时返回 409。
- 「打开」走前端已有的文件查看器，传目录里那个文件的绝对路径。
- 每次切到页签、以及会议结束后都会重读一次，另有手动刷新按钮。
- **结束会议直接进入记录详情**，没有单独的「会后纪要」界面；生成中 / 生成失败 / 无产物都在详情里表达。
- 详情默认落在**资源**页签，页签顺序是 资源 / 纪要 / 转写 / 校对 / 聊天；资源页签顶部是会议链接（结束后不能再进会，但记录持续可读，见上）。
- **记录可以改名**：详情标题右侧的铅笔，与会话改名同一个输入框。**只改名字，不动磁盘目录**——所有产物路径都指向创建时的目录，改名不该搬动任何文件。上限 80 字（前端先拦，避免服务端 400 只换来一句「重命名失败」）。纪要 / 校对任务正在运行时也能改：链式任务写回标题前重新读库，用户填的名字不会被模型生成的名字覆盖

### 导入已有的录音 / 视频

会议记录不一定来自一场「直播」。把一段录音或视频拖到会议列表（或点 footer 的「导入」，
手机上没法拖）就会生成一场会议：转写 → 校对 → 纪要，与录下来的会议走**完全相同的链条**。

- **格式支持 = ffmpeg 的支持范围**：mp3 / m4a / aac / wav / flac / ogg / opus / amr / wma /
  aiff / ape 等音频，mp4 / mov / m4v / mkv / avi / wmv / flv / ts / mpg / 3gp / webm 等视频。
  解码交给服务器上的 `ffmpeg`，不在 Go 里重写一遍解码器——「支持任意音视频」这件事本身
  就是 ffmpeg 的职责。**没有安装 ffmpeg 时导入不可用**，接口返回 503，前端在拖动的那一刻
  就提示（能力位跟着会议列表一起下发），不会先传几个 G 再报错
- **统一转成一种形态**：`ffmpeg -vn -ac 1 -ar 16000 -c:a libopus` → 会议目录的
  `audio/meeting.webm`。这正是「一个人开的会议」合并后的样子，所以切片（20 秒窗口）、
  播放、重新识别、产物落盘全都不需要知道这场会议是导入的
- **原片留在会议目录里**：拖进来的那个文件被移动到会议根目录（同名，非法字符替换、不会覆盖
  `minutes.md` 这类产物名），在「资源」页签里能直接打开——会议要的是声音和文字，但原片是
  用户自己放进来的东西，不该用完就丢。移动而不是复制：一个两小时的视频不该在磁盘上占两份；
  上传暂存在系统临时目录，跨文件系统时退回复制
- **关键画面自动截**：没有「打开文件」这种触发点，所以用**画面变化**（ffmpeg 场景检测，
  score > 0.3）自动取帧，理由记为「画面变化」。两帧之间至少隔 15 秒（否则一页 PPT 一次
  切换会把会议变成连环画），单场最多 60 张，宽度上限 1280；超过 60 张时在整段里**均匀取样**，
  否则一场两小时的会只会留下开头二十分钟的画面。开场帧总是保留（纯口播的视频没有场景变化，
  至少得有一张能看出画面）。抽帧与转写并行跑——两者互不依赖，谁先完成谁先出现在页面上。
  纯音频文件没有画面，直接跳过，不算失败
- **上传与转码分开**：接口在文件落盘后就返回记录（`{token, session}`），转码与识别在后台跑，
  进度就是记录上的产物状态，列表本来就按 `generation` 轮询
- **会议时间取文件自身的时间戳**（`File.lastModified`），未来时间会被夹到当前时间：一段上周的
  录音应该落在上周，而不是拖进来的那一刻。会议名默认取文件名（去掉扩展名）——文件名本来
  就是录它的人起的名字，比日期占位符有信息量，也正因为它不是占位符，模型不会再去改名
- **上传走 XHR**：`fetch` 没有上传进度，几百兆的文件会让界面毫无反应
- **失败也是记录**：转码失败会把 `import` 错误码写在转写上（详情里显示 ffmpeg 的原始原因），
  并照常写结束时间——否则列表会把它当成「进行中」并给出「加入会议」
- 单文件上限 4 GB；一次拖多个文件时串行导入，每个文件各生成一场会议

### 产物重新生成

三个产物（转写 / 校对稿 / 纪要）各自可以重新生成，入口在文本页签顶部的状态条上，滚动时吸顶。**重新生成是修复动作，不是重来一遍**：失败保留旧内容，只在成功后才覆盖。

- **两条轴，不是一个状态**：内容轴（有没有内容、什么时候写的）+ 任务轴（当前 / 上次尝试的状态）。「正在重新生成」与「已有旧内容」必须能同时成立，单状态表达不了
- **转写的「重新生成」= 重跑语音识别**：从整场录音按 20 秒窗口切片、逐片送 STT、全部成功后再一个事务替换分段。识别质量不满意、模型升级、文件损坏都靠它。只按现有分段重建是另一条更便宜的路（级联补齐时默认走它）
- **向上级联的条件是「缺失或过期」**，不只是缺失。只补缺失会让「转写已更新、校对稿还是旧的」这种情况产出基于旧输入的纪要
- **向下级联默认开，可在确认面板取消**：重新生成转写会同时更新校对稿与纪要（内容保持一致）；想「只修转写错字、先别花纪要的钱」就取消勾选，下游标「待更新」，之后可以单独更新
- **非破坏性**：开始与进行中都不清空旧内容，失败只写错误码与状态，旧稿继续显示。级联中未执行的步骤回到空闲，内容轴不受影响
- **内容没变化不推进内容时间**：转写重建后字节相同却把下游标成过期，会白跑两次模型
- **单会议单任务**：用数据库事务抢占，不靠内存锁——多设备、多标签页、进程重启后都能正确互斥。任务状态落库，按模型分片写心跳，10 分钟无心跳判中断
- **取消只发 context cancel**，状态由任务 goroutine 唯一写入，避免取消处理器与任务同时写状态
- **生成链的输入是数据库里的文本**，磁盘文件是导出副本。手工改 `transcript-revised.md` 不会回流到下一次生成
- **完成时复用会议事件通知**，页面可见时客户端自己抑制；用户离开会议页也能收到结果

### 隐私

听记默认开启（用户是主动开共享的），但**观众端会显示「听记」入口**——被记录的人能看见，不做静默录音。关闭开关则完全不采集、不上传。

开启后**录音会以文件形式永久留在发布端项目目录里**（`audio/`），不只是转写文本。默认被 `audio/.gitignore` 排除在 git 之外，但文件确实在磁盘上，共享前应当让参与者知情。

## 会议设置（设置 → 视频会议）

一级分类「视频会议」，只放三类东西：**全局默认值**、**所有会议共用的能力**、**会改变产物成本 / 隐私的策略**。每场会议能改的开关仍在创建页与「会议管理」里，设置里只以「新会议默认值」出现——同一个开关有两份事实源，用户会以为设置没生效。

| 分组 | 配置 | 默认 | 说明 |
|---|---|---|---|
| AI 纪要 | 纪要模型 | 共享 `ai_summary` | 与语音摘要、推荐回复、自动命名、`/btw` 共用；改这里会一起变 |
| AI 纪要 | 会议结束后自动生成 | 开 | 由主持人客户端在结束时发起；关掉仍可在详情页手动生成 |
| AI 纪要 | 生成前先校对转写 | 开 | 关掉省一次模型调用，纪要改用原始转写 |
| AI 纪要 | 纪要输出语言 | 跟随转写 | `""` / `zh` / `en`，只影响纪要，不影响转写 |
| AI 纪要 | 读取打开的文件内容 | 开 | 最多 5 个文件各约 1500 字；关掉保留文件时间线，不发送内容 |
| AI 纪要 | 纪要输出上限 | 3000 tokens | 1000–8000；超出会以 `budget` 错误显式失败，不会静默截断 |
| 新会议默认 | 听记 / 关键画面 / 允许观众发言 / 允许成员共享屏幕 | 都开 | 只作为创建页的初始值，会议中仍可改 |
| 中继服务 | 地址 / API Key / API Secret | 未配置 | 服务器级共用；保存前先测通；Secret 只写不回显。创建页只留「本次使用中继服务」开关 |

**纪要模型为什么不做会议专用**：`ai_summary` 是一个共享凭据（provider + key），会议、语音摘要、推荐回复、自动命名、`/btw` 共用。再加一份会议专用模型就是第二份事实源，轮换密钥要改两处。真需要更长上下文的模型时，是在 `ai_summary` 之上加 override，而不是替换。

**输出上限只作用于最终 pass**：长会议的 map-reduce 分段提取仍有自己的固定预算（24000 runes / 4800 tokens 每段）。调大上限会让纪要写得更展开，但不会找回分段提取时已压掉的信息；调得过低会触发 `ErrLiveNotesBudget`（`errorCode=budget`），详情页的产物条会提示调大上限并提供「去设置」。

## 安全

- 管理端点（`POST`/`GET`/`DELETE /api/live-share`）**需登录**，且只操作本项目；发布端 WS 校验 token 与项目归属
- 观众 WS（`/api/share/{token}/signal`）与听记读取（`/api/share/{token}/notes`）**公开**，token 即凭证；信令 WS 必须带 `?name=`（观众称谓），清洗后为空或超过 32 字在**升级之前**返回 400（`ViewerNameRequired`），token 不存在/无发布端仍是 404 且先判（会议结束后房间已销毁，信令 WS 自然 404——那是「不能再进会」，与记录可读无关）
- **`{token}/notes` 在会议结束后继续可读**（记录是永久的，房间只是实时通道），因此一条链接等于一份**长期**的会议记录读凭证：纪要、转写、校对稿与聊天。这是「链接长期保留到记录被删除」的直接代价，删记录即撤销；`hidden` 的历史行不解析（404），与列表一致。`?full=1` 才带归档聊天与校对稿正文，实时轮询不带
- 称谓清洗：去掉控制字符（换行替换为空格并压缩连续空白）。称谓会逐字写进归档 `chat.md` 的发言人列与通知正文，一个换行就能伪造一整行会议记录
- 称谓在房间内**唯一**：与发布端称谓及每个已加入观众比对（忽略大小写与首尾空白）。重名会让观众列表、归档 `chat.md` 的发言人列与转写无法区分两个人（这三处都按名字归属发言）。拒绝走**升级之后**的 `name-taken` 帧再关 socket，不是升级前的 400——WebSocket 握手失败没有页面能读的响应体，分享页只能报「连接失败」；收到该帧后退回称谓门、保留原名并提示换一个
- 观众帧 `control-request` 与 `viewer_joined` 按 `(token, 观众 id / 称谓, 事件类型)` 做 **30 秒窗口去重**：分享链接匿名可写，不去重的话一个脚本循环发帧就能把通知表灌满（500 条上限会挤掉真实通知），并让主持人端每帧弹一次 toast
- 听记上传（`/api/live-share/notes/segment`）需登录 + 项目 cookie，且 token 必须属于该项目；上传体上限 4MB、单段时长上限 120s、每段文本上限 2000 字
- 成员共享屏幕需要发布端打开房间开关（初始值见「设置 → 视频会议」，出厂为开）；同一时刻只允许一个共享者
- `setPendingCaptureSource` 一次性消费：消费后清空，任何页面后续调用 `getDisplayMedia` 都会被拒绝
- 复用 `ServeSharePage` 的 `Referrer-Policy: no-referrer`，避免 token 经子资源请求泄露
