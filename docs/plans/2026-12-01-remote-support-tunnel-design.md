# 远程运维通道设计方案

## 一、要解决的问题

ClawBench 部署在**内网 A**，要运维的目标设备在**另一个内网 B**。两边都不能被外部主动连进来，中间只有一台**公网服务器**能同时被两边访问。

需求：从 ClawBench 直接连到内网 B 的目标设备（Linux），过程中**目标设备的账号密码始终由设备方掌握，不交到运维方手里**。

## 二、整体结构

```
内网 A                     公网服务器                 内网 B
┌─────────────┐          ┌──────────────┐         ┌──────────────────┐
│  ClawBench  │──TCP────▶│  服务端程序   │◀──TCP───│ 客户端程序(Windows)│
│  (DBeaver/   │  端口X  │  (Linux)     │  固定   │      │            │
│   ssh 客户端)│          │              │  端口   │      │            │
└─────────────┘          └──────────────┘         └──────┼──────────┘
                                                          │ 内网
                                                          ▼
                                                    ┌──────────┐
                                                    │ 目标设备  │
                                                    │ (Linux)  │
                                                    └──────────┘
```

三条连接：

1. **客户端 → 服务端**：设备方那台 Windows 主动连出去，长连接，固定端口。
2. **客户端 → 目标设备**：客户端用设备方保管的凭据，在需要时登录目标设备。
3. **ClawBench → 服务端**：运维方连到服务端分配的对外端口。

两条主动连接都是"由内向外"，内网 A 和内网 B 都不需要开放任何入站。

## 三、为什么用"代登"而不是"直接转发"

中间有两种做法：

| 做法 | 说明 | 是否满足"密码不外流" |
| --- | --- | --- |
| 直接转发 | 服务端把 TCP 字节透传给目标设备，运维方直接面对目标设备的 SSH 登录 | ❌ 运维方仍需目标设备密码 |
| **代登（本方案）** | 客户端在每条连接上用**自己保管的**凭据登录目标设备，再与运维方会话对接 | ✅ 运维方从不知道目标设备密码 |

要求「设备方只允许运维方进入，但密码不泄露」，只能选代登。

## 四、程序形态

**同一个程序，两种身份，两份编译产物：**

- `tunnel-server`（Linux 版）→ 部署在公网服务器
- `tunnel-client.exe`（Windows 版）→ 发给设备方

代码一份，编译目标不同。

### 4.1 服务端（公网服务器）

无网页界面。配置写文件，**第一次启动时自动生成带中文注释的配置文件**，改完重启生效。

配置项：

```yaml
# 服务端配置
listen_port: 7000          # 客户端连过来的端口，固定
relay_port_range: [22000, 22999]  # 分配给各现场的对外端口范围
log_file: /var/log/tunnel-server.log
```

职责：

- 接受客户端连接，完成认证
- 为每个客户端**自动分配**一个空闲对外端口（从 `relay_port_range` 中取，用完回收）
- 在分配的端口上监听，收到连接后通过已建立的通道通知客户端
- 记录日志：谁连上、占了哪个端口、什么时候断的

### 4.2 客户端（设备方 Windows）

Windows 原生对话框（`syscall` 调系统 API），不引入任何 UI 库，产物保持单文件小体积。

第一次运行时依次弹窗填写：

| 字段 | 说明 |
| --- | --- |
| 公网服务器地址 | 服务端所在机器 |
| 服务端账号 / 密码 | 客户端登录服务端用 |
| 目标设备地址 | 内网 B 中那台 Linux |
| 目标设备账号 / 密码 | 设备方的凭据，仅存本地 |
| 访问密码 | 自动生成，8 位 |

**连接成功后，弹窗显示三样东西**，供设备方口头或截图告知运维方：

```
地址：  1.2.3.4
端口：  22017
密码：  Kx9#mQ2f
```

填写完成后窗口收起，程序在后台维持连接。**关闭程序 = 公网服务器上的端口一起关闭。**

## 五、连接建立后的流程

```
运维方连 1.2.3.4:22017
        │
        ▼
服务端接受连接，转给对应的客户端
        │
        ▼
客户端校验"访问密码"  ── 不对 ──▶ 断开
        │ 对
        ▼
客户端用保管的目标设备凭据登录 192.168.1.50:22  ── 失败 ──▶ 告知运维方
        │ 成功
        ▼
双向搬运字节，运维方看到的就是目标设备的命令行
```

**每一条外部连接都独立走一遍**「验密码 → 登目标设备 → 搬运」，因此可以同时开多个窗口，互不影响。

## 六、密码与安全

**访问密码**：程序自动生成，8 位，含大小写字母、数字、符号。**排除易混淆字符**（`l` `1` `O` `0` `|` `I`），保证口头传达不出错。

**本地存储**：服务端账号密码、目标设备账号密码存在 Windows 凭据保管（Credential Manager），配置文件中只存引用；访问密码存哈希（`crypto/subtle` 定长比较）。

**防护层数**：访问密码 + 端口不公开（在 `22000-22999` 中随机分配，外部无法枚举）。两者叠加才够——单纯 8 位密码强度有限。

## 七、稳定性处理

| 问题 | 处理 |
| --- | --- |
| 短时断网 | 自动重连，间隔指数退避（1s→2s→4s…上限 30s） |
| **半死连接**（TCP 还在但已不通） | 定期心跳检测，超时主动断开重连 |
| 服务端重启 | 客户端自动重连并重新申请端口 |
| 目标设备登录失败 | 明确回报"无法连接目标设备"，而不是给一个空窗口 |
| 多窗口并发 | 每条连接独立的会话，不共享 |

## 八、需要设备方配合的事

1. 在 Windows 上双击运行程序，按弹窗填写（约 2 分钟）
2. 把弹窗显示的**地址 / 端口 / 密码**告知运维方
3. 目标设备的账号密码由设备方自己填写，**运维方不需要也不应该知道**

## 九、不在本方案范围内

- 图形化远程桌面（本方案只提供 SSH 命令行，不做画面传输）
- 多台目标设备的批量管理（当前每个现场一台）
- 服务端的 Web 管理界面（只出配置文件 + 日志）

## 十、后续可扩展

- 一个客户端管理多台目标设备
- 访问密码支持定期轮换
- 服务端增加在线状态查询（当前只能看日志）
