# 多所 300 人大会：观众模式 + 每所中继

日期：2026-11-03
前置：[直播共享的融合方案](2026-10-30-live-share-hybrid-sfu-design.md)、[桌面屏幕与声音共享](2026-10-28-desktop-screen-audio-share-design.md)、[AI 听记](2026-10-30-live-share-ai-notes-design.md)

## 背景

真实需求与前面几份设计稿的假设不同：

| 维度 | 现状假设 | 实际需求 |
|---|---|---|
| 规模 | 8 人（`internal/liveshare/room.go:53`） | **300 人** |
| 分布 | 同一局域网 | **4 个研究所，可变** |
| 所间带宽 | 无（P2P 不过服务器） | **10–100 Mbps** |
| 发言 | 人人可说话 | **发言人很少，观众举手后经批准才开麦** |
| 单所人数 | — | **单所 100+ 人** |

「发言人很少」是这份设计成立的前提：它把问题从「N 人互相看见」降级为「N 人看 1 人」，带宽和 CPU 都随之降一个数量级。

**非目标**：多地之间自由讨论、观众互看、观众开摄像头。这些需求一旦出现，本方案不适用，需要重新评估。

## 结论

三条同时成立才可行：

1. **观众只订阅主播**——每人 4 Mbps，而不是 300 人互相订阅；
2. **每个研究所一台 LiveKit 中继**——所间只走「所数」路，与人数无关；
3. **控制面从「全量广播」改为「主持人全量 / 观众摘要」**——这一条是主要工作量，不是媒体。

第 3 条最容易被低估：现在的名单与状态推送是按 8 个人写的，300 人会把服务器先压垮，而不是带宽。

## 一、为什么不是单节点

300 人 × 4 Mbps = **1.2 Gbps**，任何单机网卡都不够，且 SRTP 加解密要吃掉 4–6 核。

分所之后：

| 位置 | 出口 | CPU |
|---|---|---|
| 主节点（主播所在所） | 3 × 4 = 12 Mbps | < 1 核（只转发） |
| 每个所（100 人） | 100 × 4 = 400 Mbps | 1–2 核 |
| 每个观众 | 4 Mbps 下行 | 无 |

经验公式：**本所人数 × 码率 < 网卡 × 0.6**。千兆网卡在 4 Mbps 下约 150 人，2.5 Mbps 下约 240 人。

## 二、拓扑

```
                    主节点（主播所在所 / 中心机房）
                    livekit-server
                        │
         ┌──────────────┼──────────────┐
         │ 视频 1 路      │              │
         ▼              ▼              ▼
      所 B            所 C            所 D
   livekit-server  livekit-server  livekit-server
   + 桥接程序        + 桥接程序        + 桥接程序
         │              │              │
     100 人看         60 人看         60 人看
     （局域网）       （局域网）       （局域网）
```

- 所间只承载「主播一路」，**与每所人数无关**；
- 所内观众从中继拉流，走局域网；
- ClawBench 只在主节点（或任意一台），承载控制 WS。

## 三、媒体组织

### 主播

发布一条视频 + 一条系统音频 + 一条麦克风。只发一次，由主节点 SFU 复制给各所中继。

**simulcast 取决于所间带宽，不是一个固定选择。**

- **所间 100 Mbps**：关闭。本地与外地都能拿 1080p，分层没有收益，只会让主播多压 1.5–2 倍 CPU。
- **所间只有 10 Mbps**：必须开启。主播发三层，本所观众订最高层（1080p，走局域网），各所中继订中间层（720p / 1.5 Mbps，走所间）。否则为了省所间带宽会把本所观众一起降成 720p——他们在千兆局域网里本不该受这个限制。

判据：`单路码率 ≤ (所间带宽 × 0.6) / (所数 - 1)`。4 所 100 Mbps 时上限约 20 Mbps，随便发；4 所 10 Mbps 时上限 2 Mbps，此时 simulcast 才有意义。

### 观众

只订阅主播的视频与音频。**不订阅其他观众**，也不发布任何轨道——这是 300 人可行的全部原因。

### 发言人（被批准后）

发布一条麦克风音频。音频 40 kbps，跨所可以忽略不计，因此**不需要为音频做级联优化**：星形两跳（发言人 → 主节点 → 各所）约 400–600 ms，对轮流问答可接受。

### 中继程序

官方组件拼不出可用的级联：`Ingress` 支持 RTMP/WHIP/URL，`Egress` 只支持推 RTMP/SRT/WebSocket（**没有 WHIP**）。RTMP 走 TCP，在窄带或抖动的所间链路上会队头阻塞，画面一顿一顿。

因此每所跑一个桥接程序（Go，`github.com/livekit/server-sdk-go/v2`）：

1. 连主节点，订阅主播的 track；
2. 连本所 LiveKit，把 track 发布进去；
3. 反向：把本所发言人的音频发布到主节点；
4. **不订阅本所自己上传的轨道**——否则本所会听到自己两次（本地直采 + 绕回），间隔约 400 ms，像回音壁。

代价是「解码 + 重编码」一道损失与一台边缘机的 1–2 核；换来的是走 WebRTC/UDP，链路劣化时自动降码率而不是卡死。

## 四、控制面改造（主要工作量）

### 现状：广播与轮询

下表描述的是**放开人数上限之后、改造之前**的行为——也就是只把 `DefaultMaxViewers` 改成 300 会发生什么。这正是为什么这两件事必须一起做。

| 位置 | 行为 | 300 人时 |
|---|---|---|
| `internal/handler/live_share.go:1123` `broadcastRoster` | 每次有人进出，向所有人推完整名单 | 12 KB × 300 人 = **3.6 MB / 次** |
| 同上，入场高峰 | 300 人陆续进入 = 300 次广播 | 约 **1 GB** |
| `web/src/composables/useLiveShare.ts` `startTalkMetering` | 每 200 ms 遍历所有观众，有变化就发 | P2P 上限 8 人时无碍；**SFU 模式下整块不需要**（改用 LiveKit 的 `ActiveSpeakersChanged`） |

`Room.Roster()`（`internal/liveshare/room.go:214`）每次调用都从 1 遍历到 `nextID`，且 `nextID` 单调递增、不复用（`:520`）。长时间会议里有人反复进出时，`nextID` 会远大于在场人数，广播成本随之线性上升。

### 目标

| 现在 | 改成 |
|---|---|
| 名单全量广播给所有人 | **主持人拿全量；观众只拿 `onlineCount` + 正在说话的 ≤3 人** |
| 200 ms 广播所有电平 | **只广播越过阈值的发言人；SFU 模式下直接采用 LiveKit 的 `ActiveSpeakersChanged`** |
| 有人进出立即广播 | **1 秒窗口内合并成一次** |
| 上限 8 | 按模式：P2P 8 / 大会 300 |

`Room.Roster()` 同时改为遍历在场集合（`len(viewers)`），不再依赖 `nextID`。

**SFU 模式下的说话指示不需要自己算**：LiveKit 服务端已经在计算音频电平并广播 `ActiveSpeakersChanged`。P2P 模式保留现有实现。

### 举手队列

新增房间级队列，与 `talkEnabled` 开关正交：

```
观众 raise-hand  →  入队（只推给主持人）
主持人 approve   →  该观众获得发言权（LiveKit 侧同步 grant）
主持人 revoke / 观众自己放下  →  出队
```

队列长度设上限（建议 20），超出时拒绝并提示「举手人数已满」——300 人同时举手时，主持人无法处理，也不该让队列无限增长。

## 五、接口变更

### WS 帧（`internal/liveshare/signal.go`）

| 方向 | 帧 | 说明 |
|---|---|---|
| 观众 → 服务端 | `raise-hand` | 举手 |
| 观众 → 服务端 | `lower-hand` | 取消举手 |
| 服务端 → 主持人 | `hand-queue` | 队列快照（全量，量小） |
| 服务端 → 观众 | `hand-ack` | 已入队 / 已批准 / 被拒绝 |
| 服务端 → 观众 | `room-summary` | `{ onlineCount, speakers[] }`，替代 `roster` |

`roster` 帧保留，但只发给主持人。

### HTTP

| 端点 | 用途 |
|---|---|
| `POST /api/live-share` | 增加 `mode: "p2p" \| "sfu"` |
| `POST /api/live-share/token` | 签发 LiveKit JWT（HS256，stdlib `crypto/hmac`） |
| `POST /api/live-share/webhook` | LiveKit 回调（**必须验签**） |
| `POST /api/live-share/guest` | 批准/撤销发言 |

`internal/api/openapi.yaml` 必须同步——仓库有 drift 测试。

### 配置

```yaml
live:
  sfu:
    url: wss://livekit.example.internal
    api_key: ...
    api_secret: ...
    max_viewers: 300
```

为空时「大会模式」入口禁用，P2P 行为完全不变。

## 六、听记

主播订阅发言人的音频 → `useLiveNotes().addViewer(id, stream)`，与现在一致。

**约束**：SFU 模式下主播必须订阅所有发布者，否则那段话不会进纪要，且不会报错。这一条要写进代码注释。

「观众不能自由开麦」不只是舞台管理，也是听记链路的容量前提——300 人同时说话会让主播解码 300 路音频。

## 七、容量与降级

| 规模 | 拓扑 | 所间流量 |
|---|---|---|
| ≤28 人（1080p 2.5 Mbps） | 单节点，不用中继 | 人数 × 2.5 Mbps（≤70） |
| 29–46 人（720p 1.5 Mbps） | 单节点，压码率 | 人数 × 1.5 Mbps（≤69） |
| 46–500 人 | 每所一台中继 | 所数 × 码率，与人数无关 |
| >500 人 | 本方案不适用 | — |

**不需要中继的门槛**：`总人数 × 码率 < 所间带宽 × 0.7`。100 Mbps 下，2.5 Mbps 约 28 人、1.5 Mbps 约 46 人。低于这个数就别搭中继——它是一整套新故障模式。

降级规则：

- 所间链路劣化 → 中继自动降码率（WebRTC 拥塞控制），不切拓扑；
- 某所中继挂掉 → 该所全员掉线，其他所不受影响（这是中继的故障隔离收益）；
- 主节点挂掉 → 全会结束，与「主播掉线」同语义。

## 八、分阶段

| 阶段 | 内容 | 产出 | 依赖 |
|---|---|---|---|
| **P0** | 房间上限按模式放开；控制面瘦身（名单分级 + 节流 + 摘要帧） | **单所 100 人可用**，不引入任何新部署 | 无 |
| P1 | 抽 `LiveTransport`，P2P 实现接上 | 行为零变化，为两条拓扑铺路 | P0 |
| P2 | LiveKit 接入：mode / token / webhook / transport 实现 | **单节点 ≤100 人**（400 Mbps 出口） | P1 |
| P3 | 每所中继 + 桥接程序 | 4 所 300 人 | P2 |
| P4 | 举手 / 批准 / 上台 | 完整大会形态 | P2 |

**P0 独立成立**，且是唯一不需要任何新部署的一步。先让单所 100 人跑通，再决定要不要背中继。

## 九、风险

| 风险 | 说明 | 对策 |
|---|---|---|
| 控制面先崩 | 300 人入场时的名单广播（约 1 GB） | P0 必须先做，不能和 P2 一起上 |
| 现场 WiFi | 100 人 × 4 Mbps = 400 Mbps，单个 AP 给不出 | 有线 / 多 AP / 降码率到 1.5 Mbps |
| 权限双写 | 房间状态与 LiveKit grant 不一致 → 禁言了还能说 | 单向：房间状态权威，变更下发并重试 |
| 听记漏人 | 主播没订阅某发布者 | 订阅策略写死为「所有发布者」，加测试 |
| 中继回声 | 本所听到自己两次 | 桥接程序不订阅本所上传的轨道 |
| 中继链路 | 4 台机器 + 4 个进程 + N 条跨所链路 | 只在人数确认超过门槛后再上 |

## 十、未决问题

1. **300 人的名单 UI**：主持人真的需要看 300 行吗？建议只显示「举手队列 + 发言人 + 在线人数」，完整名单折叠。
2. **举手并发**：300 人同时点举手时，队列上限 20 是否合适？超出后是拒绝还是排队等待？
3. **跨所发言的延迟**：星形两跳 400–600 ms。若实际使用中反馈「抢话困难」，再评估音频全互联（每所直连其他所，4 所 12 条链路，合计 < 1.5 Mbps，100 Mbps 下完全铺得起）。
4. **中继的部署归属**：每所一台由谁维护、证书怎么发、升级怎么推。
5. **是否保留 P2P**：大会模式上线后，小会仍走 P2P。两条拓扑两套代码，用 `LiveTransport` 隔离，但回归面翻倍——是否值得，需要在 P2 之后回看一次。
