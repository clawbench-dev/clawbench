## 0.2.3 评审修复

安全存储读取失败按服务器降级，保留列表、名称和选中目标，失效的保存引用不能继续用于认证。本地登录页可在本次会话忽略已保存凭据，使用手动密码完成认证且不读写安全密码资产；这不是清空密码或绕过服务器认证。网页重新认证后的 `setSSHPassword` 已接通实际消息桥，原生及时更新当前隧道密码和日志脱敏，并按接收时的服务器地址串行保存。已接收写入在页面关闭后仍归属于原服务器，保存、删除与后续登录共用队列；重新进入登录页先等在途写入结束，保存错误向用户报告。

宿主契约测试执行真实打包 bootstrap，并与共享 TypeScript 接口的必需成员逐一比较，另行覆盖 RPC 参数、成功应答、失败传播与不等待 Promise 的调用方式。单元 / 契约测试只能证明所覆盖的代码行为，不能代替真机 ArkWeb、AssetStore 和网络链路验收。

连接、密码存取、通知、文件和分享等原生失败使用中英文消息，切换语言时即时更新文件反馈、通知标题及状态错误。HTTPS 继续验证 CA 和服务器主机名：证书不可信、过期或域名不匹配不再混同于普通网络错误；TLS 协商、CA 配置、DNS、超时和权限问题分别分类。当前没有应用内自签名证书信任例外，设置页按 `forgetTrustedCerts` 是否真实存在显示证书管理，不暴露不可用入口。

`EntryAbility` 仍强制原生壳采用深色模式，保持启动、连接和加载过程的现有外观。网页主题与系统栏同步继续独立工作；网页切为浅色不代表原生弹窗和控件已完成浅色适配，此项保持待验收。

## 隧道与浏览器边界

SSH 通过 libssh2 + mbedTLS 实现，认证前检查按服务器保存的主机密钥，首次或变化时要求确认。HTTP2 通过 nghttp2 实现，TLS 保留主机名与受信 CA 校验。依赖版本、下载 SHA-256 和许可在原生构建配置中固定；不接受忽略 TLS 校验的替代方案。

SSH 与 HTTP2 的正向和反向分别各通过 6 轮模拟器数据测试，包含 2 MiB、慢读与并发，收发 SHA-256 一致。SSH 指纹 UI 与隔离测试服务公开密钥哈希核对一致后信任，实际状态为 `transport: ssh`、`connected: true`，已有正反向映射自动恢复通过。这证明已测试路径的数据完整性，不代表真机、所有 TLS、网络切换、错误恢复和长期连接场景都已通过。

半关闭测试链路中的 hdc 会提前关闭双向连接，无法区分客户端半关闭与测试转发层的影响。因此本轮半关闭记为未验收，需要换用能保留单向 EOF 的链路，不能将连接关闭或双向数据测试算作通过。

原生连接不在 UI 线程阻塞；离前台时不发起新连接或主机指纹确认，已有隧道只在应用进程继续获准运行时转发。系统浏览器有独立 Cookie / 存储，未实现 Android BrowserActivity 的内嵌 sandbox 会话语义；打开前的隧道就绪处理也不能提供无限后台保活。

## 悬浮会话状态

安卓实现使用跨应用悬浮窗显示运行中、待批准和未读会话的计数，展开后按项目分组，并携带会话和项目标识跳转。数据来源为 `GET /api/ai/sessions/overview` 与会话、任务事件。完整复刻包含后台显示、关闭与重新启用、分组列表、点击跳转和切服清理，不能以应用内部弹窗替代跨应用能力后宣称完成。

当前鸿蒙工程保持 `floatingStatus: false`，未加入需要特殊授权的悬浮窗权限，也未用空实现返回启用成功。

| 途径 | SDK 26 定义 | 当前判断 |
| --- | --- | --- |
| `window.createWindow` + `WindowType.TYPE_FLOAT` | `SYSTEM_FLOAT_WINDOW` 为 `system_grant`、`system_basic`，允许通过签名 profile 配置（`provisionEnable: true`） | 当前未配置相应权限资格，普通运行时授权对话框不能补足签名侧要求 |
| API 26 的 `floatView` | `FLOAT_VIEW` 为 `user_grant`，但权限级别仍为 `system_basic`，且需要 profile 许可 | 用户同意与签名资格是两层条件；不能因它是 `user_grant` 就视作普通应用可直接使用 |
| `floatingBall` | `USE_FLOAT_BALL` 为 `system_grant`、`system_basic`，需要 profile 许可 | 不能作为绕过上述门槛的通用途径 |

证据位置：

- `openharmony/toolchains/lib/PermissionDefinitions.json`：`SYSTEM_FLOAT_WINDOW`（本 SDK 第 615 行）、`USE_FLOAT_BALL`（第 7536 行）、`FLOAT_VIEW`（第 7565 行）的 `grantMode`、`availableLevel` 与 `provisionEnable`。
- `openharmony/ets/api/@ohos.window.d.ts`：`createWindow` 的权限说明（第 1850 / 1883 行）和 `201 Permission verification failed` 错误。
- `openharmony/ets/api/@ohos.abilityAccessCtrl.d.ts`：`requestPermissionsFromUser` 说明其用途为请求 `user_grant` 权限；该接口不会改变应用的 APL 或签名 profile。
- `openharmony/ets/api/@ohos.window.floatView.d.ts`：能力起始于 API 26；`start()` 要求 `FLOAT_VIEW`，并明确需收到 `STARTED` 回调才能确定真正启动成功。`start()` 的 Promise 返回不代表窗口已显示。
- 项目 `harmony/build-profile.json5` 的 `signingConfigs` 为空；本轮没有特殊权限授权 profile，也没有相关真机能力验收证据。

`availableType: NORMAL` 不等于 `availableLevel: normal`。前者说明可用的应用类型，后者决定权限等级。具备所需平台批准与签名授权后可以继续实现和验收，当前结论不是“鸿蒙永远不支持悬浮窗”。

若后续取得授权，实施时应将“用户启用该功能”和“窗口当前可见”分开保存：成功创建并确认启动后才能报告启用；回到前台或没有活动时隐藏，不擅自取消用户偏好；切服、退出与权限撤销时释放窗口、监听及旧事件。API 26 的 FloatView 还需独立处理低版本兼容、系统限制尺寸、前台创建条件和用户关闭后的恢复。

## 通知与后台范围

普通系统通知使用 NotificationKit 的动态授权及 wantAgent 点击拉起，不依赖上述悬浮窗或实况窗权限。当前实现提供按服务器隔离的原生事件订阅、补拉、去重、已读撤销和冷启动导航。

0.2.1 修复启动授权缺失：原先只由远程工作台的 `setNativePushEnabled(true)` 触发申请，未部署鸿蒙适配的前端无法可靠触发。现在由本地登录页完成加载、消息端口就绪后调用 `requestStartupPermission()`，通知点击直接进入工作台时也在页面就绪后补充调用；后台延迟到前台再申请。应用进程内自动申请一次，已授权时跳过；与设置页请求共享在途 Promise，拒绝或服务异常不会阻塞登录，也不改变服务器推送方式。权限状态支持在尚未绑定服务器时查询。

配套 SDK `openharmony/ets/api/@ohos.notificationManager.d.ts` 第 770 至 807 行说明：`requestEnableNotification(context)` 必须在界面 `loadContent` 成功后使用；用户拒绝后该 API 不能再次弹出授权框。这种情况下需从系统设置的应用通知管理中开启，重启应用不会绕过拒绝。首次弹框与拒绝后继续显示登录页已用 HarmonyOS 7 / API 26 模拟器独立测试包验证；不代表已完成真机消息投递验收。

0.2.2 引入原生接收启用：绑定已认证服务器以及前后台切换时，原生层读取该服务器的 `/api/config`，按 `push_mode` 同步本地订阅；只有 `native` 启用，`disabled` 和其他 IM 通道保持关闭，不向服务器写设置。缺字段使用上游默认 `native`，非法响应和请求失败保留已知偏好并报告异常，后续配置同步再核对。不以系统授权自动替代推送方式选择；旧服务器前端没有鸿蒙宿主适配时，这条路径也可工作。

0.2.3 修复了退后台时的接收空档。选择原生推送且获系统授权后，前台也维持独立原生 WebSocket 观察，前台只抑制系统通知；切后台保持已有连接，异步核对配置，不再先断线等待 `/api/config`。关闭原生推送或撤回系统授权时停止接收。后台每 15 秒单飞补拉 pending，覆盖只有持久化记录、没有即时广播的回复；切前台、关闭、切服或销毁时清除补拉定时器。

首次绑定或启用时等待一次静默 HTTP 基线，空历史也记录 `baselineInitialized`，不会把之后首次出现的新回复再次当作初始历史。HTTP 游标只由 pending 返回的行推进，前端和 WebSocket ID 仅进入已见集合，避免实时专用 ID 跳过未拉取的持久事件。同一会话及有效正整数 `message_id` 的完成回复跨 pending / WebSocket 去重，不把同会话的其他审批或新回复粗略合并。旧游标失效或不存在时回查历史，保留旧游标之后的新行，已知旧事件仍受去重和服务端已读标记约束。

后台没有发出通知的 WebSocket 重放不进入已见或消息去重集合，前端 `updateLastSeenEventId` 也仅接受前台标记。这样即使重连时 HTTP 补拉暂时失败，随后收到的静默重放或仍在后台运行的网页也不会阻止下一次 pending 补偿。

配置请求只带当前服务器作用域的认证 Cookie，禁止重定向并限制响应大小；不记录或保存完整配置内容。异步配置读回受连接与设置代次约束，切服、销毁或后续显式桥设置可使旧请求失效。系统授权拒绝仍保留服务器选择的原生方式，之后从系统设置授权即可恢复。

0.2.0 至 0.2.2 的历史模拟器验证包含后台发送系统通知和点击后定位会话；这些结果不能证明本次用户报告的真机问题已解决。0.2.3 的新增定向代码回归覆盖退后台空档、空基线、游标来源、跨路径去重、轮询清理、授权变化及语言切换，本轮尚未完成设备安装和启动复验。通知点击期间若用户选择了其他服务器，旧密码查询、登录快照和连接失败会因代次失效而停止，不再覆盖新页面。

设置页在服务器推送模式之外独立显示系统通知授权与实际接收状态。`refreshStatus()` 通过 `notificationManager.isNotificationEnabled()` 查询，未获授权显示拒绝、系统查询异常显示未知；不会把查询失败误报为用户拒绝，也不会因此修改服务器 `push_mode`。返回应用时重新检查；系统撤销授权后停原生订阅，重新授权后恢复仍被用户选择的原生接收方式。异步读回带连接与设置代次保护，旧服务器或旧授权查询不能覆盖新状态。该 API 的 Promise 重载从 API 11 起提供，本轮 SDK 定义见 `openharmony/ets/api/@ohos.notificationManager.d.ts` 第 502 至 520 行。

授权已允许但原生接收未启用时，接收状态显示“已关闭”；接收已启用且无错误、连接尚未建立时显示“已就绪”，原生 WebSocket 确认建立后显示“已连接”，前台和后台均可处于已连接状态。授权、接收方式和实际连接分别报告，不能把未连接直接当作权限拒绝或连接错误。通知标题与状态错误按当前语言即时更新。

发布请求已指定 `notificationSlotType: SERVICE_INFORMATION`；配套 SDK 的 `notificationManager` 声明说明，指定的槽不存在时会自动创建，该类型对应高提醒等级。因此未显式调用 `addSlot` 不能直接认定为全部消息缺失的原因。系统用户设置仍可关闭对应槽；同一服务器和通知主题使用一致的 ID / label 发布、更新和撤销。

原生 WebSocket 只在应用进程仍获准运行期间工作。进程被系统挂起或结束后，不承诺立即收到通知；恢复时补拉事件。能力状态明确为 `backgroundDelivery: "while-process-running"`。没有以无关音频或其他后台任务类型制造常驻效果，也未声明已完成厂商推送接入或长时间锁屏验收。

2026-11-06 真机复测确认：用户重新打开应用、连接服务器后按 Home 返回桌面并保留最近任务，HDC 查询仍有应用进程，AbilityManager 的应用和页面状态均为 `BACKGROUND`，两次读取该进程的 `cgroup` 都包含 `freezer:/Frozen`。系统不允许读取该组的 `freezer.state`，因此记录的是冻结组归属，没有声称读到了内核冻结状态值。这与此前清理最近任务后进程退出是两个不同场景；仅要求用户保留最近任务不能解决当前后台接收问题。当前 HAP 声明版本为 `0.2.3 / 203`，安装时间晚于本地最终 HAP 导出时间，但未取得已安装模块哈希，不能仅凭版本标签证明安装字节完全一致。

要解决冻结或结束进程后的投递，需独立的系统级消息通道：客户端取得并更新 token，按已认证服务器及账号绑定；服务端或受信中继调用推送 REST 接口；通知点击保持导航校验，并与前台消息去重。云端应用及签名身份、服务端授权、消息分类权益和账号切换解绑须一起验证，服务端密钥不得打入 HAP。当前没有这条链路；0.2.4 按维护者决定停止接入，将后台限制保留在 PR 与维护文档中，不宣称已解决，也不影响应用已有功能的启动和使用。

配套 SDK `hms/ets/api/@hms.core.push.pushService.d.ts` 说明 token 需要上报应用服务器，由服务器调用推送 REST 接口；仅调用客户端 `getToken()` 不能完成端到端投递。`openharmony/ets/api/@ohos.resourceschedule.backgroundTaskManager.d.ts` 则限定 `DATA_TRANSFER` 为有进度的真实上传下载、`VOIP` 为真实音视频通话，手机上的 `TASK_KEEPING` 需要受限 ACL 权限。当前普通任务完成提醒不应通过这些不匹配的任务类型绕过冻结，也不应把系统后台限制归结为通知权限未开启。

通知携带的是原生生成的一次性随机标识；实际导航数据仅保存在应用偏好中，消费时核对已保存服务器清单，并在对应服务器登录和页面就绪后定位。只有首次基线静默接收历史；已经建立基线后的游标恢复保留较新的未读事件，避免遗漏后台回复。

Forge 仓库变化使用服务端 `forge_event` 的 `data.event` 与 `data.item` 契约生成实时系统通知。议题、合并请求按编号定位，流水线按 `run_id` 与 `pipeline/run:<id>` 定位，并保留所属项目路径；冷启动时再次校验这些字段，重放事件不弹。当前服务端 pending 端点不持久化 Forge 事件，因此本实现不推进 Forge 补拉游标，也不承诺应用挂起后的仓库事件补发。Forge 未读状态仍由网页恢复时从服务器加载。
