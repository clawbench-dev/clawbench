## 一、为什么要转到服务端

### 1.1 开发效率的瓶颈在 Check

开发的本质是一个 **PDCA 循环**：Plan（计划）→ Do（执行）→ Check（检查）→ Action（调整）。人开发是这样，AI 开发也是这样。

用 AI 之后，Plan 和 Do 已经很快了——你提需求，AI 自动计划、自动写代码。**瓶颈落在了 Check**，也就是测试环节：

| 你想要 | 就需要 |
|---|---|
| 结果**对** | 大量测试用例覆盖业务逻辑 |
| 循环**快** | 足够高的硬件性能，让测试跑得完 |
| 全天候**久** | 一台不关机的机器 |

这三点都指向同一个结论：**PC 端撑不住**。一台 16G 内存、8 核的笔记本，跑几千个用例就要等很久；而且环境要人人重搭，脚本支持度、编码、换行符都是坑。

所以：把开发从客户端搬到服务端。

### 1.2 服务端的三个优势

| 优势 | 具体表现 |
|---|---|
| **环境** | 搭一次全员共享。Java / Go / C++ 以及各种依赖库统一装好，缺什么大家一起补一次，之后谁都不用再装 |
| **性能** | 几十个核心、数百 G 内存，可以放开跑大型项目的全量测试 |
| **不断电** | 7×24 在线，晚上的垃圾时间可以拿来做 review、补测试、跑长任务 |

> 这不是为了造轮子而造轮子。之所以自研，是因为**现有工具都不满足「服务端执行 + 客户端可视化」这个组合**。用命令行的方式在服务端开发效率也不错，但图形界面更符合大多数开发人员的工作习惯。

## 二、思维方式的四个转变

功能只是工具，**用不好往往不是工具的问题，是习惯没转过来**。以下四点值得反复强调。

### 2.1 把工作全部纳入 AI 体系

不只代码——**需求、调研、写文档、排障、运维，全部走同一个入口**。

**为什么**：纳入体系之后，你的所有会话都进了同一个库，可以全文检索、可以互相交叉关联。半年下来的工作大概也就占 2G 资源，但你可以随时倒查：

- 当时为什么这么设计？
- 这个特性为什么会有这个功能？
- 上次那个卡死问题是怎么解决的？

**并且这个倒查可以让 AI 替你去做**（见 [4.2](#42-用-ai-检索历史cb-chatsearch)），不用自己翻。

**具体做法**：给每类工作建一个工作区（项目）：

- 主线开发 → 单独一个项目目录
- 日常杂活 / 文档 / 调研 → 一个「日常工作」项目
- 每个人在 `data` 上建一个**个人仓库**，杂七杂八的东西都往里放

> ⚠️ **唯一事实源是你的仓库**。服务器上的目录、钉钉知识库、本地电脑，都应该是仓库的**副本**，不是另一个正本。否则会出现「今天在那边改一下，明天在这边改一下，最后两边不一致」。

### 2.2 借 AI 的眼睛看代码

**停止逐行纠结实现细节**，改为看**意图、边界、影响面**。

自己打开代码一行行点着看，有效，但**太原始、效率太低**。让 AI 把 API、语法这类细节从阅读过程中剥离掉，你只关注业务逻辑实现。

**粗与细完全取决于你怎么问**：

| 你的问法 | 得到的结果 |
|---|---|
| 「梳理一下这个项目」 | 很粗的概览 |
| 「梳理一下数据接入流程」 | 细一些 |
| 「梳理一下数据接入流程里的通道管理 / topic 管理」 | 更细 |

很多人觉得「AI 梳理得太粗、老漏东西」——**其实是你压根没让它细理**。

> 说句不客气的：大部分人看代码的能力，**绝对不如 AI 一根毛**——哪怕是我自己，看代码能力也就 AI 的一根毛。给它合适的上下文、合适的力度、合适的角度，它的准确性和完整性都远超我们自己。

**适用场景举例**：一个概率性卡死的问题，你自己找半天找不到。但如果你把范围框死——「数据接入的查询流程里，调某接口时经常概率性卡死，我怀疑是死锁或某些静态逻辑」——AI 大概率能揪出相关的代码细节。哪怕它指出的不是最终根因，也能给你一批**可能导致这个问题的线索**，而这往往是人自己看不出来的。

### 2.3 把执行交给 AI，你审证明

**第一反应不是自己去验，而是让 AI 想办法向你证明它解决了。**

AI 说「已修复」时，不要直接信，也不要自己埋头重跑一遍。**让它自证**：

> 「你先用最小的方式把对应模块跑起来，通过接口或内部调用复现这个问题；然后用你改完的代码再调一次，看是不是真的解决了。」

然后**你去观察它的验证步骤**：

- 它跑了什么？看到了什么？
- 边界情况怎么处理的？失败路径呢？
- 结论和证据对得上吗？是不是只测了 happy path？有没有循环论证？

验证逻辑没问题，就可以比较相信它真的修好了。**最终验收当然还是由人做**，但在此之前让 AI 把该做的都做掉，能把你验收时的通过率从 60% 提到 90–95%。

> **算一笔账**：如果你不做这一步，直接自己验，可能有 40% 的情况会漏掉问题，于是要回头跟 AI 说「你刚改的有问题」，AI 又得吭哧吭哧重来一遍。**本来一轮能解决的事变成了好几轮，中间浪费的是你的时间。**

你的角色从「验证结果」升级为「**挑证明的漏洞**」。

### 2.4 不懂就学：AI 输出不是黑箱

上面三点容易让人走向一个极端：AI 很能干、能看代码、能写代码、还能自证——那我把它当黑箱不就行了？

**这是必须警惕的。**

AI 会输出很多你没用过的技巧、思路、方法：Chrome DevTools 的高级调试技巧、C++ 的二进制调试手法…… 这些东西你原来都不会。

**你不需要学到能亲手复现的程度**，但你需要知道：

- 什么场景下该用什么技巧？
- 什么场景下该用什么工具？
- 什么场景下该用什么架构？
- 什么时候该用哪种测试方法？

也就是——**学架构层面、设计层面的思路，而不是编码层面**（调什么 API、用什么函数库，这些不用学）。

**为什么这点很关键**：AI 给你三个方案，A 有什么好处、B 有什么好处、C 有什么好处。如果你都不懂，就只会说「你推荐哪个就哪个吧」，然后下一步它又给三个方案，你又选一个……

- **短期**：小项目不会有大问题
- **长期**：**技术债会逐步累积**。你压根不知道它在用什么，也不知道这些东西有哪些局限性。等到发现「当时这个选型确实不太合适」的时候，架构就得调整，技术债就得还了。

所以底线是：**AI 输出的东西，你要处于「基本能看懂」的状态**。不要求全面看懂——我自己也经常有看不懂的——但用了什么方案、什么架构、什么技术，你都应该有对应的理解。

## 三、单人多线并行：四个机制

这是 ClawBench 与目前主流智能体最大的区别：**多线执行，但我同时只看一件事**。

> **为什么不建议同时刷多个窗口**：以前在本地开发，很多人（包括我自己）会开三个窗口，三个都在刷，东看看西看看。这种做法大脑的**上下文切换非常频繁，会非常累**。
>
> 正确姿势：聚焦当前在干的事，让它先跑着；有必要介入时才切过去。**同一时间只看一个东西。**

### 3.1 多会话

![会话列表](../user-guid/screenshots/sess-01-list.png)

一个项目内可以开任意多个会话，**每个会话独立干活**。界面结构：

| 位置 | 内容 |
|---|---|
| 顶栏 | **项目列表**，一键切换项目，原项目不中断 |
| 顶栏 | 当前项目的**分支**列表，一键切换 / 管理 / 删除 |
| 顶栏 | **工作区**切换、**最近打开的文件** |
| 右侧 | 当前项目的**会话列表** |
| 右侧底部 | **「其他项目」分组**——其他项目里待你推进的会话 |

**会话项交互**：

| 操作 | 效果 |
|---|---|
| 单击 | 切换会话 |
| 右键 | 置顶 / 取消置顶、重命名、设置标签、归档 |
| 悬停 | 出现归档按钮 |

**标签**：会话多了以后可以打标签分类，比如「已 review」「已验证」，之后点标签过滤。少的时候不必用。

> 💡 **给会话起名字**：右键 → 重命名，别让它一直叫「未命名会话」。多个会话并行时，标题是你在「其他项目」列表里唯一能快速识别它的东西。

#### 分叉（Fork）：从某条消息另起一条线

![斜杠命令菜单](../user-guid/screenshots/chat-02-slash.png)

AI 给了好几个方案，你一个都不懂，怎么办？**分叉出去问**。

1. 在要分叉的消息上点**分叉会话**，创建一个新会话
2. 在新会话里逐条问：「这个东西是什么？什么含义？什么场景下用？」
3. 原来的会话**不动**，继续按正常节奏干活

这样分叉出来的会话就成了你的**学习和调研台**，原线不受任何影响。

#### 回溯（Rewind）：聊错了的后悔药

如果发现前面聊错了方向，在要回退的那条消息上点**回溯会话**，把后面的内容截断掉。

- 回溯会**把截断前你问的下一句话放回输入框**，你可以改一下再重新问
- 回溯会同时**清空计划面板**（计划不持久化，属于设计如此）
- 对话上下文保留，不用重开

### 3.2 多 Worktree

![工作树管理](../user-guid/screenshots/git-04-worktrees.png)

**一条线一个 worktree，主工作区不受污染。**

**什么时候用**：你手头的工作区还有未提交的改动，不想动它，但又要开一条新线干活。

**怎么创建**（直接用自然语言说就行）：

> 「帮我创建一个 worktree」

AI 会问基于哪个分支创建，你选一个（比如 main），再让它建一个新分支。它会：

1. 建一个分支
2. 建一个独立目录，把分支的内容切出来

**结果**：当前工作目录完全不受影响，你在新目录里怎么改都行。

**怎么用起来**：

- 在「项目历史 → 管理 → 工作树」里能看到这个新工作区
- 点它 → 「将这个工作区作为项目打开」→ 进入独立工作区
- 它会在**同一个项目下**显示为另一个工作区，随时切回去
- 两边可以**同时干活，互不影响**

> Worktree 本质上是**同一个项目的两个工作区**，也可以理解成两个项目。

**聊天里出现的 worktree 路径会被自动标注**，点击可直接跳转到该 worktree 下的文件。

> ⚠️ **纪律**：提交时**只 `git add` 明确路径，不要用 `git add -A`**。多只手在同一棵树上时，`-A` 会把别人的改动一起卷进你的提交。

### 3.3 多项目热切换

- 顶栏项目列表一键切换，**原项目正在跑的会话不会中断**
- 各项目的会话、任务、Git 状态、文件树完全独立
- 切换项目时**聊天输入草稿会保留**，切回来自动恢复
- 项目 = 上下文边界（会话归属、cookie 作用域都跟着走）

**跨项目跳转**：会话列表底部的「其他项目」分组列出其他项目的活跃会话，点击直接跳转（注意跳过去后是在**那个项目**的上下文里对话）。

### 3.4 跨项目通知

这是多线并行能成立的**关键**——你不用盯着每条线，线会来找你。

![应用内完成通知](../user-guid/screenshots/00-completion-popover.png)

| 渠道 | 说明 |
|---|---|
| **「其他项目」tab** | 列出其他项目中**运行中 / 未读 / 待审批**的会话，是主动巡检的入口 |
| **应用内完成卡片** | 会话完成 / 取消 / 待审批、任务启动 / 完成 / 失败 / 取消、仓库议题与合并请求变化，滑入一张纯通知卡片，点击跳转并标记已读，5 秒自动消失 |
| **跨项目标识** | 事件属于其他项目时，卡片整张换色，底部显示「外部」标签 + 项目名 + 完整路径 |
| **系统通知** | 页面最小化或不在前台时走操作系统通知（浏览器与 App 模式都可用） |
| **手机推送 / IM** | 原生推送、钉钉、飞书，手机不在电脑旁也能收到 |

**典型场景**：一条线卡在**待审批**，你切走干别的去了。回来后通过「其他项目」tab 或完成卡片把它捞回来。

> **通知是可以关的**：设置 → 推送通知。但注意「推送方式」和「浏览器系统通知」**互不影响**——想彻底静音要两处都关。

## 四、把上下文喂给 AI：引用与检索

### 4.1 五种引用方式

| 方式 | 操作 | 适用 |
|---|---|---|
| **@ 引用** | 输入 `@` 唤出文件菜单，会优先列出你**最近打开过的文件** | 引用项目内文件 |
| **拖拽** | 直接把文件拖进输入框 | 本地文件、分享出去的文件 |
| **粘贴** | 直接粘贴剪贴板里的图片或文件 | 截图 |
| **选中文本引用** | 在聊天或文档里选中一段文字，点「+」加进来 | 让 AI 改某一段 |
| **行范围引用** | 引用文件时指定行范围 | 只把需要的片段送进去 |

**选中文本引用是最常用的**——它会**带上行号**，所以 AI 知道这段东西在文件的哪一行，能精准定位去改。

> **推荐的工作方式**：文档尽量让 AI 写，你只做微调。看到哪段不对，选中 → 加进来 → 「这段不太符合我的要求，我希望……」→ 让它改。

引用进来的内容会显示为 chip，标注文件路径与行号，点击可预览确认。

### 4.2 用 AI 检索历史：`/cb-chatsearch`

![会话搜索](../user-guid/screenshots/sess-06-search-rag.png)

**这是「所有工作都纳入体系」最大的回报。**

场景：你遇到了一个问题，记得以前解决过，但想不起来具体情况。

**不要自己搜出来再告诉它**，直接让它搜：

```
/cb-chatsearch 我之前遇到过一个概率性卡死的问题，帮我检索一下当时是怎么定位和解决的
```

AI 会自己去查历史会话，把当时的情况读出来，然后把**你的工作从历史到现在联系起来**，而不是割裂的两件事。

**检索范围**（AI 会自动判断，你也可以直接说）：

| 说法 | 范围 |
|---|---|
| 「这个项目」/ 不提 | 当前项目 |
| 明确点名某个项目 | 那个项目（含**目录已被删除**的项目，历史仍可查） |
| 「跨项目」「所有项目」「到处找找」 | 全部项目 |

**也可以直接用界面搜**：会话搜索抽屉支持混合 / 全文检索，以及归档状态、排序、类型、时间范围筛选。

> 💡 数据都在数据库里，所以你也可以直接让 AI「到项目数据库里帮我找 xxx」。另外，**项目整体删掉了，历史记录仍在**，仍然搜得到。

### 4.3 引用议题与合并请求

绑定 GitHub / GitLab 后（见 [5.2 事件任务](#52-事件任务)），Forge 详情页的引用按钮可以把 issue / PR 作为附件带进聊天，chip 显示 `owner/repo#123`，还能再划取文本补充。

于是可以：「谁在 GitLab 上提了个议题 → 我直接引用这个议题 → 让它改」。

### 4.4 查看用量：`/cb-usage`

```
/cb-usage 最近 30 天各个项目的 token 消耗分别是多少
```

适合用来做跨项目的用量对比（会自动按项目分组）。

**界面上也能看**：Dock →「数据统计」，三个子页签：

![用量统计](../user-guid/screenshots/09-stats-usage.png)

| 页签 | 内容 |
|---|---|
| **用量统计** | 按时间 / 模型 / 后端统计 token 消耗、缓存命中率、Credit，含环形图与维度明细表 |
| **代码存量** | 按语言统计项目代码行数 |
| **代码增量** | 指定时间窗内按作者统计新增 / 删除 / 净增行数与提交数 |

> **代码增量建议关注一下自己的数字**。正常特性开发或新软件开发，每天代码产出效率**至少应该在 800 行左右**。如果只有一两百行，说明效率提升跟以前人工开发没多大区别。
>
> （传统人工开发的效率大概每天 150–200 行。这是团队用来对齐的标准，不是硬性考核。）

### 4.5 终端与快捷指令

![终端](../user-guid/screenshots/term-01-tabs.png)

Dock →「终端」是服务器上的**真实 PTY 会话**，可以开多个标签。

**快捷指令**：把常用命令存起来（点工具栏的小闪电图标），之后一键写进当前终端。

> 快捷指令只作用于**当前可见的活动终端标签**，不会误发到后台标签。
>
> ⚠️ 终端执行的是服务器上的真实命令，权限与运行 ClawBench 的用户一致。破坏性操作请谨慎。

## 五、把夜晚用起来：任务自动化

> **核心思路**：人每天只上班 8–10 小时，但服务器 24 小时开着。**晚上的时间让 AI 接着干**——把任务时间定到凌晨，第二天来看结果。

### 5.1 定时任务

![任务列表](../user-guid/screenshots/task-01-list.png)

**适合夜间跑的事**：

| 用途 | 说明 |
|---|---|
| **代码 review** | 最核心的用途。每晚 review 新提交的合并请求 |
| **问题定位** | 新提交的 issue 自动定位 |
| **测试补充** | 测试用例不达标时，让它自己补——**补一晚上可能就达标了** |
| **调研** | 需要长时间阅读资料的调研任务 |
| **自动化测试** | 自动化编译 → 部署 → 测试，第二天看结果 |

**两种创建方式**：

1. **界面创建**：Dock →「任务」→「+」新建任务，填名称、执行 Agent、频率、提示词
2. **对话创建**（更简单）：直接说

```
/cb-task 帮我建一个任务，每天凌晨 3 点 review 新提交的合并请求
```

AI 会问你多久跑一次、用哪个 Agent、提示词是什么，然后创建。

> ⚠️ **必须走 `/cb-task`**。如果直接让 AI 自己建而不带这个命令，它可能建出一个**不受管理的临时任务**——理论上是能干活，但你在界面上看不到、也管不了。走 `/cb-task` 才会落到任务系统里，你才能在「任务」面板看到卡片、查看执行记录。

![任务创建表单](../user-guid/screenshots/task-02-create.png)

**执行记录**：点任务项进详情页，能看到每次执行的状态、耗时、摘要与**完整原文**。

- 执行失败（比如后端异常）→ 点**「继续对话」**让它接着往下干，不用从头重跑
- 每个执行记录**独立计数未读**，点进具体执行才标记已读

### 5.2 事件任务

让任务**监听仓库事件**，事件一到自动触发，形成闭环。

**可监听的事件**：

| 分组 | 事件 |
|---|---|
| 议题 | 新建、关闭、重新打开、评论 |
| 合并请求 | 新建、关闭、合并、重新打开、评论 |
| 流水线 | 流水线完成 |

**配置步骤**：

1. 设置 → GitHub/GitLab 集成，按 host 保存访问令牌
2. 在「议题与合并请求」面板绑定仓库（从项目 git remote 自动识别，自建实例需确认 host）
3. 新建任务时触发方式选「事件」，勾选要监听的事件，写提示词

**事件变量**（触发时会自动替换）：

| 变量 | 说明 |
|---|---|
| `{{TITLE}}` / `{{NUMBER}}` / `{{URL}}` / `{{BODY}}` | Issue/PR 的标题 / 编号 / URL / 正文 |
| `{{AUTHOR}}` / `{{ACTION}}` / `{{REPO}}` | 操作者 / 动作名（如 `opened`）/ 仓库全名 |
| `{{PIPELINE_STATUS}}` / `{{PIPELINE_BRANCH}}` / `{{PIPELINE_URL}}` | 流水线状态 / 分支 / URL |

示例提示词：

```
新 Issue「{{TITLE}}」已打开，请查看 {{URL}} 并给出分析。
```

**完整闭环**：

```
有人在 GitLab 提 issue
  → 事件任务自动触发
  → AI 定位问题原因
  → 你审查定位结论
  → 正确 → 让它继续解决问题
  → 不正确 → 让它调整
```

> **注意**：事件任务需要项目**已绑定仓库**，否则永远不会触发。未绑定时表单会显示警告。
>
> **AI 自身事件抑制**：AI 在对话中自己执行的操作（比如它去评论了 Issue）产生的事件**不会再次触发**任务，避免「AI 动作 → 事件触发 → AI 再响应」的死循环。

## 六、多线并行的纪律

多线并行最大的风险不是工具，是**多只手在同一棵树上互相踩**。以下是必须遵守的几条。

### 6.1 资源避让

**跑测试、跑构建前，先看别人在不在跑。**

```bash
ps -eo pid,ppid,etime,cmd | grep -E "vitest|go test|npm run build" | grep -v grep
```

有就等一下，不要并发起跑。原因：

- 并发争抢 CPU / 内存会把对方拖到超时，产生**成片的假失败**
- 同一命令并发下可能撞 600s 超时，单独跑只要 128s
- `npm run build` 与全量 vitest **绝不能同时跑**，会 OOM 被 Killed，并把结果污染成假失败

**优先跑隔离测试**（单文件、单包），能用隔离测试回答的问题就不要跑全量。

### 6.2 提交安全

| 规则 | 原因 |
|---|---|
| 只 `git add` 明确路径，**不用 `git add -A`** | 会把并发的他人改动卷进你的提交 |
| 提交前**逐文件看 diff** | 确认改动范围符合预期 |
| 发现「改动被回退」先别动手 | 大概率是并发 agent 的中间态，先核对 |
| 绝不用 `git stash` | 多只手场景下会误弹别人的 stash |

### 6.3 数据安全

- **唯一事实源是你的仓库**，服务器上的目录只是工作副本
- **数据存两份**：服务器磁盘也可能损坏，定期上库
- PC 上保持干净，不用维护太多东西

### 6.4 只用这一个工具

> **大家尽量不要用别的（CLI），切过来，有问题我们解决问题。** 把问题提上来，才能把这个东西搞稳定、搞好用。

如果遇到问题就退回原来的工具，问题永远暴露不出来，工具也永远稳定不下来。**有问题就在群里反馈**，这是让工具变好用的唯一路径。

## 七、常见问题：症状 → 解法

| 症状 | 根因 | 解法 |
|---|---|---|
| 两个会话改同一文件，改乱了 | 共享同一工作区 | 用 **worktree 隔离**，一条线一个工作区 |
| 切项目回来，消息 / 输入没了 | 项目热切换会重建组件树 | 输入草稿会自动恢复；**消息以数据库为准**，刷新即重建 |
| 提交里卷进了别人的改动 | 用了 `git add -A` | 逐文件看 diff，只 add 自己的路径 |
| 测试超时 / 成片失败 | 与并发 agent 争抢资源 | 先 `ps` 查，隔离单跑 |
| 会话卡着不动，AI 不回复 | **在等审批** | 去「其他项目」tab 或完成卡片找**待审批**标记 |
| 代码和 diff 对不上 | 并发 agent 改了同一文件 | 比对文件 mtime，确认是谁后写的 |
| 杀进程误伤主服务 | 用了模糊匹配 | **只按端口或记录过的 PID**，绝不按子串扫全表 |
| AI 一直不回复（确实卡死） | 进程异常 | 用错误横幅上的**重置会话**重启 AI 进程，对话上下文保留 |
| 刷新后消息重复 / 丢失 | 流式内容尚未落库 | ClawBench 以数据库为权威，稍等再刷新 |
| 定时任务报错没跑完 | 后端异常（如 Agent 报错） | 进执行详情，点**「继续对话」**接着跑 |

## 附录 B：内置斜杠命令

ClawBench 内置命令以 `/cb-` 为命名空间，**绝不会与智能体自带的命令冲突**（其他 `/xxx` 会原样转发给智能体）。

| 命令 | 用途 | 说明 |
|---|---|---|
| `/cb-chatsearch <查询>` | 检索历史会话 | 可指定项目，或跨所有项目检索。需要 RAG 已就绪；**必须带查询内容**，空查询会被拒绝 |
| `/cb-task <需求>` | 管理任务 | 创建 / 查询 / 修改 / 删除任务与执行记录。**创建定时任务请务必用它**，否则任务不受管理 |
| `/cb-usage <需求>` | 查看 token 用量 | 支持当前项目 / 指定项目 / 全部项目（跨项目时自动按项目分组） |

> **命令必须位于消息开头才生效**。输入 `/` 会弹出菜单，内置命令带「内置」标签。
