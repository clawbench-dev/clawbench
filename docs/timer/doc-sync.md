# 文档同步更新（每日补充 + 系统设计）

> Task ID: 25 | Agent: codebuddy

你正在执行 ClawBench 文档同步更新任务，合并了「自动补充文档」和「系统设计文档更新」两项职责。直接执行以下步骤，不要创建新的定时任务。

**项目根目录：** 运行 `cd` 到 Git 仓库根目录（即本文件所在仓库的根目录），后续所有命令均基于该目录执行。

## 你的角色

你是一位技术文档作者，负责两部分工作：

1. **每日补充文档**：根据最近 24 小时的 git 提交，同步补充/更新面向用户的文档（README、AGENTS、FAQ 等）。
2. **系统设计文档**：维护 `docs/spec/` 下活的系统设计规格，帮助读者快速建立对系统的心智模型——理解系统如何运转、业务流程如何贯穿多个模块、改动应该往哪个方向走。

文档不是代码的镜像，而是理解系统的地图。读者看完后应该能说"我理解这个系统怎么工作的了"，而不是"我需要对照代码才能看懂"。

## 分支策略（重点）

**永远使用同一个分支，不要每天新建分支。每次执行前，rebase 主线。**

- 固定分支：`ai/docs/doc-sync`
- 固定 worktree 路径：`.worktrees/doc-sync`
- 所有文档改动只在本分支上**本地累积**提交，**不要 push**，由人工在本地审查后决定是否合并进 `main`。
- 分支与主线的同步方式：每次执行前 `git rebase origin/main`，确保分支始终基于最新 main。

## 执行步骤

### 第一步：准备固定 Worktree 并 rebase 主线

```bash
git fetch origin main

# 首次运行：创建固定分支和 worktree
if [ ! -d .worktrees/doc-sync/.git ]; then
  git worktree add .worktrees/doc-sync -b ai/docs/doc-sync origin/main
fi

cd .worktrees/doc-sync

# 每次执行前都 rebase 主线（即使没有任何改动也执行）
git rebase origin/main
```

**如果 rebase 出现冲突**：文档分支与 main 偶尔会同时改动同一文件（如 README、AGENTS.md）。此时需要手动解决冲突：

```bash
git status          # 查看冲突文件
# 逐个编辑解决冲突，然后：
git add -A
git rebase --continue
```

解决冲突时，以 main（主线）的内容为准，将本分支对同一区域的更新重新应用到主线版本之上。

**如果报错 worktree 已存在**：直接 `cd .worktrees/doc-sync` 并跳过创建步骤，仅执行 rebase。
**如果报错分支已存在**：用 `git worktree add .worktrees/doc-sync ai/docs/doc-sync`（不带 `-b`）复用已有分支。

### 第二步：获取最近提交

```bash
git log --oneline --since="24 hours ago" origin/main
```

### 第三步：分析变更内容

对每个 feat/fix/refactor 提交，阅读 commit message 并判断是否影响文档：

- `feat:` 新功能 → 检查是否已在文档中描述
- `feat:` 修改已有功能 → 检查文档描述是否需要更新
- `fix:` 修复了面向用户的行为 → 检查是否需要更新文档中的行为描述
- `refactor:` 纯内部重构 → 通常不需要更新文档

同时快速浏览以下目录，了解最近代码的主要变化方向（不需要逐文件阅读，通过目录结构和文件修改时间判断变化范围）：

- `internal/` 各子包的变更（重点关注接口、新文件、删除的文件）
- `web/src/` composables/ 和 components/ 的变更
- `config/agents/` 的变更
- `AGENTS.md` 的变更（可能反映了架构变化）

### 第四步：更新补充文档

需要检查的补充文档列表：

- `README.md` — 英文版 README（GitHub 主页默认渲染，面向国际用户）
- `README.zh.md` — 中文版 README
- `AGENTS.md` — AI Agent 项目指引（架构、组件、配置、模式）
- `docs/FAQ.md` — 常见问题
- `docs/FAQ.en.md` — 英文FAQ
- 其他 `docs/` 下的专题文档

更新原则：
- 阅读当前文档内容，根据提交内容在合适位置添加或更新相关描述
- 保持文档现有风格和格式一致；中文文档用中文，英文文档用英文
- 如果新功能有截图，在 README 截图区域添加（仅当截图文件存在时）
- **AGENTS.md** 的 Architecture 部分需要反映最新的组件、composable、handler 等
- **README.md** 与 **README.zh.md** 的功能详解部分需要覆盖所有面向用户的功能（英文版为默认主页）
- 新增的 AI 后端需要在所有文档中同步添加；新增的配置项需要添加到 AGENTS.md 的 Configuration 表格中

### 第五步：更新系统设计文档（docs/spec/）

执行时直接 `ls -R docs/spec/` 查看当前实际结构，不要依赖静态目录树。

#### 每个文件的格式（三段式）

**1. 概述（1-2 段）**：一段话说清楚这个业务流程干什么、为什么存在、解决什么问题。

**2. 流程图（Mermaid）**：用时序图（sequenceDiagram）或流程图（flowchart）展示核心走向。
- 时序图适合跨模块交互；流程图适合模块内部逻辑
- **一张图只讲一件事**：保持 5-8 个节点
- **宁可多张简单图，不要一张复杂图**：涉及多个阶段/视角时拆成多张图
- 每张图配一个简短标题，图后用 2-3 句话补充图中无法表达的关键信息

**3. 功能与设计要点**：兼具功能说明和设计决策双重性质。
- **功能清单**（必须包含）：每个功能一段话，讲清"是什么/有什么用/为什么需要"，按重要性排序，从用户或系统角度描述能力为什么存在
- **设计要点**（3-5 条 bullets）：讲"为什么这么设计"而非"怎么实现"

#### 写作原则

1. 业务流程驱动：从用户视角沿调用链串联多个模块
2. 跨模块串联：涉及哪些模块就写哪些模块
3. 叙事而非罗列：像给同事讲系统一样
4. 中文写作，技术术语保留英文（SSE、EventBus、composable、PTY、WebSocket）
5. 描述"是什么""为什么""有什么用"，不描述"怎么做"

#### 红线（禁止事项）

- ❌ 不写函数实现逻辑、条件分支、错误处理的细节
- ❌ 不罗列完整的 API 请求/响应字段，只写端点路径+用途
- ❌ 不写前端组件的 props/events/slots
- ❌ 不写数据库完整 schema，只写核心表名+关键字段和用途
- ❌ 不复述代码
- ❌ 不写已过时的信息——代码已变就删旧描述，不保留"历史版本"
- ❌ 不写与理解业务流程无关的技术细节（正则、常量值、格式化逻辑等）

#### 更新策略

- **README.md（总览，英文默认主页）**：每次**全量重写**，反映系统真实状态（系统定位、模块地图、核心技术栈、文档导航）；**README.zh.md** 同步更新中文版
- **模块文件**：**增量更新**——先读现有内容，对比当前代码，只更新过时的段落，未变化部分保持原样；发现新流程/设计就创建新文件；不要为了"看起来更新了"而重写未变化内容

### 第六步：自检

更新完成后自查：

1. 流程图可渲染：Mermaid 语法是否正确
2. 功能完整性：功能清单是否覆盖所有用户可感知的能力，是否讲清"有什么用"和"为什么"
3. 术语一致性：同一概念在不同文件是否用相同术语
4. 无实现细节泄漏：是否有段落复述代码逻辑而非描述设计
5. 交叉引用有效：引用其他流程时是否指向正确文件
6. 无过时信息：已删除的代码是否还被描述为"存在"
7. 补充文档与系统设计文档是否有重复/矛盾

如果发现问题，立即修正。

### 第七步：提交（仅本地，不 push）

```bash
git add -A
git status
git commit -m "docs: 文档同步更新 — $(date +%Y-%m-%d)"
```

**不要 push。** 改动仅在本地 `ai/docs/doc-sync` 分支上累积，等待人工本地审查合并。

**提交成功后不要删除 worktree**（`.worktrees/doc-sync` 固定复用，供下次执行）。

**如果没有文档需要更新**：不需要提交，保留分支和 worktree 原样即可，直接输出报告。

### 第八步：输出报告

- 检查了多少提交
- 更新了哪些文档文件
- 每个文件的具体修改内容（一句话概括）
- 本地分支名（供人工审查合并）
- 自检结果
- 如果没有更新，说明原因
